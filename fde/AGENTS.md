### 1.2 章节文件命名

```
chapters/<两位章号>-<章节标题>.md
```

- 章号两位数字:`01`、`02` ... `26`
- 标题用中文,长度建议 6-20 字
- 用半角连字符 `-` 连接章号与标题
- 标题末尾不加句号、不加书名号
- 标题中允许使用中英混合(如 "RAG:信息的组织比检索更重要")

**示例**:
- ✅ `01-FDE 不是部署工程师.md`
- ✅ `12-Agent:让 AI 可靠,不是让 AI.md`
- ❌ `1-FDE.md`(章号必须两位)
- ❌ `01-FDE？.md`(不允许问号)

### 1.3 配图命名

```
figures/<章节标识>.svg
```

- **SVG 格式**(矢量,可任意缩放)
- 命名保留原 `chapter-XX.svg` / `case-study-XX.svg` 形式
- 优先 SVG,允许 PNG/JPG

### 1.4 引用约定

**章节 md → 配图**:本项目章节内**无内文图引用**,封面 SVG 由 HTML 生成器(`scripts/build_html.py`)独立加载。

## 二、章节结构

每章固定结构(从第 1 章到第 26 章保持一致):

```markdown
# 第 N 章 章节标题

(开头 1-2 段:本章动机 + 与前一章的衔接,200-400 字)

## 一级标题(3-5 个)

(正文 8000-12000 字,每章为独立单元,案例与观点均一线项目实证)

## 本章小结

- 关键观点 1
- 关键观点 2
- 关键观点 3

(可选)## 实战清单

- [ ] 行动项 1
- [ ] 行动项 2
```

### 2.1 字数控制

| 部分 | 字数 |
|---|---|
| 开篇衔接 | 200-400 字 |
| 正文 | 8000-12000 字 |
| 本章小结 | 200-400 字 |
| **合计** | **9000-13000 字** |

> FDE 章节字数比 ai-coding 略多(8000-12000 vs 5000-8000),因为案例密度高、读者需要更多上下文。

### 2.2 章节引用

- 引用一线项目:脱敏后引用,标注行业/规模/角色
- 引用数据/价格:正文写"截至 XXXX 年 X 月"
- 引用模型/技术:注明模型名称与版本(GPT-4 / Claude Sonnet 4.5 / Qwen3 等)

## 三、文字风格

### 3.1 人称与语气

- **默认第二人称**(你、读者)
- 严肃专业,**允许直接的判断**("X 不行"、"Y 才是关键")
- 给出反直觉观点时,明确标注"反直觉点:..."
- 不写"可能"、"也许"等模糊语;以一线经验为依据

### 3.2 术语处理

- **专业术语首次出现**:中文 + 英文 + 简释
  - 例:"三轴验证(数据 / 技术 / 组织三维度的 Go/No-Go 评估框架)"
- 后续使用统一术语

### 3.3 段落与节奏

- 单段不超过 8 行
- 案例段落用引用块 `>` 包裹
- 关键结论用粗体 `**...**`

### 3.4 标点与排版

- 中文标点全角,英文标点半角
- 引号统一用 `"..."`
- 代码、命令、文件名:用反引号包裹

## 四、四篇结构

26 章分 4 篇,每篇有明确命题:

| 篇 | 章号 | 命题 |
|---|---|---|
| 第一篇 · 认知 | 1-4 | FDE 是什么、不是什么;为什么 PoC 阶段死;够好就行;能不用 AI 就不用 |
| 第二篇 · 侦察 | 5-8 | 需求挖掘、问题翻译、三轴验证、期望管理 |
| 第三篇 · 推进 | 9-18 | 模型与提示词、RAG、Agent、评估、成本、上线、运维、故障、复盘 |
| 第四篇 · 反挫 | 19-26 | FDE 能力建设 + 7 个垂直行业反挫案例(医疗/金融/制造/政务/教育/法律) |

**每个篇章开头需要明确**:
- 本篇要回答的核心问题
- 本篇与其他篇的衔接逻辑

## 五、出版级质量基线

### 5.1 三审三校

| 环节 | 责任 | 检查项 |
|---|---|---|
| 一审(作者自查) | 作者 | 案例真实性、引用准确性、章节衔接 |
| 二审(同行评审) | FDE 同行 | 一线可复现性、行业覆盖、立场平衡 |
| 三审(主编终审) | 主编 | 出版级质量、读者预期、反直觉点的论证 |
| 一校/二校/三校 | 编辑 | 错别字、标点、引用规范 |

### 5.2 风险内容

- **避免**对模型/厂商的褒贬(中立)
- **避免**对客户的指代(脱敏)
- **争议话题**(如:AI 取代人)给双方观点,不下定论
- **数据来源**:可量化结论必须有源

## 六、给 AI 协作者的执行摘要

如果你是一个 AI agent,正在协助本项目:

1. **先读 [README.md](./README.md)** 了解项目当前状态
2. **再读 [chapters/01-FDE 不是部署工程师.md](./chapters/01-FDE%20不是部署工程师.md)** 了解章节风格
3. **修改任何文件前** 确认文件路径与本规范一致
4. **创建新文件时** 严格遵循 1.2 / 1.3 的命名规范
5. **写新章节时** 严格遵守四篇结构(第几篇、第几章)
6. **不要直接覆盖已定稿内容**:如需修改,先备份到 `appendix/case-studies/_archive/`,再改原文件
7. **遇到歧义**:回到本规范第 1-5 章;若仍无答案,向用户提问而不是猜测
