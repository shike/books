# 第 6 章 Skill 是什么

## 本章要点

- Skill 是 WorkBuddy 的灵魂:把"派活"沉淀为可复用的工具,让"对话"升级为"流程"
- 提示词 vs Skill:一次性的对话 vs 永久的工具。前者解决"这一次",后者解决"每一次"
- Skill 的三大构成:**触发条件 + 执行逻辑 + 输出规范**,缺一不可
- Skills 市场已收录过万技能(官方内置 20+ 官方技能,SkillHub 社区 2 万+,兼容 OpenClaw 生态 1.3 万-7 万+),管理者可以直接"装上就用",不必自己造轮子
- 三个判断标准决定提示词值不值得变成 Skill:被反复使用、有稳定输入输出、能跨人复用
- Skill 真正的威力,不在"省时间",而在"组织级一致性"——团队所有人都按同一种标准做事

## 开篇

上一章讲了"派活型提示词"——三件套、5 个模板、迭代日志。用上两周,你会撞上新问题:**提示词越来越多了**。

周报、汇报、翻译、纪要、PPT……每个都打磨过几轮,每次用都得手动复制粘贴。某天同事问"周报提示词借我用",你发过去,他改了半天还是不对——因为提示词里嵌了你的"个人风格",他套不进去。

半年后回看自己的"提示词库",已经分不清哪个是最新版、哪个是哪个场景的。**你的"提示词"变成了"私房菜谱",只对你有用,别人用不起来**。

这正是 Skill 要解决的问题。

一句话定义:**Skill = 触发条件 + 执行逻辑 + 输出规范**。它把"一个被反复使用的提示词"封装成"一个可以反复调用的工具"。

一个类比:在没有导航的年代,你出门前要打电话问路,朋友说"走三环,半小时";后来有了导航,你输入起点终点,它自动给出路线。**这一次和上一次的逻辑、输出格式几乎一致**。

从"问路"到"用导航",本质变化是:**对话变成了工具**。WorkBuddy 的 Skill,就是把"你和 AI 的对话"变成"AI 的工具"。

本章回答五个问题:为什么需要 Skill、Skill 是什么、怎么用现成的 Skill、怎么把提示词变成 Skill、Skill 与团队的关系——为什么 Skill 是组织级一致性的载体,如何把"老师傅经验"沉淀下来。Skill 的开发细节(写得更精细、用变量与分支、与外部系统集成),留到第一卷附录 C(Skill 编写手册)。

## 一、为什么需要 Skill

### 1.1 提示词的三个局限

提示词很好,但有天然的三个局限。

**第一,每次都要写**。即使有 90 分的提示词模板,每次用都要打开、复制、改写"约束"和"输出"两段,花 3-5 分钟;改完还要核对"漏没漏约束"。一个月用十次,30-50 分钟的重复劳动。

**第二,容易漏**。模板写了 8 条约束,每次都可能漏一两条。比如你要求"语气克制、不夸大",今天急,只看了"格式"那段就发了——AI 给你写出一份"激情澎湃"的汇报。一次漏、两次漏,最后你对提示词库失去信心。

**第三,不可复用**。提示词默认只有你能用。同事想用,要么复制、要么自己再写。即使复制过去,你的"个人风格"也写进了约束里,他用起来别扭。复制给十个人,就有十种"变体"。

根因是**"提示词是文本,而 Skill 是产品"**。文本每次用都要"读一遍理解一遍",产品每次用只要"调一下"就行;文本没法强制约束,产品可以;文本没法跨人一致,产品可以。

### 1.2 三个数字,看提示词的"重复成本"

数据来自 7 位中层管理者访谈(2026 年 5-7 月,脱敏处理)。

**周均提示词复制次数**——7 位合计每周把"自己写过的提示词"复制到新对话里 **14 次**(平均每位每周约 2 次)。其中 3 位长期只用同一个"周报整理"提示词,4 位同时维护 3-5 个不同场景的提示词。

**平均改写耗时**——每次复用提示词,平均 **3.7 分钟**做"针对当下场景的微调"。这部分时间,严格说是"被浪费的时间"——调整的逻辑本可以在 Skill 阶段就固化。

**跨人复用失败率**——把提示词给同事、同事能"一次就按预期输出"的成功率,只有 **40%**(2/5 一次成功,3/5 要改 2-3 次)。失败主因:个人风格嵌入太深、上下文不通用、约束写得太模糊。

三个数字加在一起:**提示词的"重复成本"真实存在,而且不小**。

粗略测算:每周 14 次复用 × 3.7 分钟 × 50 周 ≈ **43 小时/年**。按 100 元/小时算,一年 4300 元——只要把高频提示词变成 Skill,这笔钱就省下来。

### 1.3 Skill 的承诺:一次写好,反复使用,人人可调

Skill 解决"重复成本"问题,承诺有三条:

**第一,一次写好**。在 Skill 里把"触发条件、执行逻辑、输出规范"全部固化。下次用,只需告诉 WorkBuddy"用 XX Skill",它就按 Skill 定义执行,不用每次再写。

**第二,反复使用**。Skill 加载后长期可用,逻辑一直在那里,不用重新记。

**第三,人人可调**。团队场景下,一个好的 Skill 分发给所有成员,大家用同样的触发条件、输出规范——周报格式一致,客户回复风格一致,方案汇报结构一致。

三条合起来就一句话:**把"私房菜谱"升级为"中央厨房的标准化菜谱"**。私房菜谱只有厨师本人做得最好;中央厨房的菜谱,任何厨师按手册做,味道都差不多。Skill 就是那个"标准化手册"。

### 1.4 一个具体的例子:周报整理的进化

用一个具体例子,看"提示词 → Skill"的进化路径。

**阶段一:从零开始**。你第一次让 WorkBuddy 整理周报,AI 给出 5 段,但太正式、太长、缺数据。

**阶段二:迭代提示词**。改几次,得到 90 分版本:

```text
基于本目录所有素材,整理一份周报。要求:
- 分为"已完成 / 进行中 / 下周计划"三部分
- 每条 1-2 句话,共 8-12 条
- 语气克制,不夸大成绩,不回避问题
- 保留原文中的具体数字(如收入、用户数、增长率)
- 不要主观判断(如"显著增长"、"大幅提升")
```

存到团队共享知识库(飞书 / Notion / 语雀均可,根据你团队的现有工具选),每周复用——你有了"私房菜谱"。

**阶段三:分享给同事**。同事小王要借,他部门用"重点 / 进展 / 风险"三段,语气也偏"硬"。一改,又给另一位同事——一份提示词出现三种"变体"。

**阶段四:升级为 Skill**。把"语气"和"段标题"留作**参数**,用户可调。小王说"用周报 Skill,段标题改 重点/进展/风险",WorkBuddy 就换标题;你说"语气正式一点",WorkBuddy 就调语气。

**这就是 Skill 的进化**——从"一份提示词,反复粘贴"到"一个工具,人人可调"。

### 1.5 Skill 与"AI Agent"的边界澄清

常见误解需要澄清:Skill 等于 AI Agent 吗?

简短回答:**不是,但 Skill 是 Agent 的"技能包"**。

- **AI Agent**:一个能感知环境、做决策、执行动作的完整系统。WorkBuddy 本身就是一个 AI Agent
- **Skill**:Agent 的一项"具体能力","整理周报"是一个 Skill,"翻译邮件"是另一个

一个 Agent 可能有几十个 Skill,每个负责一个具体场景。WorkBuddy 内置了通用 Skill(写邮件、读文件、改文档),你也可以从技能市场加载更多,或自己创建。

这个区分的意义:**你不用关心"我是不是在做 Agent"这种术语问题,只关心"我这个工作场景,有没有现成的 Skill"**。类比:你不用关心 Word 是怎么实现的,只关心"它能不能帮我写报告"。Skill 同理。

## 二、Skill 的三大构成

### 2.1 一个定义

**Skill = 触发条件 + 执行逻辑 + 输出规范**。

这是 WorkBuddy 官方对 Skill 的定义(来源:WorkBuddy 帮助中心,2026-06 查阅)。三部分缺一不可:

- 缺**触发条件**,Skill 不知道自己什么时候该被加载
- 缺**执行逻辑**,Skill 不知道自己该做什么
- 缺**输出规范**,Skill 不知道自己该输出什么格式

让我用"周报 Skill"作为例子,逐一拆解。

### 2.2 第一构成:触发条件

**触发条件** = Skill 在什么情况下被自动(或手动)加载。

WorkBuddy 的触发条件分两类:

**自动触发**:基于用户输入的关键词、场景、上下文自动匹配。比如用户说"整理周报"或"写周报",WorkBuddy 自动加载"周报 Skill"。

**手动触发**:用户在 Skill 面板里点选,或者用 `/skill 名称` 这样的命令调用。比如 `/skill weekly-report` 就是手动调用"周报 Skill"。

触发条件的核心是**"明确性"**。如果触发条件写得模糊,会出现两个问题:

- **误触发**:用户本来想说"翻译邮件",但因为某句话里有"周报"两个字,Skill 错误地加载了
- **漏触发**:用户其实想用周报 Skill,但他说"总结一下本周工作"——"总结"和"整理"用词不同,Skill 没识别

一个好的触发条件,应该**列出 3-5 个等价表达**:

```text
触发关键词:
- "整理周报"
- "写周报"
- "本周工作汇总"
- "weekly report"
- "周报整理"
```

WorkBuddy 的语义匹配能力,允许这 5 个表达指向同一个 Skill。**写好触发条件,是 Skill 普及的第一步**。

**一个反例**:把触发条件写成"工作汇报"——太宽泛。用户说"汇报这个项目进展",Skill 加载;说"汇报一下昨天会议",Skill 也加载——但用户其实想要"会议纪要"Skill,不是"周报"Skill。

**触发条件的颗粒度,直接决定 Skill 的"被使用率"**——太窄,用户找不到;太宽,用户用错。

### 2.3 第二构成:执行逻辑

**执行逻辑** = Skill 做什么、怎么做、按什么步骤。

这是 Skill 的"主体",占整个 Skill 定义的 60-70% 篇幅。

执行逻辑的核心是**"步骤化"**。一个复杂的 Skill,要拆成 5-10 个步骤,每个步骤有明确的输入和输出。

以"周报 Skill"为例,执行逻辑可以拆成这样:

```text
执行步骤:
1. 读取工作目录下 `inbox/` 文件夹
2. 提取本周(最近 7 天内)创建或修改的文件
3. 读取每个文件,提取"做了什么、结果如何"两个维度的信息
4. 按"已完成 / 进行中 / 下周计划"三组分类
5. 合并同类项,去除重复
6. 排序:已完成按重要性降序,进行中按优先级降序
7. 控制总条数 8-12 条
8. 输出到 `drafts/weekly_YYYYMMDD.md`
```

**为什么步骤要这么细**?因为 AI 模型的执行,本质是"按步骤推理"。你给的步骤越明确,它越能稳定执行;步骤越模糊,它越容易"自由发挥"——自由发挥有时是惊喜,有时是事故。

WorkBuddy 的"执行逻辑"部分还支持几类高级能力:

- **变量引用**:用 `{{input}}` 这样的语法引用用户输入的参数
- **条件分支**:用 if-else 让 Skill 在不同条件下做不同事
- **工具调用**:让 Skill 触发 WorkBuddy 的内部工具(读文件、发邮件、设提醒)

详细语法在第一卷附录 C(Skill 编写手册)展开,本章不深入。

### 2.4 第三构成:输出规范

**输出规范** = Skill 的结果长什么样。

输出规范是"质量门"——它告诉 WorkBuddy,"做完之后,我期望看到什么"。

输出规范通常包括:

- **格式**:Markdown / Word / Excel / PPT?段落 / 列表 / 表格?
- **长度**:总字数?段落数?每段句数?
- **风格**:语气(克制 / 正式 / 轻松)?人称(我 / 我们 / 你)?
- **强制项**:必须包含的元素(数据 / 引用 / 链接)
- **禁止项**:不能出现的内容(主观判断 / 夸大 / 商业宣传词)

以"周报 Skill"的输出规范为例:

```text
输出要求:
- 格式:Markdown
- 结构:三段(已完成 / 进行中 / 下周计划)
- 长度:每段 3-5 条,每条 1-2 句话,总 200-300 字
- 风格:克制,不夸大,不回避问题
- 强制项:每条必须包含具体数字或可验证的事实
- 禁止项:
  - 不使用"显著增长""大幅提升""卓越表现"等夸大词
  - 不使用"我们认为""我们觉得"等主观判断
  - 不引入本周素材之外的内容
```

**这一段是"质量门"**。用户审阅时,只要看输出是否符合这五条,就能判断 Skill 跑得好不好。

如果输出不符合,不是 Skill 错了,是触发条件没匹配对、或者执行逻辑的步骤拆得不对、或者输出规范写得不清楚。**三构成之间,任何一处薄弱,Skill 整体就不稳**。

### 2.5 三构成的关系:一个等边三角形

三构成画出来是等边三角形:

- **触发条件**(顶点):决定"什么时候"被调用
- **执行逻辑**(左下):决定"做什么"
- **输出规范**(右下):决定"输出什么样"

三者是平等的,缺一不可。

![Skill 三大构成:触发条件、执行逻辑、输出规范,缺一不可](figures/1.6.2-skill-three-parts.png)

*图 1.6.2 Skill 三大构成:触发条件、执行逻辑、输出规范,缺一不可*

**一个类比**:Skill 是一份菜谱。触发条件是"什么时候点这道菜",执行逻辑是"做菜的步骤",输出规范是"出锅的菜长什么样"——菜谱写得不好,菜就做不好;Skill 三构成写得不好,Skill 跑得就不对。

### 2.6 表格:三构成的速查

| 构成 | 回答的问题 | 写不好会怎样 | 写得好长这样 |
|---|---|---|---|
| 触发条件 | 什么时候调用? | 误触发 / 漏触发 | 3-5 个等价表达 + 手动调用命令 |
| 执行逻辑 | 做什么、怎么做? | 执行不稳定、AI 自由发挥 | 5-10 个步骤,每步输入输出明确 |
| 输出规范 | 输出什么样? | 风格漂移、质量不稳 | 格式 + 长度 + 风格 + 强制项 + 禁止项 |

*表 1.6.1 Skill 三大构成速查*

这三列,任何一列写得敷衍,Skill 都不合格。**很多用户写 Skill 时只写"执行逻辑",忽略触发条件和输出规范——这是 Skill 跑得不好的高频原因**。

### 2.7 一个完整的 Skill 拆解示例

让我把"周报 Skill"完整地写出来,作为本章的范例。这个 Skill 你可以照着用,也可以照着改。

```text
# 周报 Skill

## 触发条件
- 自动触发:用户输入包含"周报""本周工作""weekly"等关键词
- 手动触发:输入 /skill weekly-report

## 执行逻辑
1. 读取工作目录下 `inbox/` 文件夹的所有文件
2. 过滤出最近 7 天内创建或修改的文件
3. 对每个文件,提取"动作 + 结果"两要素(如"完成 XX 报告,提交给 CFO")
4. 按以下规则分类:
   - 已完成:动作有时间戳,结果已确认
   - 进行中:动作有开始时间,无结束时间
   - 下周计划:文档中提到"下周""接下来""计划"等
5. 去重、合并同类项
6. 每段按重要性降序排列
7. 写入 `drafts/weekly_YYYYMMDD.md`

## 输出规范
- 格式:Markdown
- 标题:# 周报(YYYY-MM-DD 至 YYYY-MM-DD)
- 三段:## 已完成、## 进行中、## 下周计划
- 长度:每段 3-5 条,每条 1-2 句话,总 200-300 字
- 风格:克制、不夸大、不回避问题
- 强制项:每条必须含可验证事实(数字、文档名、事件)
- 禁止项:
  - 不使用主观判断("显著""大幅""卓越")
  - 不引用本周素材之外的内容
  - 不替用户做承诺("下周一定完成"改为"下周计划")
```

这是一个**最小可用的 Skill 范例**——它不一定完美,但包含了三大构成的所有要素。你把它加载到 WorkBuddy 后,每周只需说"写周报",它就会按这个流程跑,产出一份格式稳定的周报草稿。

## 三、技能市场:现成的 Skill

### 3.1 技能市场是什么

**技能市场**(Skill Marketplace)是 WorkBuddy 内置的 Skill 商店。Skills 市场已收录过万技能(官方内置 20+ 官方技能,SkillHub 社区 2 万+,兼容 OpenClaw 生态 1.3 万-7 万+),覆盖文档处理、数据分析、内容生成、翻译、项目管理等多个领域。

技能市场的入口在 WorkBuddy 左侧栏的"技能市场"图标,点击后进入浏览页面。

### 3.2 技能市场的分类

技能市场的 Skill 按场景分为 8 个大类:

| 分类 | 数量(约) | 典型场景 |
|---|---|---|
| 文档处理 | 80 | 周报、报告、邮件、纪要、合同 |

### 3.3 给管理者推荐的 10 个 Skill

我从技能市场里,挑出 10 个最值得管理者先加载的 Skill。这 10 个覆盖了管理者每周 80% 的高频场景。

1. **周报整理 Skill**——每周一次,把分散素材汇总成结构化周报

4. **会议纪要生成 Skill**——基于会议录音/笔记生成结构化纪要

6. **客户邮件回复 Skill**——基于客户来信和历史沟通,生成回复草稿
7. **Excel 数据汇总 Skill**——把多张工作表的数据汇总到一张总表
8. **合同条款核对 Skill**——对照标准条款,核对合同偏差
9. **周计划生成 Skill**——基于本周周报,自动生成下周计划初稿
10. **新闻简报 Skill**——每天 9:00 自动汇总行业新闻,生成 1 页简报

### 3.4 试用 → 加载 → 卸载:三步流程

技能市场的 Skill 使用流程,分三步:

**第一步:试用**。点开 Skill 详情页,看"触发条件 / 执行逻辑 / 输出规范"是否匹配你的需求。匹配的话,点"试用"按钮,WorkBuddy 会让你提供一个"测试素材",跑一遍给你看输出。试用不消耗 Credits。

**第二步:加载**。试用满意后,点"加载到我的 WorkBuddy"。加载后,这个 Skill 就出现在你的 Skill 列表里,以后可以反复调用。加载本身不消耗 Credits,但每次调用消耗。

**第三步:卸载**。如果用了一段时间觉得不合适(用不到、效果不好、消耗太多),可以在"我的 Skill"里点"卸载"。卸载后这个 Skill 消失,但你的"使用历史"和"评分"会保留(供他人参考)。

**一个建议**:**不要一次性加载太多 Skill**。我见过一位用户加载了 30 多个,Skill 列表长得像应用商店,他都忘了哪些加载过哪些没加载,每次调 Skill 还要先翻列表找名字,反而慢。

**合理数量**:对你个人,5-10 个 Skill 就够覆盖 80% 场景。多于 15 个,就要卸载一些用不到的。

### 3.5 选 Skill 的三个判断标准

技能市场的 Skill 良莠不齐。判断值不值得加载,看三个标准:

**第一,看评分和使用量**。评分低于 4.0 或加载量低于 1000 的,要谨慎——可能是早期版本或开发者不再维护。

**第二,看更新日期**。超过 6 个月没更新的 Skill,可能与最新 WorkBuddy 版本不兼容,加载后报错。优先看 3 个月内更新的。

**第三,看输出样例**。每个详情页都有"输出样例"——一段示例输入和对应输出。**看输出样例,比看定义更直观**;样例符合期望,大概率能用。

常见误区是**"按评分盲选"**。评分高不等于适合——某个翻译 Skill 评分 4.8,但你要"邮件翻译",它提供的是"论文翻译",用不上。

**选 Skill 是"按需"不是"按评分"**——先想清楚场景,再匹配 Skill。

### 3.6 不要追求"全"

最后一个提醒:**不要追求"装齐所有 Skill"**。

我访谈过 7 位管理者,其中 3 位尝试过"把技能市场的好评 Skill 都装一遍"。结果 3 个月后,3 位都卸载了 60% 以上——很多 Skill 装了不用,占着位置反而干扰选择。

Skill 的价值在于"用",不在"装"。一个你每周用 3 次的 Skill,比 10 个你装了不用的,价值大得多。

**反直觉的事实**:**Skill 越少,效率越高**。你的工作场景有限,10 个 Skill 完全覆盖;装了 50 个,每次派活都要先"想一下该用哪个",反而比直接写提示词还慢。**选择本身是有成本的**。

## 四、提示词 → Skill 的转化

### 4.1 什么样的提示词值得变成 Skill

不是所有提示词都值得变成 Skill。**值得变的提示词,只占你写过的 20-30%**。

判断标准有三条:

**第一,被反复使用**。你过去 30 天内,用了至少 3 次同样的提示词(或者高度相似的)。如果只用过 1-2 次,变成 Skill 是"过度设计"。

**第二,有稳定输入输出**。每次用的时候,输入和输出的格式都差不多。比如"周报整理"——输入总是"工作素材",输出总是"三段式周报"。如果每次输入输出都不同,不适合变 Skill(更适合用普通提示词)。

**第三,能跨人复用**。你写了这个 Skill 后,你的同事也能用(或者将来某天能用)。如果是非常个人化的提示词(嵌入太多"我"和"我们部门"),暂不适合变 Skill——先简化、抽象,再变。

**三条同时满足**,才是"值得变 Skill 的提示词"。

### 4.2 反例:什么样的提示词不值得变 Skill

为了对照,我列几类"不值得变 Skill"的提示词:

- **一次性研究型**:"基于这 5 篇论文,总结 AI Agent 的发展史"——一次性任务,变 Skill 没意义
- **探索型对话**:"我想了解一下 RPA 技术,你能给我讲讲吗"——开放式探索,没稳定结构
- **个人备忘**:"我今天心情不好,帮我写一段日记"——太个人化,无法跨人
- **临时性需求**:"把这段话改得更有诗意"——只这一次

这些场景,继续用普通提示词就行,不必 Skill 化。

### 4.3 转化的标准流程

把一个提示词变成 Skill,有标准的 5 步流程。

![提示词到 Skill 的转化标准流程,5 步走](figures/1.6.4-prompt-to-skill-flow.png)

*图 1.6.4 提示词到 Skill 的转化标准流程,5 步走*

**第 1 步:从"提示词库"识别候选**。翻一下你过去 30 天的提示词使用记录(WorkBuddy 有这个日志),找出"用了 3 次以上、输入输出稳定"的提示词。这是候选列表。

**第 2 步:抽象出"通用部分"和"参数部分"**。把候选提示词拆成两部分:
- **通用部分**:不因场景变化的部分(如"语气克制""保留数字"等)
- **参数部分**:每次需要调的部分(如"段标题""目标读者"等)

通用部分写进 Skill 定义;参数部分保留为"用户输入时的可选项"。

**第 3 步:写出三构成**。按本章第二节的模板,写出"触发条件 / 执行逻辑 / 输出规范"三段。**第一次写,先求"对",不求"精"**。

**第 4 步:用真实场景跑 3 次**。拿 3 个真实的输入,各跑一遍 Skill。检查输出是否符合预期。如果某次输出明显不对,回头调整 Skill 定义(可能是触发条件太宽、执行逻辑漏步、或者输出规范没写清楚)。

**第 5 步:固化 + 命名 + 归档**。跑通后,给 Skill 起一个清晰的名字(动词 + 名词,比如"周报整理 Skill"),归档到"我的 Skill"列表。

**一个常见错误**:**第 3 步就发布,跳过第 4 步**。直接把自己写的 Skill 拿去用,不先用真实场景跑几次。结果,Skill 看起来定义完美,但实际用起来各种漏——因为写的人和用的人视角不同,自己写的"看似清晰",在真实场景下未必清晰。

**第 4 步是质量门**。跳过它,Skill 一定不稳。

### 4.4 第一个自建 Skill 的完整示例

让我用一个完整例子,走一遍 5 步流程。

**背景**:某位市场总监小张,过去一个月用了 5 次"市场周报整理"提示词。每次输入都是"本周市场动态 + 内部讨论",输出都是"市场观察 / 关键数据 / 下周关注"三段。她决定把它变成 Skill。

**第 1 步:识别候选**。这个提示词一个月用了 5 次,满足"3 次以上"标准,候选。

**第 2 步:抽象通用 vs 参数**。她拆解后,发现:
- 通用部分:三段结构、克制语气、保留数字、避免主观判断
- 参数部分:可以是"市场观察 / 关键数据 / 下周关注"(她的部门用),也可以是"行业动态 / 重点数据 / 团队同步"(另一个部门用)

**第 3 步:写 Skill 定义**:

```text
# 市场周报整理 Skill

## 触发条件
- 自动触发:输入包含"市场周报""本周市场""市场动态"等关键词
- 手动触发:输入 /skill market-weekly

## 执行逻辑
1. 读取工作目录 `inbox/market/` 文件夹
2. 提取最近 7 天的素材(新闻、报告、内部讨论)
3. 抽取"事件 + 数据"两要素
4. 按用户指定的段标题(默认"市场观察 / 关键数据 / 下周关注")分三组
5. 每组 3-5 条,按重要性降序
6. 输出到 `drafts/market_weekly_YYYYMMDD.md`

## 输出规范
- 格式:Markdown
- 长度:每段 3-5 条,每条 1-2 句,总 250-350 字
- 风格:克制、不夸大、不回避问题
- 强制项:每条必须含可验证事实(数据 / 引用 / 链接)
- 禁止项:
  - 不使用主观判断
  - 不引用本周素材之外的内容
- 参数:段标题可由用户指定(如"重点数据 / 行业动态 / 团队同步")
```

**第 4 步:跑 3 次真实场景**。小张用过去 3 周的真实素材各跑一次,检查输出。结果:
- 第一次:某条用了"显著增长",违反"不夸大"——回去在禁止项里再强调
- 第二次:某条引用 8 月初素材,她发现 8 月初距今 10 天,不在 7 天范围,Skill 处理正确
- 第三次:输出完全符合预期,稳定

**第 5 步:命名 + 归档**。她把这个 Skill 命名为"市场周报整理 Skill",加载到"我的 Skill"。

**之后的使用**:小张每周只需说"用市场周报 Skill",WorkBuddy 自动按上面的流程跑。一年的工作量,从"每周手动改写提示词 5 分钟"变成"每周一句话调用"——一年省下 **4-5 小时**。

**更重要的是**:她把这个 Skill 分享给了市场部的两个同事,他们按自己部门的段标题配置,各跑各的,互不干扰。**一个 Skill,服务三个人,跨部门复用**。

### 4.5 自建 Skill 常见错误

自建 Skill 时,有几个高频错误:

**错误一:触发条件太宽**。"任何工作相关"都触发——误触发率 50% 以上。**触发条件宁窄勿宽**,用错用户能调,触发错了就烦了。

**错误二:执行逻辑写得太抽象**。"读素材 → 整理 → 输出",每步太空。**每一步都要具体到"读哪个文件、做什么动作、什么标准"**。

**错误三:输出规范漏禁止项**。只写"应该是什么",不写"不应该是什么"。AI 模型倾向"自由发挥",没禁止项就放飞。

**错误四:不做真实场景测试**。写完直接用,出问题再说。**至少用 3 个真实输入跑一遍**,有问题就改 Skill 定义,不要"将就着用"。

**错误五:Skill 越加越多**。新人最容易犯——写完一个再加一个,3 个月有 20 多个 Skill,大部分闲置。**Skill 是"工具"不是"收藏品"**,用不上就卸载。

### 4.6 表格:提示词 vs Skill

| 维度 | 提示词 | Skill |
|---|---|---|
| 形态 | 文本段落 | 工具(可被调用) |
| 触发 | 每次手动输入 | 自动触发或 `/skill 名称` |
| 复用 | 复制粘贴(每次改写 3-5 分钟) | 一键调用(每次 < 10 秒) |
| 跨人 | 难(个人风格嵌入深) | 易(规范一致) |
| 维护 | 分散在文档里 | 集中管理 |
| 适用场景 | 一次性、探索性 | 反复使用、模式化 |
| 学习成本 | 低(写就行) | 中(要写三大构成) |
| 长期价值 | 低(易过期、易丢) | 高(沉淀为团队资产) |

*表 1.6.3 提示词 vs Skill 对照*

这张表是本章的核心。**提示词解决"这一次",Skill 解决"每一次"**。你大部分短期需求用提示词;**长期反复用的,沉淀为 Skill**。

## 五、Skill 与团队最佳实践

### 5.1 Skill 是团队知识的载体

讲完个人视角,最后讲团队视角。

**Skill 的真正威力,不在"个人省时间",而在"团队一致性"**。

一个组织里,不同人写出来的周报格式不同、邮件回复风格不同、方案汇报结构不同——这是"组织熵"。**组织熵越大,跨人沟通成本越高**。新员工看老员工的周报,看不懂格式;老员工看新员工的方案,觉得不规范。

Skill 是"组织熵"的天敌。当一个组织用同样的 Skill 做同一类工作,产出就会趋近一致。新员工调起"周报 Skill",产出的格式和老员工一样;调起"客户邮件 Skill",回复风格和老员工一样。**新人不需要"师傅带",Skill 本身就承载了"老员工的经验"**。

这就是为什么说"**Skill 是团队知识的载体**"——它把"老员工脑子里怎么做的"沉淀为"组织里每个人都能用的工具"。

### 5.2 把"老师傅经验"封装为 Skill

一个具体的例子:某公司有个 15 年经验的财务总监王姐,她审过的报销单从来没出过问题。她做报销审阅,有一套自己的"潜规则":

- 餐饮发票超过人均 200 元,必有"业务说明"附注,否则打回
- 打车发票,只认"工作日 9-21 点"和"周末 7-22 点",其他时间打车要说明
- 礼品采购,单笔超过 1000 元的,必须附"接收人 + 接收时间 + 接收凭证"

这些规则在王姐脑子里,但新员工不知道。结果:新员工审的报销单,总有些细节漏掉,被打回重做。

如果王姐把自己这套"潜规则"封装成一个 Skill:

```text
# 报销审阅 Skill

## 触发条件
- 自动触发:用户输入包含"审报销""报销单""reimbursement"等关键词
- 手动触发:输入 /skill expense-audit

## 执行逻辑
1. 读取工作目录 `inbox/expense/` 的报销单
2. 提取每张发票的金额、类型、时间
3. 按以下规则审阅:
   - 餐饮:人均 > 200 必须有"业务说明",否则标记"待补"
   - 打车:非工作日 9-21 / 周末 7-22 必须有说明,否则标记"待补"
   - 礼品:单笔 > 1000 必须有"接收人 + 时间 + 凭证",否则标记"待补"
4. 输出"通过"和"待补"两类清单

## 输出规范
- 格式:Markdown 表格
- 列:报销人 / 金额 / 类型 / 审阅结果 / 需补内容
- 风格:客观、不带评价
- 强制项:每条标记必须给出"违反的具体规则编号"
```

王姐把这套经验封进 Skill 后,新员工审报销,调起这个 Skill,**结果和王姐审的几乎一样**。王姐的 15 年经验,沉淀到了一个工具里,新员工也能复用。

**这就是 Skill 的真正威力**——它把"个人的不可言传的经验"变成"组织可复用的工具"。

![Skill 跨人复用模型:老师傅经验 → Skill 化 → 全员复用](figures/1.6.5-skill-team-reuse.png)

### 5.3 团队 Skill 库的搭建原则

一个团队怎么开始建 Skill 库?三个原则:

**原则一:从高频场景开始,不要一上来就铺开**。先建 3-5 个覆盖团队 80% 工作量的 Skill,跑通流程,再扩展。

**原则二:每个 Skill 都有"维护人"**。没有维护人的 Skill,3 个月后就过时。**维护人的责任**:监控使用、收集反馈、定期更新、回答同事问题。

**原则三:用业务结果度量 Skill 的价值**。不要用"Skill 数量"度量——堆 100 个没用的 Skill 没价值。要用"用 Skill 后节省了多少时间 / 减少了多少错误"度量。

详细的团队 Skill 库搭建方法,在**第二卷第 4 章《技能市场:选现成的 Skill》和第 5 章《专家中心:沉淀团队最佳实践》**展开。

### 5.4 团队 Skill 库的常见误区

搭建团队 Skill 库,有三个常见误区:

**误区一:建库不维护**。某公司让每个部门都"提报"5 个 Skill,3 个月收了 80 个 Skill,放在共享库,没人维护。结果:6 个月后,80 个 Skill 里有 30 个因为 WorkBuddy 升级不兼容,20 个因为业务变化已经过时。**没维护的 Skill 库,就是"Skill 坟场"**。

**误区二:Skill 不让改**。某公司的 Skill 库是"只读"的——任何人都不能改。理由是"统一管理"。结果:业务变化后,Skill 跑出来的结果不对,大家只好不用,改用普通提示词。**Skill 库要"可演化"**,允许维护人在审核后更新。

**误区三:用 KPI 倒推 Skill**。某公司把"每人每月创建 3 个 Skill"作为考核指标。结果:员工为了凑数,创建了大量"为创建而创建"的 Skill,质量低下,几个月后全被卸载。**Skill 不是越多越好,是越用越好**。

这些误区的共性:**把 Skill 当"项目交付",而不是"持续运营"**。Skill 库是活的,需要持续维护、持续迭代、持续淘汰。

### 5.5 一个小型团队 Skill 库的案例

[案例来源:某 SaaS 公司运营总监访谈,2026-07,脱敏处理]

某 30 人 SaaS 公司,运营团队 8 人,过去半年建了一个小型 Skill 库,共 12 个 Skill,覆盖 80% 运营日常工作。维护人是运营总监 + 1 个运营骨干。

12 个 Skill 包括:周报/月报整理(2)、客户邮件回复(3,按客户类型分)、营销文案改写(2,公众号/知乎)、活动复盘报告、用户调研纪要、渠道数据分析、内部通知、报销审阅。

**效果**:运营团队每周节省 12-15 小时;新人入职 1 周内就能产出符合团队风格的周报;运营总监不再需要每天给新人改格式——Skill 替他做。

**关键经验**:**"少而精"**。12 个 Skill 不多,但每一个都用得起来,每一个都有维护人。**不是"Skill 多才好",是"用得起来才好"**。

## 小结

这一章讨论了五个问题。

**第一,为什么需要 Skill**。提示词有三个局限:每次都要写、容易漏、不可复用。Skill 用"一次写好,反复使用,人人可调"解决这三个问题。从"问路"到"用导航",Skill 把"对话"升级为"工具"。

**第二,Skill 的三大构成**。触发条件 + 执行逻辑 + 输出规范,三者缺一不可。触发条件决定"什么时候用",执行逻辑决定"怎么做",输出规范决定"输出什么样"。三构成写得敷衍,Skill 跑得就不稳。

**第三,技能市场提供了现成的 Skill**。Skills 市场已收录过万技能(官方内置 20+ 官方技能,SkillHub 社区 2 万+,兼容 OpenClaw 生态 1.3 万-7 万+),管理者可以直接选用。对管理者,推荐 10 个最值得先加载的——周报整理、汇报材料、邮件翻译、会议纪要、PPT 大纲、客户邮件、Excel 汇总、合同核对、周计划、新闻简报。**不要追求"全",要追求"用"**。

**第四,提示词到 Skill 的转化有标准 5 步流程**。识别候选 → 抽象通用 vs 参数 → 写三构成 → 跑 3 次真实场景 → 命名归档。第 4 步"真实场景测试"是质量门,跳过它,Skill 一定不稳。

**第五,Skill 是团队知识的载体**。它把"老师傅经验"沉淀为可复用工具,让"新人也能产出老员工的水平"。团队 Skill 库的搭建要从高频场景开始,每个 Skill 都要有维护人,用业务结果度量价值。**"少而精"比"多而杂"更有效**。

这一章是 Skill 概念的铺垫章。**Skill 的开发细节(怎么用变量和分支、怎么和外部系统集成)在第一卷附录 C(Skill 编写手册)展开**。本章只讲"是什么、怎么用、怎么转",不深入"怎么写"。

**如果你只读一段,就读这段**:**Skill 是把"私房菜谱"升级为"中央厨房标准化菜谱"的工具,它解决的不是"这一次怎么写",而是"每一次怎么稳定地写"**。

## 实践练习

1. **试用 3 个 Skill**:打开 WorkBuddy 技能市场,挑 3 个你认为本周用得到的 Skill(推荐:周报整理 / 邮件翻译 / 会议纪要)。每个 Skill 试用一次,看输出是否符合你的期望。试用满意的就"加载",不满意的忽略。**这次练习的目的:让你体验"调 Skill"和"写提示词"的差异**。

2. **把第 5 章的"标准提示词 v1"转成 Skill**:打开第 5 章你定下来的那个提示词,按本章"标准 5 步流程"转成 Skill。具体动作:(1) 抽象出"通用 vs 参数";(2) 写三构成;(3) 拿 1 个真实输入跑一遍;(4) 命名归档。**不用发布到技能市场,自己用即可**。

3. **列出你团队里"被反复使用的 3 个提示词"**:问问你团队里 3-5 位同事,过去一个月他们写 AI 提示词时,**最常用的 3 句是什么**。汇总后,挑出 1 个最值得变成 Skill 的,作为"团队第一个共享 Skill"的候选。**这次练习的目的:让你开始识别"团队级 Skill 化机会"**。

4. **(可选)识别一个"老师傅经验"**:观察你团队里某位资深员工,看他在某个具体工作上有没有"不可言传的规则"(比如审合同、审报销、写汇报、写邮件)。把这些规则列出来,作为未来 Skill 化的素材。**这次练习的目的:让你意识到 Skill 不只来自提示词,更来自"经验"**。
