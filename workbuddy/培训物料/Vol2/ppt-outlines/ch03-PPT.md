## Slide 2 — 本章导问
- 一句话核心问题:团队从 1 人扩到 10 人,如何让文件夹"自己会说话"——找文件不靠"问张三要"?
- 副标:30 分钟搭好一套"5 年不崩"的团队文件夹体系
- 关键:不靠工具,靠"人 + 流程 + 工具"三位一体

## Slide 3 — 三层结构:公共 / 个人 / 项目
- 内容:三层模型一张图
  - 公共区:长期资产,全员可见、负责人可改
  - 个人区:草稿,本人全权,他人不可见
  - 项目区:有时限的临时战场,结束即归档
- 配图:`figures/2.3.1-three-tier-folders.png`
- 数据来源:章节 1.1-1.5(46-145 行)

## Slide 4 — 没有分层的 5 种乱象
- 内容:一屏五卡片
  - 散落 / 重名 / 越权 / 失联 / 重复劳动
- 配图:自绘 5 个生活化场景(桌面、微信、邮件附件穿插)
- 数据来源:章节 1.1(36-43 行)
- 关键句:"每个人都是好意的,合起来就是一场灾难"

## Slide 5 — 公共区:中央图书馆
- 内容:特征 = "写一次,读多次"
- 典型内容:公司制度 / 客户资料 / OKR / 品牌资产 / 定稿方案
- 反模式:把"进行中"的方案也丢进公共区,导致新员工不知道哪版是定稿
- 配图:`figures/2.3.5-team-folder.png`
- 数据来源:章节 1.2(52-67 行)

## Slide 6 — 个人区:私人抽屉
- 内容:特征 = "写得多,共享得少"
- 边界:默认仅本人可见,即使是团队负责人也不应"为方便"看成员私人草稿
- 工程做法:`chmod 700` 或 NAS 权限隔离,不要依赖 WorkBuddy 应用层权限(可绕过)
- 数据来源:章节 1.3(69-91 行)

## Slide 7 — 项目区:临时战场
- 内容:特征 = "高强度协作,有时限"
- 编号:每个项目立项即分配唯一编号(例:`PRJ-2026-018`),整个生命周期不换
- 子目录:`00-项目立项/ 01-需求/ 02-设计/ 03-开发/ 04-测试/ 05-复盘/ + README.md`
- 反模式:项目做完三个月不归档,半年后没人记得这项目是干嘛的
- 数据来源:章节 1.4(93-122 行)

## Slide 8 — 案例 1:实习生的"无意识越权"
- 内容:20 人团队,实习生误删财务预算表
- 根因:公共区被当便签墙,没有 R/W/S 分级
- 启示:"一个人能看到的,不应多于他完成工作所需要的"
- 配图:自绘误删时间线
- 数据来源:章节 1.1(36-43 行)+ 3.2(298-312 行)

## Slide 9 — 三种反模式与一条检验标准
- 内容:三种反模式
  - 反模式 1:桌面 + Downloads 大杂烩
  - 反模式 2:一个超大的共享盘
  - 反模式 3:过度细分,每个文件一个文件夹
- 检验标准:新人入职第一天,只看文件夹,能否在 30 分钟内搞清楚协作方式?
- 配图:三张并排反例截图
- 数据来源:章节 1.6(149-159 行)

## Slide 10 — 文件命名:四段式 + 日期格式
- 内容:公式 `<项目编号>_<类型>_<日期>_<负责人>_<状态>.<扩展名>`
- 示例:
  - `PRJ-2026-018_设计方案_20260615_张三_v2.3_终稿.pdf`
  - `PRJ-2026-018_开发周报_20260622_李四_w12.xlsx`
- 日期格式:推荐 `YYYYMMDD`,可直接按字典序排序等价按时间排序
- 配图:`figures/2.3.2-naming-convention.png`
- 数据来源:章节 2.1 + 2.4(170-194 行 + 225-232 行)

## Slide 11 — 必须杜绝的 5 种命名 + 3 种失败
- 内容:大字 + 红叉
  - ❌ `最终版.docx` / `最终版(2).docx` / `最终版(真的).docx`
  - ❌ `新建文件夹` / `新建文件夹(2)`
  - ❌ `2025 方案` / `2025 方案 - 副本`
  - ❌ 含空格、特殊符号(`!@#$%`)
  - ❌ 中文 + 英文混排(`Project-方案-最终`)
- 失败模式:规范太长没人看 / 没人检查 3 个月回退 / 工具不配合(Windows 同步截断)
- 解药:规则 ≤ 1 页 ≤ 5 条 + 自动化检查 + 人工季度抽查
- 数据来源:章节 2.2 + 2.6(200-204 行 + 246-254 行)

## Slide 12 — 状态标签 7 选 1
- 内容:速查表
  - 草稿 / 评审 / 定稿 / 终稿 / 已废弃 / 已归档 / 临时
- 规则:状态变化时,复制一份并重命名,不要在原文件上改状态
- 数据来源:章节 2.3(208-222 行)

## Slide 13 — 权限 R/W/S 三种粒度
- 内容:三种粒度速查
  - R 读:可查看,不可改 — 全员
  - W 写:可修改,删除受控 — 项目成员 / 负责人
  - S 分享:可对外生成外链 — 部门负责人以上
- 配图:`figures/2.3.3-permission-matrix.png`
- 数据来源:章节 3.1(279-296 行)

## Slide 14 — 「最小可见」原则 + 权限变更留痕
- 内容:金科玉律 — "一个人能看到的,不应多于他完成工作所需要的"
- 落地两个动作
  - 默认拒绝:新建文件夹默认仅负责人可见
  - 定期复盘:每季度审计一次权限
- 外链 30 天过期,过期后需重新申请
- 留痕四字段:时间 / 变更人 / 内容 / 原因
- 数据来源:章节 3.2 + 3.3 + 3.6(298-377 行)

## Slide 15 — 案例 2:`~/Downloads/` 设为工作目录
- 内容:产品经理把 Downloads 挂载成 WorkBuddy 工作目录
- 后果:WorkBuddy 索引到工资单 / 合同 / 微信截图
- 真相:不是 WorkBuddy 偷看,是用户亲手"把门打开"
- 解药:`_private` 下划线前缀 = 团队命名级的"默认不可见"
- 配图:`figures/2.3.4-workspace-folder.png` + 自绘对比图(挂载 / 不挂载)
- 数据来源:章节 3.4 + 4.5(329-346 行 + 456-464 行)

## Slide 16 — 多工作目录 + 跨平台路径
- 内容:v3.2 支持最多 5 个工作目录(2026 年 6 月版本)
- 三个推荐挂载
  - 01-当前项目/(主要)
  - 02-参考资料/(只读)
  - 03-个人草稿/(个人)
- 跨平台:macOS `/Users/<user>/` / Windows `C:\Users\<user>\` / Linux `/home/<user>/`
- 关键:不要求绝对路径统一,每人本地建立 `~/workbuddy-workspace/`,内含符号链接指向团队盘
- 数据来源:章节 4.3 + 4.6(423-436 行 + 466-496 行)

## Slide 17 — 版本控制 + 项目归档
- 内容:三份副本 / 两种介质 / 一份异地
  - 副本 1:团队 NAS(主存储)
  - 副本 2:Git 远程仓库(GitHub / GitLab)
  - 异地备份:每周全量到 AWS S3 / 阿里云 OSS
- 网盘历史版本:保留 90 天(性价比最高的设置)
- Conventional Commits:`feat:` / `fix:` / `docs:` / `refactor:`
- 项目结束 30/30 规则:30 天内归档 + 归档后保留 30 天只读 + 之后进入历史归档
- 归档四件套:冻结目录 / 打包备份 / 写复盘(进 Git tag)/ 移出活动区
- 配图:`figures/2.3.6-version-control.png`
- 数据来源:章节 5.2 + 5.3 + 5.4 + 5.5(522-588 行)

## Slide 18 — 互动 / 讨论

- 开放题 2:数一数"最终版 / 副本 / 新建文件夹"占你当前共享盘多少?全删会误删定稿吗?

## Slide 19 — 小结 + 附录 D 清单 3 速览
- 3 句话
  - 目录分层(公共 / 个人 / 项目)+ 命名四段式 + 权限最小可见,这三件套是团队协作的"语法"
  - WorkBuddy 工作目录 = 它能看到的整个世界,用 `_private` 下划线前缀做"默认不可见"
  - 备份 3-2-1 原则 + Git 提交规范 + 项目 30/30 归档规则,出事后能找回才是真版本控制
- 附录 D 清单 3:团队工作目录建立检查表 5 段式(目录结构 / 权限 / 命名 / 版本 / 上线公告),新团队搭建当日打印照勾,磨合期 1 周
- 配图:附录 D 清单 3 拍一张工位贴图(自拍或示意图)
