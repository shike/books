## 一、本模块回答的核心问题(1 句)
WorkBuddy 接入 OA / CRM / 知识库时,如何设计一套权限清晰、限流可控、数据一致的集成方案?

## 二、学习目标(完成后能...)
1. 用 4 模式(查询/写入/触发/审批)对集成需求分级,划清读写边界。
2. 为任意集成画出 API + Webhook 组合图,标注限流、对账机制。
3. 知识库选 RAG 而非微调,设 85% Top-5 召回率为质量基线。
4. 走通附录 D 清单 3 的 4 类目,把"爆炸半径"写进方案。

## 三、关键案例(2-3 个)

### 案例 1:零售 ERP 的"9 折价格"事故
- 场景:某零售企业让 WorkBuddy 接入 ERP,店长一句"全部 9 折"导致 8000+ SKU 改价,损失十几万元。
- 冲突/问题:写入无二次确认;调价无金额/品类白名单;无灰度。
- 启示:写操作永远比读操作严苛一个数量级——必确认、必白名单、必灰度。来源:第三卷 §6.5,L418-430。

### 案例 2:对话式 CRM 把销售跟进数从 8 提到 11
- 场景:某 SAAS 销售在飞书里"说话"调客户全貌(联系/商机/合同/健康度),不再切 CRM。
- 冲突/问题:行级权限、写入回滚、数据新鲜度三件事要同时解决。
- 启示:销售驱动型团队,CRM 对接 ROI 最高,但必须配齐权限+回滚两道闸门。来源:第三卷 §1.2,L58(SAAS 销售总监访谈,2026-03)。

### 案例 3:实习生"客户画像"看到了高管联系方式
- 场景:某公司 WorkBuddy 调 CRM 用"超级 Token"绕过权限,实习生拿到高管手机号。
- 冲突/问题:认证鉴权未闭环,下游按"应用身份"放行。
- 启示:任何"为效率"开的后门都会成泄露入口——必须 OAuth 2.0 + 用户身份透传。来源:第三卷 §6.1,L348-353。

## 四、互动题(讲师在课堂上抛出的问题)
1. 开放题:列你公司最想接入的 3 个系统,用 4 模式分别打勾、估 QPS。讲师点评"哪些可灰度、哪些直接封死"。
2. 投票题:AI 写操作你倾向哪种确认机制?(a) 自动 (b) 单次确认 (c) 双重审批 (d) 仅白名单)
3. 分组题:3 个真实场景,组内画 API + Webhook 集成图,标限流与对账。
