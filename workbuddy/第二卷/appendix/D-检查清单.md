# 附录 D 检查清单

本附录是第二卷的速查工具。前面 7 章讲的是为什么、是什么、怎么想,这一份给的是"做之前对照一遍"的硬指标。每份清单都按 checkbox 形式编排——打印出来贴工位上,或者塞进周会的文件夹,做完一项打一个勾。

清单不是替代正文的方法论,而是方法论的最后一公里。它存在的意义只有一个:把"我记得要这么做"变成"我打完了勾,所以我做了"。

每份清单的勾选项数控制在 15-25 之间,这是经过实践验证的密度——少于 15 项往往遗漏关键控制点,多于 25 项会让执行者疲劳、放弃勾选。请按顺序完成,不要跳项。

## 清单 1 团队三阶段推进检查表

**适用场景**:决定在团队内引入 WorkBuddy 时,按"试点-推广-固化"三阶段推进,每个阶段退出前对照本表。试点期建议 2-4 周,推广期 4-8 周,固化期 8 周以上。三阶段时间不可压缩。

### 一、试点期(2-4 周)

- [ ] 选定 1 个高频、低风险、可量化的业务场景(例:周报生成、会议纪要、SQL 查询)
- [ ] 圈定 3-5 名种子用户,覆盖一线执行者与中层管理者各 1-2 名
- [ ] 为种子用户开通独立工作目录,与生产数据物理隔离
- [ ] 设定 3 个可量化指标(例:周报耗时下降 30%、会议纪要准确率 >85%、SQL 一次通过率 >70%)
- [ ] 准备 1 份"使用日记"模板,要求种子用户每天记录 1 个有效用例 + 1 个失败用例
- [ ] 每周固定 30 分钟复盘会,只回答"这周多做了什么、省了多少时间、踩了什么坑"
- [ ] 明确试点期的"禁用清单":不接核心生产数据、不发对外材料、不动财务/法务/合同文档
- [ ] 给种子用户开通独立 Credits 预算,不与企业主账号混用
- [ ] 指定 1 名内部"答疑人",处理种子用户每天的提问
- [ ] 第 2 周末做一次中期评估,数据低于目标 50% 时启动复盘而非延期
- [ ] 试点结束产出 1 份《试点报告》,包含数据、案例、未解决问题

### 二、推广期(4-8 周)

- [ ] 将试点期的 3-5 名种子用户扩到 20-50 人,覆盖 3-5 个业务部门
- [ ] 把《试点报告》内部分享 1 场,记录提问清单作为 FAQ 第一版
- [ ] 建立团队工作目录标准结构(参考清单 3),所有用户遵循同一规范
- [ ] 启用 1 套自动化触发器(参考清单 6),从手动操作过渡到自动执行
- [ ] 开通"工作目录权限矩阵",区分可读/可写/可删,严格执行
- [ ] 培训分两轮:第 1 轮基础操作,第 2 轮提示词工程(每轮不超过 90 分钟)
- [ ] 建立"提示词库"共享区,鼓励用户复用而非重复造轮子
- [ ] 设立"WorkBuddy 周会"机制,固定每周 15 分钟同步进展
- [ ] 设定推广期的"灰度策略":每个新部门先放 20% 试用,1 周后扩到 100%
- [ ] 同步给 IT/信息安全团队报备,确认数据合规边界
- [ ] 第 4 周做一次全量数据复盘:使用率、活跃用户、Credits 消耗、问题工单
- [ ] 产出《推广手册 v1》,沉淀操作流程、提示词模板、踩坑案例

### 三、固化期(8 周以上)

- [ ] 将 WorkBuddy 写入团队年度工具栈,纳入采购预算
- [ ] 制定 Credits 月度预算分配规则,按部门/角色/使用量三维度核算
- [ ] 建立"内部专家中心",沉淀团队专属知识(参考清单 5)
- [ ] 设立"WorkBuddy 委员会",由 1 名高管 + 2-3 名种子用户组成,每季度复审
- [ ] 把"使用 WorkBuddy"写进岗位 JD,作为招聘加分项
- [ ] 把"提示词能力"纳入绩效评估的辅助项,不强制但加分
- [ ] 每季度发布 1 次《WorkBuddy 应用报告》,覆盖全公司
- [ ] 建立"反面案例库",记录违规使用、数据泄露、安全事故
- [ ] 设定"退出机制":如果 6 个月内活跃用户低于 30%,启动复盘是否继续投入
- [ ] 把 WorkBuddy 培训纳入新员工 onboarding,首周完成基础操作培训
- [ ] 与厂商建立季度沟通机制,反馈产品建议与版本需求

## 清单 2 Claw 远程控制开启检查表

**适用场景**:为某台设备(办公电脑、测试机、家庭办公设备)开启 Claw 远程控制功能,正式接入 WorkBuddy 之前,逐项对照。本清单按"硬件-网络-身份-命令-应急"五段式编排,顺序不可调换。

### 一、设备与硬件

- [ ] 确认设备系统版本满足最低要求(WorkBuddy v1.2 起:Win 11 / macOS 14+)
- [ ] 设备为长期开机状态,非临时借用机器
- [ ] 已安装最新版 WorkBuddy 桌面客户端,且登录账号与待绑定的 WorkBuddy 账号一致
- [ ] 设备硬件指纹(MAC 地址或设备 ID)已记录在案,用于异常登录识别
- [ ] 关闭设备的"自动休眠",避免远程唤醒失败
- [ ] 关闭设备的"屏幕锁自动登出",或延长至 8 小时以上

### 二、网络与可达性

- [ ] 设备所在网络支持双向通信(非纯内网 NAT),否则需配置中继
- [ ] 设备 IP 或域名已写入 WorkBuddy 控制台的网络白名单
- [ ] 测试从外网 Ping 设备的延迟,要求 <200ms,否则体验下降
- [ ] 设备的防火墙已放行 WorkBuddy 客户端的端口(默认 47811)
- [ ] 设备的代理服务器(如有)已放行 WorkBuddy 域名

### 三、身份与权限

- [ ] 启用"二次确认登录":每次新设备首次接入,需手机扫码或邮箱验证码
- [ ] 设备绑定到具体责任人(非"公用设备"),出问题时责任可追溯
- [ ] 设置单设备最长在线时长(建议不超过 24 小时),超时自动断连
- [ ] 限制可下发命令的人员范围,非管理员账号只能"查看"不能"执行"
- [ ] 开启"敏感操作二次确认":删除文件、提交代码、发送消息等动作需责任人确认

### 四、命令与脚本

- [ ] 预审所有通过 Claw 下发的命令清单,白名单制而非黑名单制
- [ ] 禁止下发 `rm -rf`、`format`、`git push -f` 等高危命令
- [ ] 命令执行结果自动归档,默认保留 90 天
- [ ] 长任务(超过 5 分钟)需有进度回调,避免网络断开后任务状态不明
- [ ] 脚本执行前必须先 dry-run,人工审核通过后才能真实运行

### 五、应急与回滚

- [ ] 配置"一键断连"快捷键,责任人本人可随时切断 Claw 会话
- [ ] 设置异常行为告警:陌生 IP 登录、凌晨执行命令、短时间内高频操作
- [ ] 保留设备本地操作日志,即使 Claw 断开也能追溯最近动作
- [ ] 制定"设备丢失"应急流程:第一时间在 WorkBuddy 控制台注销该设备
- [ ] 每季度演练 1 次断连-重连流程,验证应急通道有效

## 清单 3 团队工作目录建立检查表

**适用场景**:为新团队、新项目、新部门建立 WorkBuddy 工作目录(workspace),首次搭建或大规模重组时使用。目录设计应一次性到位,后续迁移成本极高。

### 一、目录结构

- [ ] 根目录命名规则:按"团队-业务-年份"三段式(例:`marketing-product-2026/`)
- [ ] 一级子目录固定为 5 类:`00-inbox/`、`10-projects/`、`20-knowledge/`、`30-templates/`、`90-archive/`
- [ ] `00-inbox/` 设为只对 WorkBuddy 可写、团队成员只读,避免误操作
- [ ] `10-projects/` 下每个项目独立子目录,命名含日期前缀(例:`2026Q3-launch/`)
- [ ] `20-knowledge/` 存放团队专属知识,按主题分二级目录
- [ ] `30-templates/` 存放提示词模板、文档模板,只允许管理员修改
- [ ] `90-/` 只追加不删除,半年内的旧文件一律归档不删

### 二、权限分配

- [ ] 区分三类角色:管理员(可改结构)、编辑者(可读写文件)、只读者(只能查看)
- [ ] 权限粒度到子目录,不开放整个工作目录的"全权"
- [ ] 权限变更需走审批流程,默认有效期 90 天,到期重新申请
- [ ] 离职成员当天撤销权限,不允许"宽限期"
- [ ] 外包/外部协作者使用独立子目录,避免与内部数据混放

### 三、命名规范

- [ ] 文件名禁用特殊字符(`# % & { } \ /` 等),避免跨平台同步问题
- [ ] 文件名日期格式统一为 `YYYY-MM-DD`(例:`2026-08-16-周报.md`)
- [ ] 中文文件名需同时保留英文别名(在文件第二行用注释标注)
- [ ] 同一项目内文件命名保持动词开头(例:`draft-`、`final-`、`review-`)
- [ ] 同一概念在不同目录下保持同义(不要 `客户` 与 `用户` 混用)

### 四、版本与同步

- [ ] 启用 WorkBuddy 工作目录的自动快照,默认每日 1 次
- [ ] 关键文件(合同、定价、对外材料)开启"修改即留痕"
- [ ] 团队工作目录与个人工作目录物理分离,不允许双向同步
- [ ] 跨部门协作通过"分享链接",不通过"复制文件到对方工作目录"

### 五、上线与公告

- [ ] 工作目录首次建立后,组织 1 场 30 分钟的结构说明会
- [ ] 输出 1 份《目录使用手册》,覆盖权限、命名、归档、应急
- [ ] 在团队周会上公布目录地址与访问方式
- [ ] 设置 1 周"磨合期",磨合期内问题优先处理,不追究使用错误
- [ ] 磨合期结束后正式启用,不再容忍"我不知道有这个目录"

## 清单 4 技能市场评估清单(给单个 Skill 试用 3 次打分的清单)

**适用场景**:在 WorkBuddy 技能市场(Skill Marketplace)挑选第三方 Skill 时,先用本表对单个 Skill 进行 3 次试用打分。3 次评分都过 4 分(满分 5 分)才建议纳入团队工具栈。

### 一、首次试用:基线测试(简单任务)

- [ ] 选 1 个简单、明确的输入(例:把 1 段 200 字的中文翻译成英文)
- [ ] 用 Skill 默认参数执行,记录 1 次跑通所需时间
- [ ] 记录输出的准确度(是否需要人工修正,修正成本多大)
- [ ] 评分 1:基础功能(1-5 分,1=完全不能用,5=开箱即用)
- [ ] 评分 2:响应速度(1-5 分,1=超时无响应,5=秒级返回)

### 二、二次试用:边界测试(异常输入)

- [ ] 故意输入 1 个边界情况(例:空字符串、超长文本、繁体中文、专业术语)
- [ ] 记录 Skill 是否优雅降级,还是直接报错或乱输出
- [ ] 检查错误信息是否清晰,是否指引用户如何修复输入
- [ ] 评分 3:异常处理(1-5 分,1=崩溃或乱输出,5=优雅降级并说明)
- [ ] 评分 4:错误提示(1-5 分,1=无任何提示,5=清晰指出问题所在)

### 三、三次试用:压力测试(真实场景)

- [ ] 选 1 个真实业务场景(例:把本周 5 份会议纪要提炼成周报)
- [ ] 不给 Skill 任何额外提示,看它能否独立完成
- [ ] 给 Skill 1 段上下文(团队历史周报、命名规范),看它能否适配
- [ ] 评估人工兜底成本:用 Skill 后比不用省多少时间
- [ ] 评分 5:真实场景适配度(1-5 分,1=必须重度人工修正,5=几乎无需修正)
- [ ] 评分 6:长期复用价值(1-5 分,1=用 1 次就弃,5=每周都会用)

### 四、综合判断

- [ ] 3 次试用 6 项评分合计 ≥ 24 分(满分 30),才进入下一轮评估
- [ ] 检查 Skill 的作者信誉:更新频率、用户评价、安全审计记录
- [ ] 检查 Skill 申请的权限:是否申请了与功能不匹配的权限(红灯)
- [ ] 试用期间 Credits 消耗是否在预算内,避免"便宜但费 Credits"
- [ ] 记录试用日志,3 个月后回看是否还在用,用于淘汰决策

## 清单 5 专家中心录入检查表

**适用场景**:向 WorkBuddy 专家中心(Expert Hub)录入团队专属知识(业务流程、操作规范、领域术语),使 WorkBuddy 在该领域能给出更准确的回答。每条知识的录入都需走完本表。

### 一、知识边界

- [ ] 明确这条知识解决什么问题(一句话讲清楚)
- [ ] 明确这条知识不解决什么问题(避免误用)
- [ ] 明确适用人群(管理者、一线、新人、客户)
- [ ] 明确时效性:知识有效期多久,过期如何标记
- [ ] 明确来源:内部规范、外部标准、专家访谈、还是会议纪要

### 二、内容质量

- [ ] 内容长度控制在 500-2000 字,过长拆分多条
- [ ] 包含至少 1 个真实案例(脱敏后),不止于抽象原则
- [ ] 包含至少 1 个反例或常见错误,帮助 WorkBuddy 识别误用
- [ ] 专业术语首次出现给定义,后续统一使用
- [ ] 不夹杂个人观点,只录入"可被验证的事实"

### 三、结构与格式

- [ ] 标题使用名词短语,不超过 20 字
- [ ] 关键结论放在第一段,避免藏在长文末尾
- [ ] 列表项不超过 7 条,超过则分组或拆分
- [ ] 引用外部材料需注明来源与日期
- [ ] 配图需有图说,避免依赖图片脱离上下文

### 四、权限与可见性

- [ ] 选择可见范围:全员、部门、仅指定人员
- [ ] 敏感内容(薪资、客户数据、未公开财报)严格控制可见范围
- [ ] 设置修改权限:只有指定专家可改,其他人只能引用
- [ ] 设置评论权限:允许团队成员提问,集中解答而非各自改
- [ ] 启用"使用统计":记录被 WorkBuddy 调用的频率,识别冷门知识

### 五、上线与维护

- [ ] 录入后先在小范围内验证 1 周,观察 WorkBuddy 调用是否准确
- [ ] 设定责任人,知识不是"录完就完",需定期回顾
- [ ] 设定更新周期:核心知识季度回顾,操作规范半年回顾
- [ ] 失效知识及时下架,避免 WorkBuddy 引用过时内容
- [ ] 累计录入 50 条以上时,组织 1 次"知识评审会"识别重复与冲突

## 清单 6 自动化触发器上线检查表

**适用场景**:在 WorkBuddy 中配置自动化触发器(Trigger),让某个事件(如定时、收到邮件、文件变化)自动触发一系列动作(如生成报告、发送通知、调用 Skill)。触发器一旦上线就是"无人值守",所以上线前必须对照本表。

### 一、触发条件

- [ ] 明确触发事件的来源(定时、邮件、文件、消息、Webhook)
- [ ] 明确触发的具体条件(例:每周五 18:00,而非"工作日结束时")
- [ ] 考虑边界时间:跨时区、夏令时、节假日的处理逻辑
- [ ] 设置防抖:同一事件在短时间(如 1 分钟)内多次触发,只执行 1 次
- [ ] 设置最大并发:同一触发器同一时间最多 N 个实例,避免资源耗尽

### 二、执行动作

- [ ] 列出所有将要执行的动作清单,顺序、依赖、超时时间
- [ ] 关键动作(如发送对外通知、提交数据)有二次确认环节
- [ ] 长任务(超过 5 分钟)拆分为可中断的子任务
- [ ] 幂等性:同一动作重复执行不会产生副作用
- [ ] 失败重试:每个动作有重试次数上限与退避策略

### 三、输出与通知

- [ ] 明确输出形式:邮件、消息、文件、API 调用
- [ ] 明确收件人:不是发给"所有人",而是发给"需要看到的人"
- [ ] 失败告警:触发器失败时通知到责任人,不能"静默失败"
- [ ] 执行日志:每次触发都留痕,包括时间、输入、输出、耗时
- [ ] 日志保留 90 天以上,便于事后审计

### 四、风险与回滚

- [ ] 评估最坏情况:触发器误触发会产生什么后果
- [ ] 设置"紧急停止"开关:任何责任人可一键停用
- [ ] 保留"手动执行"通道:自动化失败时可用相同参数手动重跑
- [ ] 灰度上线:先在测试环境跑 1 周,再切到生产
- [ ] 首次生产环境执行时,责任人现场值守,确认无异常再离开

### 五、上线后观察

- [ ] 上线 24 小时内每 4 小时检查 1 次执行日志
- [ ] 上线 1 周内每天检查 1 次成功率与失败原因
- [ ] 收集 5 名真实用户的反馈,识别"理论上对但实际别扭"的环节
- [ ] 第 2 周末做 1 次复盘,调整触发条件或动作顺序
- [ ] 1 个月后正式"毕业",进入常规运维节奏

## 清单 7 30 天培训日清表

**适用场景**:面向 5-20 人小团队的 WorkBuddy 集中培训,周期 30 天(4 周)。每天 30-60 分钟,既有动手练习也有答疑。完成后团队成员应能独立完成清单 1 中"试点期"的所有动作。

### 第一周 基础操作(打地基)

- [ ] Day 1:开营 30 分钟,介绍 WorkBuddy 能做什么、不能做什么,签订使用承诺
- [ ] Day 1:每位成员独立完成客户端安装、登录、工作目录初始化
- [ ] Day 2:教 5 个基础交互(对话、追问、复制结果、生成文件、调用 Skill)
- [ ] Day 2:每人用 WorkBuddy 完成 1 个真实小任务(例:把 1 封邮件改成正式版本)
- [ ] Day 3:教 5 个常用快捷键与 3 个高阶设置(自定义指令、上下文长度、模型选择)
- [ ] Day 3:每人复盘昨天任务,提交 1 段"我哪里卡住了"
- [ ] Day 4:答疑专场 60 分钟,集中解答 Day 1-3 的所有问题
- [ ] Day 4:布置周末作业:用 WorkBuddy 完成本周 1 份周报
- [ ] Day 5:周中复盘,展示 3 份优秀作业,识别共性问题
- [ ] Day 5:预告下周内容:提示词工程基础

### 第二周 提示词工程(写出能用的提示词)

- [ ] Day 8:教"角色+任务+约束+示例"四段式提示词结构
- [ ] Day 8:每人用四段式重写 1 个上周用过的提示词,对比效果
- [ ] Day 9:教如何给 WorkBuddy 喂上下文(上传文件、引用工作目录、粘贴文本)
- [ ] Day 9:练习:把 1 份 5 页的产品文档提炼成 1 页摘要
- [ ] Day 10:教如何让 WorkBuddy 持续对齐你的偏好(自定义指令、风格设定)
- [ ] Day 10:每人设定自己的"个人风格文件",作为后续对话的默认上下文
- [ ] Day 11:答疑专场,收集 5 个最常见的"提示词失灵"案例
- [ ] Day 11:布置周末作业:用提示词完成 1 个跨 2 个工作日的任务
- [ ] Day 12:周中复盘,评选本周"最佳提示词",沉淀到团队提示词库
- [ ] Day 12:预告下周内容:工作目录与团队协作

### 第三周 工作目录与协作(用起来)

- [ ] Day 15:教工作目录的设计原则(参考清单 3),用真实场景演示
- [ ] Day 15:每位成员在团队工作目录下建立自己的子目录
- [ ] Day 16:教权限管理:谁能看、谁能改、谁能删
- [ ] Day 16:演练"误操作恢复":删除一个文件,再找回
- [ ] Day 17:教 Claw 远程控制(参考清单 2),演示但不强制每位成员开启
- [ ] Day 17:答疑专场,集中解决工作目录使用中的具体问题
- [ ] Day 18:教团队协作模式:共享提示词、共享工作目录、共享 Skill
- [ ] Day 18:布置周末作业:2 人一组,用 WorkBuddy 协作完成 1 份周报
- [ ] Day 19:周中复盘,展示协作过程中的 3 个亮点与 3 个问题
- [ ] Day 19:预告下周内容:自动化与长期运营

### 第四周 自动化与长期运营(用得久)

- [ ] Day 22:教自动化触发器(参考清单 6),用 1 个简单案例演示
- [ ] Day 22:每位成员尝试配置 1 个自己的自动化(例:每日待办提醒)
- [ ] Day 23:教专家中心(参考清单 5),演示如何录入 1 条团队知识
- [ ] Day 23:每人录入 1 条自己领域的知识,集体评审
- [ ] Day 24:教技能市场(参考清单 4),演示如何评估 1 个第三方 Skill
- [ ] Day 24:答疑专场,收集长期使用的顾虑(数据、隐私、长期价值)
- [ ] Day 25:小组项目展示,每组 5 分钟演示"我们用 WorkBuddy 做了什么"
- [ ] Day 26:总复盘,颁发"完成证书",发布《30 天学习报告》
- [ ] Day 27:建立"WorkBuddy 周会"机制,确定后续固定节奏
- [ ] Day 28-30:自由练习期,答疑人在线但不强制参加
- [ ] Day 30:正式收官,每位成员提交 1 份"30 天使用总结"
