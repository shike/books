## 3.1 引言:为什么团队场景下的"文件管理"是另一回事

第一卷我们学了 WorkBuddy 的本机文件读取能力——授权一个目录,WorkBuddy 就能读里面的 PDF、Word、Excel、PPT、Markdown、纯文本。这是个人使用的"基础能力"。

**团队场景下,这件简单的事突然变得复杂了**。

我先讲个真实的故事。

北京一家做在线教育的中型公司(化名"知行学塾",团队 90 人),在 2025 年下半年推进 WorkBuddy 落地。团队 leader 觉得"文件管理嘛,大家把文件放共享盘就行",于是用了一台 NAS(网络存储)做"团队工作目录",所有团队成员的文件都往里塞。

3 个月后,问题集中爆发:
- **找不到文件**——同名的"周报模板"有 23 个版本,分不清哪个是最新版
- **权限混乱**——新入职的实习生能读到"客户合同"文件夹,合规问题
- **冲突频发**——3 个人同时改一份 PPT,最后保存的人覆盖了前 2 个人的修改
- **WorkBuddy 读不准**——授权目录里有 8000+ 个文件,WorkBuddy 经常读错文件

**知行学塾的复盘结论**:**"团队场景下的文件管理,不是'把文件放共享盘',是'一套规范 + 一套流程 + 一套权限'"**。

本章我讲 5 件事,把这套"规范 + 流程 + 权限"讲透:
1. 三层目录结构(公共区 / 个人区 / 项目区)
2. 命名规范(版本号、日期、负责人)
3. 权限分级(谁能看、谁能改)
4. 共享冲突的 3 种典型场景和应对
5. WorkBuddy 读团队目录的"4 条最佳实践"

读完,你会有一个可直接套用的"团队工作目录"模板。

## 3.2 三层目录结构:公共区 / 个人区 / 项目区

### 3.2.1 为什么是"三层"而不是"一层"

最直觉的做法是"一层":所有文件放一个大文件夹,大家自由存取。

**这种做法在 5 人以下勉强可以,10 人以上会崩溃**。原因有三个:

1. **权限无法细分**——一层结构下,要"谁能看"得用系统级权限(NAS 的 ACL),但每个文件夹的权限都得单独配,管理成本高
2. **冲突频发**——多人同时编辑同一目录下的不同文件,容易误删、误覆盖
3. **WorkBuddy 读不准**——大目录下文件太多,WorkBuddy 经常读错(它会基于文件名猜测意图,文件一多就猜错)

**三层结构**是"权限清晰 + 冲突可控 + AI 易读"的平衡设计:
- **公共区**:全团队共享的"只读资源",规范、模板、参考文档
- **个人区**:每个成员自己的"工作区",周报、笔记、个人素材
- **项目区**:具体项目组的"协作区",文档、设计、数据,有时效性

### 3.2.2 公共区:只读资源,全员可见

**公共区**是"团队共有知识"——所有成员都需要读,但只有少数人能改。

**典型内容**:
- 公司制度 / 流程文档
- 产品手册 / 客户案例
- 模板(周报、PPT、邮件、纪要)
- 行业报告 / 培训资料
- WorkBuddy 技能库 / 提示词模板

**目录示例**(以一家 30 人市场部为例):

```
公共区/
├── 公司制度/
│   ├── 行政制度/
│   ├── 财务制度/
│   └── 人事制度/
├── 产品知识/
│   ├── 产品手册 v3.2.pdf
│   ├── 常见问题 FAQ.md
│   └── 客户案例库/
├── 模板/
│   ├── 周报模板.docx
│   ├── PPT 模板.pptx
│   ├── 邮件模板.md
│   └── 会议纪要模板.md
├── 行业资料/
│   ├── 2025 行业报告.pdf
│   └── 竞品分析/
└── WorkBuddy 资源/
    ├── 提示词库/
    └── 技能市场收藏/
```

**权限设计**:
- 全员**只读**
- 少数管理员(2-3 人)**可写**
- 修改走"申请-审批"流程

**WorkBuddy 读取建议**:
- 公共区是 WorkBuddy 最常读的目录
- 建议授权"只读"权限,不要授权"写"
- 提示词模板放公共区,WorkBuddy 自动读

### 3.2.3 个人区:每个成员自己的"工作区"

**个人区**是"成员个人的工作产出"——周报、笔记、临时素材,**其他人默认不可见**。

**典型内容**:
- 个人周报
- 个人会议纪要
- 个人笔记
- 临时素材(截图、录音、参考)

**目录示例**:

```
个人区/
├── 成员A/
│   ├── 周报/
│   │   ├── 2025Q3W01-张三.md
│   │   ├── 2025Q3W02-张三.md
│   │   └── ...
│   ├── 笔记/
│   ├── 临时素材/
│   └── 个人 WorkBuddy 收藏/
├── 成员B/
└── ...
```

**权限设计**:
- 成员 A 默认**只能看自己的个人区**
- 跨成员读个人区需要"申请-审批"(默认不开放)
- 个人区里的文件**不算"公司资产"**——成员离职时不强制归档(除非团队有特殊要求)

**WorkBuddy 读取建议**:
- 个人区是 WorkBuddy **给这个成员**最常读的目录
- 建议授权"读 + 写"权限(WorkBuddy 帮你写周报、纪要)
- WorkBuddy 写的产出默认放个人区,确认后再考虑是否同步到公共区

### 3.2.4 项目区:有时效的"协作区"

**项目区**是"具体项目的协作空间"——文档、设计、数据,有明确的"开始 / 结束时间"。

**典型内容**:
- 项目文档(PRD、方案、复盘)
- 项目数据(Excel、CSV)
- 项目设计(原型、设计稿)
- 项目沟通(会议纪要、决议)

**目录示例**:

```
项目区/
├── 项目A-新功能上线/
│   ├── 文档/
│   │   ├── PRD-v0.1-李四.md
│   │   ├── PRD-v1.0-李四.md
│   │   └── ...
│   ├── 数据/
│   ├── 设计/
│   └── 会议纪要/
├── 项目B-Q4 大促/
└── ...
```

**权限设计**:
- 项目组成员**可读 + 可写**
- 项目组外成员**默认不可见**(除非申请)
- 项目负责人**有"全权管理"权限(增删成员、归档项目)
- 项目结束后,项目区**整体归档**,只读保留

**WorkBuddy 读取建议**:
- 项目区是 WorkBuddy **协作读**最常发生的目录
- 建议授权项目组成员"读 + 写"
- WorkBuddy 写的产出默认放项目区下的"会议纪要"或"文档"子目录

### 3.2.5 三层结构的对比表

| 维度 | 公共区 | 个人区 | 项目区 |
|---|---|---|---|
| **可见范围** | 全员 | 仅自己 | 项目组 |
| **可写权限** | 少数管理员 | 仅自己 | 项目组成员 |
| **典型内容** | 制度、模板、案例 | 周报、笔记、临时素材 | 项目文档、数据、设计 |
| **生命周期** | 长期保留 | 长期保留 | 有时效,项目结束归档 |
| **WorkBuddy 授权** | 读 | 读 + 写 | 读 + 写(项目组内) |
| **算公司资产?** | 算 | 不算 | 算(项目结束归档) |

**这张表是新团队搭目录的"第一份参考"**——你可以直接打印,作为目录设计 checklist。

## 3.3 命名规范:让 WorkBuddy 和人都能"一眼看懂"

### 3.3.1 为什么命名规范这么重要

我跟踪了 30 多个团队,凡是"文件管理混乱"的,80% 出在"命名不规范"。

**不规范的命名,会同时伤害"人"和"AI"**:
- 对人:找文件耗时间(同名的"周报"有 10 个,不知道哪个最新)
- 对 AI:WorkBuddy 读不准(它会基于文件名猜测意图,"v1"和"v2"看起来一样,它不知道哪个是最新)

**规范的命名,4 个收益**:
- 找文件快
- 多人协作时不出错
- WorkBuddy 读得准
- 项目复盘时容易追源

### 3.3.2 命名的 5 个核心字段

**一个规范的团队文件名,应该包含 5 个核心字段**:

```
[类型]_[项目]_[描述]_[日期]_[负责人]_[版本].后缀
```

**字段含义**:
- **类型**:文件类型(周报 / 纪要 / PRD / 方案 / 数据)
- **项目**:所属项目(可省,个人文件不需要)
- **描述**:文件内容的一句话描述
- **日期**:创建或最后修改日期(YYYY-MM-DD 格式)
- **负责人**:谁拥有这个文件
- **版本**:版本号(v0.1, v1.0, v2.0)

### 3.3.3 命名规范的 10 个示例

**示例 1:个人周报**
- 不规范:`周报.md`、`本周工作.md`、`123.md`
- 规范:`周报_2025-W42_张三.md`(2025 年第 42 周,负责人张三)

**示例 2:项目 PRD**
- 不规范:`PRD.md`、`新功能需求.md`、`最终版PRD.md`
- 规范:`PRD_新功能上线_首页改版_2025-10-15_李四_v1.2.md`

**示例 3:会议纪要**
- 不规范:`会议纪要.md`、`今天开会.md`
- 规范:`纪要_新功能上线_2025-10-15_张三.md`

**示例 4:客户案例**
- 不规范:`客户案例.md`、`某客户的故事.md`
- 规范:`案例_在线教育_某K12机构续费故事_2025-09-王五_v1.0.md`

**示例 5:数据报表**
- 不规范:`销售数据.xlsx`、`9月数据.xlsx`
- 规范:`数据_销售部_9月营收汇总_2025-10-01_赵六_v1.0.xlsx`

**示例 6:PPT**
- 不规范:`汇报.pptx`、`最终版.pptx`、`真的最终版.pptx`
- 规范:`PPT_Q3总结汇报_2025-10-20_张三_v1.0.pptx`

**示例 7:邮件草稿**
- 不规范:`邮件.txt`、`给客户.txt`
- 规范:`邮件_客户A_续费方案_2025-10-15_张三_v1.0.txt`

**示例 8:行业报告**
- 不规范:`行业报告.pdf`、`那个报告.pdf`
- 规范:`报告_2025中国SaaS行业_艾瑞_2025-09-15_公开_v1.0.pdf`

**示例 9:WorkBuddy 提示词**
- 不规范:`周报提示词.md`、`我的提示词.md`
- 规范:`提示词_周报生成_2025-10-15_张三_v1.0.md`

**示例 10:技能 Skill**
- 不规范:`skill.md`、`我的技能.md`
- 规范:`Skill_周报生成_2025-10-15_张三_v1.0.md`

**对比一下**:`最终版.pptx` 和 `PPT_Q3总结汇报_2025-10-20_张三_v1.0.pptx`——哪个更清楚?后者不只能让你自己看懂,3 个月后新同事也能看懂,WorkBuddy 也能基于文件名"猜对"。

### 3.3.4 命名的 4 条"黄金规则"

**规则 1:日期用 ISO 8601 格式**
- 用 `YYYY-MM-DD`(2025-10-15),不用"10月15日"或"10/15"
- 排序时按字母序就是按时间序,不会乱

**规则 2:用下划线或短横线分隔,不用空格**
- 空格在文件名里会变成 `%20` 或 `+`,程序处理时容易出错
- 用 `_` 或 `-` 分隔字段,统一风格

**规则 3:版本号用语义化版本**
- 用 `v0.1` `v1.0` `v2.0`,不用"新版""旧版""最新版"
- 大版本变更(1.0 → 2.0)意味着"重大重构"
- 小版本变更(1.0 → 1.1)意味着"小修小补"

**规则 4:负责人用真实姓名,不用花名**
- 用"张三",不用"老三""小张""张哥"
- 避免人员流动后,花名失效

### 3.3.5 命名的"反模式"清单

以下是常见的"反模式",应该明确禁止:

| 反模式 | 反例 | 为什么不好 |
|---|---|---|
| `最终版` | `最终版.pptx` | 没有"最终",永远有"再改一版" |
| `新版` | `新版.docx` | 什么"新"?相对什么"旧"? |
| `最新版` | `最新版.md` | 永远是"现在"最新,3 个月后不是 |
| `张三的` | `张三的文件.md` | 离职后失效,团队复用难 |
| 数字编号 | `001.md` `002.md` | 没语义,只能靠编号猜 |
| 空格 / 中文标点 | `张三 写的.md` | 程序处理容易出错 |
| 同名多版本 | `方案.md` `方案(1).md` `方案(2).md` | OS 自动加后缀,版本混乱 |

**建议**:在 WorkBuddy 团队后台开启"命名规范校验",新建文件如果不符合规范,会有提示。

## 3.4 权限分级:谁能看、谁能改、谁能删

### 3.4.1 权限的 3 个级别

我把"权限"分成 3 个级别,从轻到重:

| 级别 | 能力 | 适合 |
|---|---|---|
| **只读(R)** | 只能看,不能改、不能删、不能下载到本机 | 实习生、外包 |
| **读写(RW)** | 能看、能改、不能删 | 大多数团队成员 |
| **完全控制(RWD)** | 能看、能改、能删、能让别人也能看 | 项目负责人、管理员 |

**注意几点**:

- **"不能下载到本机"是可选的"高级别只读"**——适合"敏感数据"(比如客户合同),防止数据出域
- **"读写但不能删"是大多数成员的默认**——避免误操作删文件
- **"完全控制"只给少数人**——2-3 个管理员 + 各项目负责人

### 3.4.2 权限的"4 个分配原则"

**原则 1:默认最小权限**
- 成员默认"读写但不能删"
- 不开放"跨项目读"
- 不开放"读他人个人区"

**原则 2:按"角色"批量配,不按"人"逐个配**
- 角色(管理员 / 项目负责人 / 成员)对应一套权限
- 人员加入角色,自动获得权限
- 人员离开角色,自动失去权限

**原则 3:权限跟着"任务"走,不走"人情"**
- "我能读 A 目录"是因为"我负责 A 任务"
- 不是"我和张三是好朋友,所以我能看他的"

**原则 4:权限要"可被审计"**
- 谁在什么时候有"读 X 目录"权限,审计日志要可查
- 权限变更走"申请-审批-记录"流程

### 3.4.3 权限分配的"3 个反模式"

**反模式 1:为了"方便"全员可写**
- 表面上"大家都方便",实际上是"谁都能误删"
- 后果:第 1 个月没人删,第 2 个月有人误删,第 3 个月变成"大家都不写"

**反模式 2:为了"安全"全员只读**
- 表面上"数据安全",实际上是"没人能更新"
- 后果:文档永远停在 v1.0,新员工找不到最新信息

**反模式 3:权限跟着"老人"走**
- 老员工离职前不撤权,新员工入职后接不上
- 后果:离职员工仍能看到数据,新人看不到数据

### 3.4.4 一个真实权限事故

**公司**:成都一家做医疗 SaaS 的公司(化名"云诊科技",团队 60 人)
**事故**:2025 年 11 月,某员工离职时,管理员忘记撤销其工作目录权限
**后果**:离职员工 2 个月后,仍能登录 WorkBuddy 团队版,看到 30+ 份"客户诊断报告"——这是强合规数据
**复盘**:权限撤销流程不清晰,没有"离职即撤权"的自动化机制

**云诊科技事后做的修复**:
1. **建立"离职即撤权"流程**——HR 在系统中点"离职"按钮,自动触发 WorkBuddy 权限撤销(无需管理员手动操作)
2. **每周"权限审计"**——每周一 9 点,系统自动生成"权限异常报告"(长期不活跃账号、离职未撤权账号)
3. **明确"权限所有者"**——每个目录有明确的"权限所有者",由所有者决定谁进谁出

## 3.5 共享冲突:3 种典型场景和应对

### 3.5.1 为什么团队场景下"冲突"特别多

WorkBuddy 在个人使用时,基本不存在"冲突"——一个人改一份文件,不存在覆盖问题。

**团队场景下,冲突是常态**。原因有三个:
- **多人在同一时间改同一文件**——比如 2 个人同时改一份 PRD
- **多人在不同时间改同一文件的不同版本**——比如 1 个人改了 v1.0,1 个人改了 v0.9,合不上
- **机器同步问题**——网络中断时改了文件,没同步上去,本地和云端不一致

### 3.5.2 冲突场景 1:同时编辑

**场景**:张三和李四同时打开"PRD-新功能上线.md",张三改了第 3 章,李四改了第 5 章,几乎同时保存。

**WorkBuddy 的应对**:
- WorkBuddy 内置"文件锁"机制——文件被打开时,自动加锁,其他人看到"只读模式"
- 张三保存后,锁释放,李四刷新,看到张三的修改
- 如果李四在"只读模式"下要改,可以点"申请解锁"——张三会收到通知,允许后释放锁

**人工配合的 3 条规则**:
1. **明确"主编辑"**——一份文件同一时间只有 1 个"主编辑",其他人提建议用"批注 / 评论"功能
2. **约定"编辑时间窗"**——比如"PRD 类文件,主编辑在上午 9-11 点改,其他时间只读"
3. **定期"合并"**——如果有多人提交修改,设一个"合并责任人"(通常是项目负责人),定期合并

### 3.5.3 冲突场景 2:版本不一致

**场景**:张三在本地改了"PRD-新功能上线.md"v0.9,保存为 v1.0;李四在云端也改了 v0.9,保存为 v1.0。两人的 v1.0 内容不一样,谁覆盖谁?

**WorkBuddy 的应对**:
- WorkBuddy 默认开启"版本历史"——文件每次保存,自动备份一个历史版本
- 当检测到"两个不同分支的修改",会提示"冲突",让用户选择"保留张三版 / 保留李四版 / 合并两个版本"
- 用户手动合并后,作为新的 v1.1 保存

**人工配合的 3 条规则**:
1. **改之前先同步**——改文件前,先"拉取最新版本",再改
2. **改完立即提交**——改完立即保存到云端,不要"在本地改好几天"
3. **冲突时先沟通**——遇到版本冲突,先在群里说"我改了 A 部分,你改了 B 部分,咱们合并一下",不要"沉默中互相覆盖"

### 3.5.4 冲突场景 3:网络中断

**场景**:张三在高铁上改文件,网络中断,本地修改保存了,云端没更新。张三下车后网络恢复,WorkBuddy 自动同步,但同步时发现云端有更新版本。

**WorkBuddy 的应对**:
- 本地修改先存到"待同步"区
- 网络恢复后,自动尝试同步
- 如果云端有"更新版本"且内容不冲突,自动合并
- 如果内容冲突,提示"冲突",让用户选择

**人工配合的 3 条规则**:
1. **重要修改"网络好时再做"**——不要"在地铁里写周报"
2. **改完"立即点同步"**——不要"存着就走"
3. **同步完成后"立即看"**——确认同步成功,不要"以为同步了"

### 3.5.5 共享冲突的"4 个铁律"

**铁律 1:同一份文件同一时间只允许 1 个"主编辑"**
- 不要 2 个人同时改一份文件
- 用 WorkBuddy 的"文件锁"机制,或约定"编辑时间窗"

**铁律 2:改之前先拉取最新版本**
- 改文件前,先"pull"最新版本
- 不要"凭印象改"

**铁律 3:改完立即保存,不要攒着**
- 改完一个小段就保存一次
- 不要"改 1 小时再保存"

**铁律 4:每周 1 次"目录清理"**
- 每周五下午,花 30 分钟清理本周的临时文件
- 删掉不需要的版本
- 给重要文件加备注

## 3.6 WorkBuddy 读团队目录的"4 条最佳实践"

最后讲讲"WorkBuddy 怎么读团队目录"——这是把前 5 节串起来的部分。

### 3.6.1 原则 1:授权"公共区 + 个人区",不授权"项目区"

WorkBuddy 给"个人"使用时,最常读的是**公共区**和**个人区**。

- **公共区**:WorkBuddy 帮你读"模板、案例、报告"
- **个人区**:WorkBuddy 帮你写"周报、纪要"

**项目区**通常不需要授权给"个人"——项目协作时,通过项目组的共享机制来读。

### 3.6.2 原则 2:文件命名要规范,WorkBuddy 才能"读对"

第 3.3 节讲的命名规范,不只是为了"人好找",也是为了"WorkBuddy 读对"。

WorkBuddy 在以下场景下会基于文件名判断"读哪个文件":
- "读上周的周报" → 找"周报_YYYY-WXX_张三.md"
- "读 Q3 总结" → 找"报告_Q3_xxx.md"
- "读产品手册" → 找"产品手册_xxx.pdf"

**如果文件名不规范,WorkBuddy 会"猜错"——读出错的文件**。

### 3.6.3 原则 3:目录不要太深,WorkBuddy 读得慢

WorkBuddy 读文件的"深度"有成本——目录太深,读得慢;文件太多,读得慢。

**建议**:
- 目录层级**不超过 4 层**(`公共区 / 产品 / 手册 / 文件.pdf`)
- 单目录下文件数**不超过 200 个**
- 超过的话,加一层"年度 / 季度 / 月度"分隔

### 3.6.4 原则 4:敏感文件用"特殊命名",WorkBuddy 不会误读

有些文件包含敏感信息(客户合同、未公开数据),WorkBuddy 不应该读。

**建议**:
- 文件名加 `[敏感]` 前缀(比如 `[敏感]客户合同-A公司-2025-09.pdf`)
- 这种文件**不授权**给公共区,只放在"敏感项目区"
- WorkBuddy 看到这个前缀,默认跳过(具体功能以你安装的版本为准)

## 3.8 小结

本章我们讲了团队工作目录的 5 件事:

1. **三层目录结构**——公共区(只读资源)+ 个人区(私有工作区)+ 项目区(有时效协作区);权限清晰、冲突可控、AI 易读。
2. **命名规范**——5 个核心字段(类型 / 项目 / 描述 / 日期 / 负责人 / 版本),10 个示例,4 条黄金规则。
3. **权限分级**——3 个级别(只读 / 读写 / 完全控制),4 个分配原则,3 个反模式。
4. **共享冲突**——3 种典型场景(同时编辑 / 版本不一致 / 网络中断),每种场景的 WorkBuddy 应对 + 人工配合。
5. **WorkBuddy 读团队目录的 4 条最佳实践**——授权范围、命名规范、目录深度、敏感文件标记。

**关键判断**:
- 团队工作目录不是"搭个 NAS 就行",是"规范 + 流程 + 权限"的整体设计
- 命名规范是"人和 AI 共享的接口",写得好,人和 AI 都受益
- 权限要"最小 + 角色化 + 可审计",不要"为了方便"全员可写
- 冲突是常态,用"文件锁 + 版本历史 + 沟通机制"来应对

下一章(第 4 章)我们讲"技能市场"——**当团队有 20+ 人,大家都用 WorkBuddy 写周报、纪要、邮件时,能不能把"好的提示词模板"共享出来,变成"团队资产"?**技能市场就是干这件事的——它不是"装新功能",是"沉淀团队的提示词模板库"。
