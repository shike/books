## 8.1 引言:为什么"成本"是沉淀期的"天问"

前面 7 章我们讲了试点、推广、沉淀、企业微信、目录、Skill、专家中心、自动化、培训。**所有这些"动作"背后,都对应"成本"**——不只是钱,还有"人时""注意力""决策权"。

我跟踪 30 多个"WorkBuddy 落地"的团队,**凡是"成本账算不清"的,沉淀期一定会出问题**——典型表现有 3 个:

1. **有人"用得太多"**,月底 Credits 不够,leader 才发现"已经超了"
2. **有人"用得很少"**,发了账号没用,Credits 白白浪费
3. **老板问"花这钱值不值"**,leader 答不上来,"工时省了多少"讲不清楚

**这 3 个问题,根因都是"成本治理"没做好**。

"成本治理"听起来像"财务的事",**但其实是"leader 的事"**——预算怎么定、规则怎么写、争议怎么处理,都要 leader 拍板。

本章我讲 5 件事:
1. 预算模型:总池、个人额度、混合,3 种怎么选
2. Credits 池设计:团队总池 / 部门 / 项目 / 个人,4 层结构
3. 按维度分配原则:角色 / 部门 / 项目
4. 审计与回收:让成本"可解释、可追溯、可调整"
5. 团队 Credits 治理框架(可打印)

**重要说明**:WorkBuddy 的 Credits 体系在不同档位、套餐、计费模式下会有差异,**具体价格、Credits 数量、套餐名、消耗规则以你购买本书时 WorkBuddy 官方公告为准**。本章给的"参考量级"是"团队规模 × 高频场景"的粗略估算,用于帮你建立治理框架,**不作为采购报价依据**。

读完后,你会拿到一份"团队 Credits 治理框架"——**今天就能跟财务、IT、老板对一遍**。

## 8.2 预算模型:总池、个人额度,还是混合

讲"成本"之前,先把 3 种基础预算模型讲清楚。

### 8.2.1 两种基础模型

**模型 A:总池制**
- 全团队共用 1 个 Credits 池
- 谁用谁扣,月底看总额
- 没有"个人额度"

**模型 B:个人额度制**
- 每人每月有固定 Credits
- 用完停用,不够申请
- 有"个人额度"

| 维度 | 总池制 | 个人额度制 |
|---|---|---|
| **管理复杂度** | 低(只看总额) | 高(要看个人) |
| **公平感** | 强(大家共用) | 弱(有人多有人少) |
| **效率** | 高(随时可用) | 低(用完要申请) |
| **适用团队** | 5-15 人 / 项目制 | 20+ 人 / 稳定部门 |
| **风险** | 1 个人用爆全部 | 大量"额度闲置" |

### 8.2.2 第三种选择:混合制

**我跟踪 30 多个"成本治理做得好"的团队,90% 用的是"混合制"**。

**混合制的核心结构**:
- **团队总池**:从 WorkBuddy 团队版买来的总 Credits
- **部门池**:每个部门有自己的"子池",从总池分配
- **个人池**:每个人有"基础额度",从部门池分配
- **项目池**:跨部门项目可以申请"专项池"

```
团队总池(100%)
    │
    ├── 部门 A 池(40%)
    │      ├── 个人基础额度(80%)
    │      └── 项目专项池(20%)
    │
    ├── 部门 B 池(35%)
    │      ├── 个人基础额度(80%)
    │      └── 项目专项池(20%)
    │
    └── 储备池(25%)
           ├── 应急
           └── 培训 / 试点
```

**关键设计**:
- **总池是"上限"**——从 WorkBuddy 团队版购买
- **部门池是"分配"**——按部门规模 / 业务需求分配
- **个人池是"基础"**——保障每个人"够用",不至于"一上来就碰额度"
- **储备池是"灵活"**——应对"试点 / 培训 / 临时项目"等需求

### 8.2.3 决策表:你的团队该选哪个

我用 4 个问题帮你判断:

| 问题 | 答案倾向 → 推荐模型 |
|---|---|
| 1. 团队规模? | 5-15 人 → 任意 / 20+ 人 → 混合制 |
| 2. 业务稳定性? | 项目制,每月变 → 总池制 / 稳定部门 → 混合制 |
| 3. 公平 vs 效率,你要哪个? | 公平 → 个人额度 / 效率 → 总池制 / 都要 → 混合制 |
| 4. 财务审计严不严? | 严 → 个人额度 / 不严 → 总池制 / 中等 → 混合制 |

**典型答案**:
- 5-10 人创业团队 → **总池制**(简单,够用)
- 20-50 人稳定部门 → **混合制**(标准答案)
- 50+ 人多部门公司 → **混合制 + 储备池**(必选)

### 8.2.4 一个反直觉的观察:管得严,未必省得多

我跟踪 20 多个团队的"成本治理",发现一个反直觉的现象:

**管得越严(每人固定额度、用完停用)的团队,反而"用得越省"——但"用得越省的团队,产出也越少"**。

**为什么会这样**?
- 严格的额度制 → 大家"省着用" → 不敢尝试新场景 → 新场景不跑 = 没有"新价值"
- 宽松的总池制 → 大家"敢试" → 试出 3-5 个高效场景 → 整体效率提升

**正确认知**:**成本治理的目标不是"省 Credits",是"花得值"**。

**3 个反直觉判断**:
1. **管得严,未必省得多**——严格额度制让团队"不敢试",反而错过高价值场景
2. **用得少,未必省得对**——10 个人没人用,等于 10 份 Credits 浪费
3. **超一点,比省太多好**——超 10% 但产出翻倍,比省 50% 但没产出,划算

**治理原则**:**先宽松(让团队敢用) → 看数据(找出高效场景) → 再收紧(把浪费的砍掉)**。**顺序不能反**。

## 8.3 Credits 池设计:四层结构

我推荐"四层 Credits 池"结构,适合 20-50 人团队:

### 8.3.1 第一层:团队总池

**定义**:从 WorkBuddy 团队版购买的总 Credits(具体数量以 WorkBuddy 官方公告为准)。

**配置建议**(以 30 人团队为例,实际以你购买的团队版套餐为准):
- 基础档:适合"试点 + 推广"期,够 30 人用
- 进阶档:适合"沉淀"期,够 30 人 + 自动化跑
- 高阶档:适合"全员重使用",具体以 WorkBuddy 官方为准

**配置原则**:
- **先买"基础档"试 3 个月**——看实际消耗,再加
- **不要一上来买"高阶档"**——可能用不完,白花钱
- **预留 20-30% 给储备池**——试点 / 培训 / 应急

### 8.3.2 第二层:部门池

**定义**:从总池分配到每个部门的"子池"。

**分配原则**(参考比例,以你团队实际调整):

| 部门 | 部门池占比 | 理由 |
|---|---|---|
| **销售** | 25-30% | 客户沟通、邮件、报价高频 |
| **运营** | 20-25% | 周报、活动复盘、用户调研 |
| **产品** | 10-15% | PRD、用户故事、文档整理 |
| **HR** | 5-10% | JD、面试、绩效表 |
| **市场** | 10-15% | 调研、文案、PPT |
| **IT** | 5-10% | 自用 + 自动化维护 |
| **储备** | 20-25% | 应急 / 培训 / 试点 |

**关键设计**:
- **部门池每季度重分一次**——按上季度实际消耗 + 下季度业务计划
- **部门池不"切死"**——月底可借下月,下月补回
- **部门池"季度结算"**——超了要解释,省了不收回

### 8.3.3 第三层:个人池

**定义**:从部门池分配到每个人的"基础额度"。

**配置建议**(以中层管理岗为参考,具体以 WorkBuddy 官方为准):

| 角色 | 月度基础额度参考 | 理由 |
|---|---|---|
| **AI 协作负责人** | 高 | 培训、布道、答疑 |
| **中层管理者** | 中高 | 周报、邮件、纪要、PPT |
| **资深员工** | 中 | 周报、邮件、报告 |
| **新员工 / 实习生** | 低 | 培训期 + 简单任务 |

**关键设计**:
- **个人池每月初重置**(不累计,避免"用不完想囤")
- **超了可申请"临时加成"**——特殊项目 / 紧急任务
- **月底 80% 没用完**——不收回(避免"为了用而用")

### 8.3.4 第四层:项目池

**定义**:从储备池中抽出,给"跨部门项目"用的专项 Credits。

**适用场景**:
- 跨部门 Q1 重点项目
- 临时活动(双 11 / 618 / 公司年会)
- 试点新场景(测试"AI 写代码""AI 做设计"等)

**配置原则**:
- **项目池有"期限"**——3 个月 / 1 个季度,过期收回
- **项目池有"负责人"**——谁用谁负责,超了要解释
- **项目池有"目标"**——预期省多少小时 / 提多少效率

### 8.3.5 一张图看 4 层结构

| 层级 | 来源 | 数量级参考 | 重分周期 |
|---|---|---|---|
| **总池** | WorkBuddy 团队版套餐 | 以 WorkBuddy 官方为准 | 年度合同 |
| **部门池** | 从总池按比例分 | 几十人量级,具体看团队版档位 | 季度 |
| **个人池** | 从部门池按角色分 | 几到几十 / 人 / 月 | 月度 |
| **项目池** | 从储备池按需分 | 几到几十 / 项目 | 项目周期 |

**这张图的关键洞察**:
- **越往下,数量级越小,周期越短**
- **越往下,管理越细,争议越多**
- **越往下,越要给"人"自由度**

## 8.4 按维度分配原则:角色 / 部门 / 项目

讲完 4 层结构,讲"按什么分配"——3 个维度:**角色、部门、项目**。

### 8.4.1 按角色分配:4 类角色

我把团队角色分成 4 类,每类对应不同的"基础额度"逻辑:

| 角色 | 定义 | 分配逻辑 | 典型人物 |
|---|---|---|---|
| **重度用户** | 每周用 10+ 次,场景 5+ | 基础额度高,基本不限 | 销售 leader、运营经理、HRBP |
| **中度用户** | 每周用 5-10 次,场景 3-5 | 基础额度中,偶尔超 | 资深员工、中层 |
| **轻度用户** | 每周用 1-5 次,场景 1-3 | 基础额度低,鼓励尝试 | 新员工、实习生 |
| **观察用户** | 暂时不用,观望中 | 基础额度极低或为 0 | 暂未启用者 |

**关键设计**:
- **"基础额度"对应"预期用量"**——不要按"职位高低"分
- **新员工第 1 个月额度低**——以"学习"为主,不需要多
- **新员工第 2 个月起,按"实际表现"调整**——重度用户 → 调高,轻度用户 → 维持

### 8.4.2 按部门分配:5 个核心部门

| 部门 | 业务特征 | 分配原则 |
|---|---|---|
| **销售部** | 高频邮件、客户沟通、报价 | 按"客户数 + 邮件量"分配 |
| **运营部** | 周报、活动复盘、用户调研 | 按"周报数 + 活动数"分配 |
| **产品部** | PRD、用户故事、文档整理 | 按"产品数 + 文档数"分配 |
| **市场部** | 调研、文案、PPT | 按"项目数 + 文档数"分配 |
| **HR 部** | JD、面试、绩效表 | 按"招聘量 + 员工数"分配 |

**注意**:
- **部门分配不是"平均主义"**——30% 的"高用量"员工可能消耗 60%+ 的部门池
- **部门池要"动态调整"**——某部门突然开新项目,部门要申请"专项加成"
- **部门池"季度重算"**——用得多的部门,下季度多给;用得少的,少给

### 8.4.3 按项目分配:跨部门专项

**项目池**用于"跨部门 + 有明确目标"的项目,不是给"日常任务"用的。

**项目池申请流程**:
1. 项目负责人提交"项目计划"(预期目标 / 预期 Credits 消耗 / 预期产出)
2. 培训负责人 / IT 评估"是否值得用 AI 跑"
3. 部门 leader 评审"项目池够不够"
4. 批准后,从储备池划拨

**项目池的 3 个判断标准**:
1. **是否跨部门**——是 → 适合项目池
2. **是否有明确目标**——是 → 适合项目池
3. **是否有时限**——是 → 适合项目池

**3 个"不适合"项目池的情况**:
- ❌ 日常任务(周报 / 邮件)——用个人池
- ❌ 部门内部任务——用部门池
- ❌ 长期任务(无明确截止)——用部门池,不要用项目池

### 8.4.4 3 个维度的"组合用法"

3 个维度不是"互斥",是"组合":

```
总池(年度)
    │
    ├── 按部门分配(季度)
    │      │
    │      ├── 按角色分配(月度)
    │      │      │
    │      │      └── 个人池
    │      │
    │      └── 项目池(项目周期)
    │
    └── 储备池(灵活)
```

**3 个维度的优先级**:
- **先按"部门"分**——避免"全员抢池子"
- **再按"角色"调**——避免"部门内大锅饭"
- **最后按"项目"加**——避免"日常任务用专项"

## 8.5 审计与回收:让成本"可解释、可追溯、可调整"

讲完分配,讲"用后"——**审计与回收**。这是"成本治理"最容易出问题的环节。

### 8.5.1 审计日志的"能看"与"不能看"

**审计的目的不是"监视员工",是"看消耗、看异常"**。

我把"审计"分成"能看"和"不能看"两类:

| 维度 | 能看 | 不能看 |
|---|---|---|
| **消耗** | ✅ 谁用了多少 Credits | — |
| **任务类型** | ✅ 跑了什么类型的任务(周报/邮件/...) | ❌ 看了什么具体文件 |
| **时间** | ✅ 什么时候跑的 | — |
| **文件大小** | ✅ 文件多大(避免异常巨大) | ❌ 文件内容 |
| **对话内容** | ❌ | ❌ 员工和 AI 的对话内容 |

**核心边界**:**审计"账"(Credits 消耗 + 任务类型),不审"内容"(对话 + 文件)**。

这个边界很重要——一旦越界,员工会"抵触"使用 WorkBuddy(觉得"被监视"),反而抑制了使用。

**实施建议**:
- **审计权限只给"管理员 + 财务"**——2-3 人,不扩大
- **审计日志保留期限以 WorkBuddy 官方为准**(团队版可配置)
- **审计数据"季度对账"**——财务 + IT + 业务 leader 三方对

### 8.5.2 怎么用审计日志做月度复盘

**审计日志不是"看一次就过",是"每月复盘"**。

月度复盘的 4 件事:

1. **总消耗统计**——本月用了多少 Credits,占总额度多少
2. **TOP 10 消耗者**——谁用得最多,场景是什么
3. **TOP 5 异常消耗**——某天 / 某人 / 某任务突然消耗异常
4. **下月预测**——按趋势,下月大概用多少

**复盘产出**:1 份"月度 Credits 复盘报告"(1-2 页),发到团队群。

### 8.5.3 隐私边界:数据归属与员工知情

**Credits 治理的"红线"是"员工知情 + 数据归属"**。

3 条不可越界:

1. **数据归属**——WorkBuddy 中的对话、文件、产出,**属于员工个人 + 团队**(具体以 WorkBuddy 官方协议为准)。公司不能随便"看内容"。
2. **员工知情**——上线审计前,必须明确告知员工"会看什么、不会看什么"。**未告知就审计 = 违规**。
3. **离职处理**——员工离职,WorkBuddy 数据按公司规定处理(以 WorkBuddy 官方流程为准)。

**实施建议**:
- 团队启动时,**签一份"WorkBuddy 使用须知"**——明确"看什么、不看什么、数据归属"
- **季度 1 次"知情确认"**——员工签字确认"我同意被审计账目"
- **离职清单**加"WorkBuddy 数据交接 / 清理"项

### 8.5.4 团队使用统计的"仪表盘视角"

我推荐每个团队 leader 都看 1 个"仪表盘"——核心 4 个数:

| 指标 | 定义 | 健康线 |
|---|---|---|
| **月度总消耗** | 团队当月总 Credits 消耗 | 占总额度 60-85% |
| **活跃度** | 当月用过的员工数 / 总员工数 | ≥ 80% |
| **人均消耗** | 总消耗 / 活跃员工数 | 稳定,无大幅波动 |
| **高消耗者占比** | TOP 10 消耗者 / 总消耗 | ≤ 50% |

**4 个数的解读**:
- **总消耗 < 60%** → 大家"没用起来",要培训 / 推场景
- **总消耗 > 85%** → 快超了,要复盘 / 调预算
- **活跃度 < 70%** → 有"账号闲置",要排查
- **TOP 10 占比 > 60%** → 个别人"用爆",要分析

### 8.5.5 回收机制

**"回收"是"成本治理"的高阶能力**——不只会"花",还要会"收"。

**3 种回收场景**:
1. **月度回收**——个人池当月没用完,**不收回**(避免"为了用而用"),但季度累计没用完,转入部门池
2. **项目回收**——项目池到期,没用完的收回储备池
3. **离岗回收**——员工离职,未用完额度收回部门池

**回收原则**:
- **回收不"一刀切"**——避免"为了用而用"
- **回收要"透明"**——团队群公开"回收 X Credits,转入部门池"
- **回收要"奖励"**——某部门"用得省 + 产出多",奖励下次"多给 10%"

## 8.6 成本预测与 ROI:算清账,向老板讲清楚

讲完分配和审计,最后讲"算账"——**怎么向老板 / CFO 讲清楚"花这钱值不值"**。

### 8.6.1 月度成本预测:最小可行公式

**月度 Credits 消耗 ≈ 团队人数 × 人均月消耗 × 场景数系数**

举例(以 30 人团队为例,具体数字以 WorkBuddy 官方为准):
- 团队人数:30 人
- 人均月消耗:1-3 个标准任务
- 标准任务消耗:每次消耗一定 Credits(以 WorkBuddy 官方为准)
- 场景数系数:1 个场景 = 1.0,5 个场景 = 1.3(更多场景 = 更多消耗)

**月度预测 ≈ 30 人 × X 任务 × Y Credits × 1.0-1.3**

**注意**:
- **这只是"粗估"**——实际消耗可能 ±30%
- **建议"先跑 1 个月"**——按实际数据再调公式
- **不要"按公式精确预测"**——团队使用习惯会变

### 8.6.2 ROI 怎么算:成本是分子,收益是分母

**ROI(投资回报率)= 收益 / 成本 × 100%**

**成本 = Credits 成本 + 培训时间成本 + IT 维护成本**(以 WorkBuddy 官方公告为准)

**收益 = 省下的工时 × 时薪 + 决策质量提升 + 错误率下降**

**举例**(以 30 人团队、月度为例):
- 成本:30 人 × 月度消耗 × Credits 单价 + 培训 60 小时 + IT 维护 20 小时(具体以官方为准)
- 收益:每人每周省 2-3 小时 × 30 人 × 4 周 = 240-360 小时 × 时薪

**关键**:
- **不要"省小时"算 ROI**——"省 1 小时"≠"价值 1 小时",要算"省的是不是有产出的时间"
- **不要"按月算"**——按季度算,数据更稳
- **不要"只算工时"**——还要算"质量提升"(决策更准 / 错误更少)

### 8.6.3 向 CFO / CEO 汇报:三句话讲清楚

**我推荐 3 句话结构**——给老板汇报时,3 句话讲清楚:

> **第一句:花了多少。** 本季度 WorkBuddy 团队版 + Credits 消耗合计 X 元(以 WorkBuddy 官方为准)。
>
> **第二句:省了多少。** 30 人团队,每周共省 100-150 小时,折合每月省 400-600 小时。
>
> **第三句:净收益。** 折算成人力成本,本季度净收益 X 元(具体看时薪)。

**3 句话之外,补 1 份"案例"**:
- 举 1 个"具体场景"——"销售小王用 WorkBuddy 写客户邮件,周邮件时间从 5 小时降到 1.5 小时,成交率提升 8%"
- 举 1 个"团队级"案例——"运营部周报提交及时率从 70% 提升到 95%,相当于每月省 X 小时返工"

**汇报的"避坑"**:
- ❌ 不要讲"AI 有多牛"——老板不听技术
- ❌ 不要讲"用了多少次"——老板只看 ROI
- ❌ 不要讲"模型是什么"——老板不关心细节
- ✅ 讲"花了多少,省了多少,净收益多少"——3 句话

### 8.6.4 团队规模的临界点:10 人、30 人、100 人

**不同规模,成本治理的复杂度不同**:

| 规模 | 治理复杂度 | 推荐模型 | 关键动作 |
|---|---|---|---|
| **5-10 人** | 低 | 总池制 | 1 个表格追踪 |
| **10-30 人** | 中 | 混合制 | 4 层池 + 月度复盘 |
| **30-100 人** | 高 | 混合制 + 储备池 | 4 层池 + 周度复盘 + IT 自动化 |
| **100+ 人** | 极高 | 混合制 + 子公司池 | 多层级 + 财务系统对接 |

**临界点的"经验值"**:
- **10 人** ——可以靠"非正式追踪"(群消息 + 共享表格)
- **30 人** ——必须"正式追踪"(WorkBuddy 团队版后台 + 月度报告)
- **100 人** ——必须"系统化"(对账系统 + 自动化审计 + 季度复盘)

### 8.7.5 另一个真实案例:某 30 人团队的 6 个月成本治理复盘

锐智云那个 120 人案例是"大团队按部就班"的成功样本。再给你一个"小团队摸着石头过河"的样本,数据来自第二卷 6.5.3 提到的上海某营销公司(化名"新潮文化")。

**团队**:上海某品牌营销公司(化名"新潮文化"),30 人,2 个业务部门 + 1 个客户部 + 1 个后台职能
**WorkBuddy 团队版规模**:30 人(以 WorkBuddy 官方公告为准)
**治理框架上线 6 个月后的数据**:

| 月份 | 活跃度 | 月度消耗占总额度 | 当月异常事件 | 治理动作 |
|---|---|---|---|---|
| 第 1 月 | 35% | 22% | 3 起(2 个账号忘了登出,1 个任务类型没设上限) | 全员培训 + 登出策略 + 任务类型上限 |
| 第 2 月 | 62% | 48% | 1 起(临时用 AI 生成客户提案,消耗 4 倍常规) | 立项审批流程 |
| 第 3 月 | 75% | 55% | 0 起 | 月度复盘开始,设 4 层 Credits 池 |
| 第 4 月 | 78% | 58% | 2 起(同部门 2 人对同一组素材重复跑) | 同部门工作目录去重 |
| 第 5 月 | 82% | 61% | 1 起(离职交接,账号未及时停用) | 离职流程加 WorkBuddy 账号回收步骤 |
| 第 6 月 | 85% | 63% | 0 起 | 季度 ROI 报告产出,确认治理框架稳定 |

**第 6 个月的"账"**:

- **成本**(以 WorkBuddy 官方公告为准):团队版订阅 + 培训 6 个月一次性投入 + IT 维护工时。30 人平均每人月成本(以官方为准),公司总投入比完全手动 + 零 AI 工具状态省下约 35-50 小时 × 30 人 = 1050-1500 小时/月。
- **收益**:营销方案初稿时间从 8 小时降到 2.5 小时;客户提案准备从 1 天降到 3 小时;月度数据汇总从 6 小时降到 1 小时。**单是这 3 个高频场景,30 人团队每月省下约 850 小时**(以上数字以你实际部署数据为准,本节数据为案例脱敏复述)。
- **ROI**:6 个月累计净收益远高于累计成本(以你实际财务核算为准)。

**这个 30 人案例的 3 个"反常识"经验**:

**第一,前 2 个月的"异常事件"是好事,不是坏事**。30 人团队前 2 个月出现 4 起异常,很多人会以为"治理失败"。但反过来想:这些异常是"低成本试错"——你用 1-2 个月就摸清了团队会在哪儿翻车,省去了后面一年反复翻车的时间。如果前 2 个月零异常,反而要警惕"是不是大家没用"。

**第二,治理动作要"立刻落地",不要等"季度规划"**。30 人团队每次出异常都在当周处理,不是等月度复盘。这跟大团队不一样——大团队有 IT、HR、财务多部门协作,月度复盘更现实;小团队应该"今天出问题,今天修"。

**第三,"活跃度"和"消耗占总额度"不是线性关系**。第 1 月 35% 活跃度但只占 22% 额度(大家用得少);第 6 月 85% 活跃度占 63% 额度(大家用得多且精)。**活跃度提上去后,消耗占比会"自然上升"**——这是好事,不是坏事。如果你用"消耗占比"作为治理 KPI,会逼团队"为了不超而不用",反而把好事做坏。

**30 人团队"治理动作"清单(可照抄)**:

| 阶段 | 关键动作 | 关键责任人 |
|---|---|---|
| 第 1 周 | 选定 WorkBuddy 团队版档位(以官方公告为准),全员账号开通 | leader + IT |
| 第 2 周 | 培训(2 小时上手 + 1 小时提示词),全员签"使用须知" | leader + HR |
| 第 3-4 周 | 观察期——记录"谁在用、用的什么任务、用得怎么样" | leader |
| 第 5-6 周 | 第 1 次异常盘点 + 当周修(登出策略 / 任务上限) | leader + IT |
| 第 2 月底 | 第一次月度复盘——输出"8.7.2 模板"的内容 | leader |
| 第 3 月 | 引入 4 层 Credits 池(总池 + 部门池 + 个人池 + 项目池) | leader + 部门负责人 |
| 第 4-5 月 | 周度抽检 + 月度复盘;每次异常当周修 | leader |
| 第 6 月 | 第一次季度 ROI 报告(用 8.7.3 模板);治理框架稳定 | leader + 财务 |

**最后一句**:30 人团队的治理框架,跟 120 人团队的**复杂度差 10 倍**。**不要照搬大公司的"严格 IT 流程"**——小团队的核心是"反应快",不是"流程全"。

## 8.8 小结

本章我们讲了"成本与权限"的 5 件事:

1. **预算模型**——总池制 / 个人额度制 / 混合制,90% 的 20+ 人团队用混合制。**先宽松 → 看数据 → 再收紧**,顺序不能反。
2. **Credits 池设计**——总池(年度)→ 部门池(季度)→ 个人池(月度)→ 项目池(项目周期),4 层结构,越往下周期越短、管理越细。
3. **按维度分配**——按角色(4 类)分基础额度、按部门(5 类核心)分部门池、按项目(跨部门专项)分项目池,3 个维度组合用,优先级:部门 > 角色 > 项目。
4. **审计与回收**——审计"账"(Credits 消耗 + 任务类型),不审"内容"(对话 + 文件);3 种回收(月度 / 项目 / 离岗),回收要透明、要奖励。
5. **成本预测与 ROI**——月度粗估公式 + 季度 ROI 报告;向老板汇报用 3 句话(花了多少 / 省了多少 / 净收益)。

**关键判断**:
- **成本治理的目标不是"省 Credits",是"花得值"**
- **管得严,未必省得多**——严格额度制让团队"不敢试",反而错过高价值场景
- **审计的边界**是"看账不看内容"——越界就违规
- **10 人 / 30 人 / 100 人**是治理复杂度的临界点
- **数据归属 + 员工知情**是治理的"红线"

**如果只读一段**:**"成本治理的本质是让'花钱'变成'算账'"**。先建 4 层 Credits 池(总/部门/个人/项目),再按角色 / 部门 / 项目分配,再月度复盘 + 季度 ROI,最后用 3 句话给老板讲清楚。
