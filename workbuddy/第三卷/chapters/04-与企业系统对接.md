# 第 4 章 与企业系统对接

> **本章学习目标**
> 1. 理解 WorkBuddy 在企业 IT 架构中的位置——它是"本机客户端 + 系统集成层",不是"替代企业系统"。
> 2. 掌握 4 种通用集成模式(Webhook / REST API / 数据库直连 / 浏览器自动化)的适用场景与边界。
> 3. 拿到 5 个常见对接场景的架构描述(OA / CRM / 知识库 / BI / 工单),能直接照着画自己组织的对接图。
> 4. 理解权限边界与审计机制,知道 WorkBuddy 在企业系统里"能做什么、不能做什么"。
> 5. 掌握失败兜底设计——网络超时、API 限流、数据错误时的处理方法。

> **界面示意图,具体界面以你安装的 WorkBuddy 版本为准。**

## 4.1 为什么 WorkBuddy 要对接企业系统

先说一个核心判断:**WorkBuddy 不是企业系统的替代品,而是企业系统的"智能接入层"**。

它的位置是这样的:

```
┌────────────────────────────────────────────────┐
│                  用户电脑                       │
│  ┌──────────────────────────────────────────┐  │
│  │            WorkBuddy 客户端                │  │
│  │  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐  │  │
│  │  │ 对话 │  │ 工具 │  │ 文件 │  │ 日志 │  │  │
│  │  │ 引擎 │  │ 调用 │  │ 读取 │  │ 审计 │  │  │
│  │  └──────┘  └──────┘  └──────┘  └──────┘  │  │
│  └────────────┬─────────────────────────────┘  │
│               │                                │
│  ┌────────────▼─────────────┐                  │
│  │  本机文件 + 本机工具     │                  │
│  └──────────────────────────┘                  │
└─────────────────────┬──────────────────────────┘
                      │ Webhook / REST / SQL / IM 协议
                      │ (本机到企业内网)
                      ▼
┌────────────────────────────────────────────────┐
│              企业 IT 系统                       │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐│
│  │  OA  │ │ CRM  │ │ 知识 │ │  BI  │ │ 工单 ││
│  │      │ │      │ │  库  │ │      │ │      ││
│  └──────┘ └──────┘ └──────┘ └──────┘ └──────┘│
└────────────────────────────────────────────────┘
```

关键点:
1. **WorkBuddy 装在用户电脑上**(本机)
2. 它通过标准协议(Webhook / REST API / GraphQL / SQL / IM 协议)跟企业系统对话
3. 企业系统的"主人"还是 IT 部门,WorkBuddy 是"客人"
4. **数据流向可控**——WorkBuddy 读什么、写什么,都有审计

这一章要回答的问题是:**WorkBuddy 怎么跟企业现有的 5 类系统(O A / CRM / 知识库 / BI / 工单)对接,以及对接中怎么不出问题**。

## 4.2 4 种通用集成模式

WorkBuddy 跟企业系统对接,有 4 种基本方式。每种有明确的适用场景和边界。

### 4.2.1 模式 1:Webhook(反向推送)

**原理**:企业系统在某个事件(如"客户提交工单")发生时,主动推送一个 HTTP 请求到 WorkBuddy,WorkBuddy 收到后处理。

**适用**:
- 事件驱动型任务(工单、审批、新客户提交)
- 实时性要求高
- 不需要 WorkBuddy 主动拉数据

**优点**:
- 实时性强(秒级响应)
- WorkBuddy 端不用轮询,省资源

**缺点**:
- WorkBuddy 需要一个公网可达的 Webhook URL(企业版 WorkBuddy 部署在内网服务器时)
- 失败重试机制需要双方约定

**典型场景**:
- 客户提交工单 → 推送 Webhook 到 WorkBuddy → WorkBuddy 自动分析工单内容,提示处理建议
- 审批流程到达 → 推送 Webhook → WorkBuddy 整理历史数据,给审批人决策参考

### 4.2.2 模式 2:REST API(主动拉取)

**原理**:WorkBuddy 通过 HTTP 调用企业系统的 REST API,主动读数据或写数据。

**适用**:
- 需要主动查询的场景
- 周期性任务(每天同步一次客户档案)
- 数据量较大、需要分页/过滤

**优点**:
- 标准协议,文档丰富
- 大多数企业系统都提供 REST API
- 支持分页、过滤、排序

**缺点**:
- 调用频率受 API 限流限制
- 复杂查询需要多次调用
- 实时性不如 Webhook

**典型场景**:
- WorkBuddy 每天拉取"昨天新增客户"列表,生成客户档案
- WorkBuddy 查询工单系统"我名下未关闭的工单",输出待办

### 4.2.3 模式 3:数据库直连(只读,慎用)

**原理**:WorkBuddy 通过 ODBC / JDBC 等标准数据库连接,直接读企业数据库(只读,不允许写)。

**适用**:
- 数据量极大、API 不够用
- 需要复杂 SQL(JOIN 多表)
- API 不开放,数据库可读

**优点**:
- 性能高
- 支持复杂查询

**缺点**:
- **安全风险高**——直连数据库意味 WorkBuddy 能读到所有表,容易越权
- 数据库 schema 变更会破坏 WorkBuddy 逻辑
- 不适合"写"操作

**最佳实践**:**永远只读、给最低权限账号、所有查询走"读副本"**(从库)**

**典型场景**:
- BI 数据分析(从数据仓库读)
- 客户档案全量同步(从 CRM 数据库读)

### 4.2.4 模式 4:浏览器自动化(UI 自动化)

**原理**:WorkBuddy 模拟人在浏览器里的操作(点击、填表、提交),跟企业系统交互。

**适用**:
- 企业系统没有 API,只有网页界面
- 老旧系统、内部工具

**优点**:
- 任何有网页的系统都能对接
- 不需要 IT 配合

**缺点**:
- **脆弱**——网页改版就坏
- 速度慢
- 不适合大规模操作

**典型场景**:
- 老旧 OA 系统的请假申请(没 API,只能网页操作)
- 内部行政系统(财务报销、出差申请)

### 4.2.5 模式选择决策表

| 场景特征 | 推荐模式 | 备选 |
|---|---|---|
| 事件驱动 + 实时 | Webhook | REST API 轮询 |
| 主动查询 + 周期 | REST API | 数据库直连 |
| 大数据量 + 复杂 SQL | 数据库直连 | REST API(分页) |
| 没有 API 只有网页 | 浏览器自动化 | 推动 IT 开放 API |
| 写入操作(改数据) | REST API(POST/PUT) | Webhook(被动响应) |
| 删除/批量操作 | REST API | 严禁数据库直连 |
| 敏感数据(财务、人事) | 严格走 REST API + 鉴权 | 严禁浏览器自动化 |

**核心原则**:**能用 API 就不用数据库直连,能用 Webhook 就不用浏览器自动化**。模式越靠前越安全可控。

## 4.3 场景一:与 OA 系统对接

OA(办公自动化)是企业中最高频、最标准的系统。请假、报销、审批、用印、会议室预订,几乎所有员工每天都要用。

### 4.3.1 对接需求

管理者用 WorkBuddy 跟 OA 对接,典型需求:

1. **快速提交**:用自然语言"我下周二上午要请半天假" → WorkBuddy 自动调用 OA 的请假 API,提交申请
2. **审批辅助**:审批流到达时,WorkBuddy 自动拉取申请人历史请假数据、当前工作量,辅助决策
3. **状态跟踪**:每天早上 WorkBuddy 主动告诉我"你今天有 3 笔待审批"
4. **批量处理**:月底统一处理一批报销单,WorkBuddy 自动读附件、填表、提交

### 4.3.2 架构描述

```
用户:"我下周二上午要请半天假,家里有事"
   │
   ▼
WorkBuddy 接收自然语言
   │
   ▼
Step 1:解析意图
   - 动作:请假
   - 时间:下周二上午
   - 时长:半天
   - 事由:家里有事
   │
   ▼
Step 2:补充上下文
   - 自动从工作目录读:本月已请假期数、剩余假期天数
   - 自动从工作目录读:下周二上午是否有会议
   │
   ▼
Step 3:生成请假单
   - 调用 OA 系统的 REST API:POST /leave/apply
   - 参数:开始时间、结束时间、事由
   │
   ▼
Step 4:提交 + 通知
   - 调用 OA API 提交
   - WorkBuddy 弹窗通知"请假已提交,审批人张三,预计 2 小时内回复"
   - 写审计日志
```

### 4.3.3 权限设计

WorkBuddy 调用 OA API,需要专用账号。**这个账号要遵循"最小权限"原则**:

- ✅ 可以:提交请假、查询自己名下的审批、读自己历史请假数据
- ❌ 不可以:审批他人请假、修改他人记录、删除任何记录
- ❌ 严格禁止:对财务模块、人事档案的写权限

账号由 IT 部门统一签发,WorkBuddy 不存储账号密码,只存 API Token(可随时吊销)。

### 4.3.4 失败兜底

| 失败场景 | 兜底方案 |
|---|---|
| OA 系统宕机 | WorkBuddy 把请假信息存在本地,OA 恢复后自动重试 |
| API 调用超时 | WorkBuddy 提示用户"系统繁忙,可手动提交",并把任务标记为"待人工处理" |
| 权限不足 | WorkBuddy 提示"请联系 IT 开通权限",并把申请记录到工单 |
| 数据校验失败(如日期冲突) | WorkBuddy 把错误信息反馈给用户,建议调整后重试 |

## 4.4 场景二:与 CRM 系统对接

CRM(客户关系管理)是销售型企业的核心。客户档案、商机、合同、跟进记录,都在 CRM 里。

### 4.4.1 对接需求

销售/销售管理者用 WorkBuddy 跟 CRM 对接,典型需求:

1. **客户档案生成**:开会时手写记录 → 回到工位 WorkBuddy 自动整理成标准客户档案 → 推送到 CRM
2. **商机跟进提醒**:WorkBuddy 每天早上告诉我"今天有 5 个商机需要跟进"
3. **销售预测**:WorkBuddy 拉取所有商机数据,按"赢率 × 金额"做加权预测
4. **客户洞察**:WorkBuddy 读客户所有历史沟通,生成"客户健康度报告"

### 4.4.2 架构描述

```
销售总监问:"下个季度我们的销售预测是多少?"
   │
   ▼
WorkBuddy 接收问题
   │
   ▼
Step 1:识别意图
   - 类型:数据查询
   - 范围:全公司销售商机
   - 输出:预测数字
   │
   ▼
Step 2:调用 CRM API
   - GET /opportunities?stage=open
   - 拉取所有"未关闭"商机
   │
   ▼
Step 3:数据处理
   - 调 DeepSeek 模型
   - 输入:商机列表(含金额、阶段、赢率)
   - 输出:按"阶段 × 赢率"加权求和
   │
   ▼
Step 4:生成报告
   - 数字预测:¥1.2 亿
   - 风险标注:3 个大单赢率被高估,实际可能 ¥1.05 亿
   - 建议:集中精力推这 3 个大单
   │
   ▼
Step 5:输出 + 写日志
   - 弹窗给销售总监
   - 写审计日志:谁在什么时候查了什么数据
```

### 4.4.3 关键技术点

**写操作要走审批**:

CRM 数据的写操作(创建商机、改客户档案)风险高,建议:

- WorkBuddy **生成草稿,人工确认后提交**
- 不要让 WorkBuddy 静默写入

**读操作要按"客户范围"授权**:

销售总监可以看全公司客户档案,销售只能看自己名下的客户档案。WorkBuddy 的 API 账号要按角色区分。

**敏感数据脱敏**:

读出的客户数据,在传给 AI 模型前要脱敏(隐藏手机号、身份证号、银行账号)。WorkBuddy 支持"数据脱敏中间件"。

### 4.4.4 失败兜底

CRM 是销售命脉,任何中断都不能影响业务。兜底设计:

- **本地缓存**:WorkBuddy 把最近 30 天的客户档案缓存在本机,CRM 故障时仍可查
- **重试机制**:API 调用失败时,自动重试 3 次(间隔 1s/3s/9s),仍失败则提示用户
- **手动覆盖**:紧急情况下,WorkBuddy 提示"CRM 不可用,已记录你的操作,等恢复后自动同步"

## 4.5 场景三:与知识库对接

知识库是企业内部"经验的集散地"。SOP、最佳实践、案例库、FAQ、规章制度,都在知识库里。

### 4.5.1 对接需求

员工/管理者用 WorkBuddy 跟知识库对接,典型需求:

1. **智能问答**:问"客户退款的标准流程是什么" → WorkBuddy 从知识库找文档,生成答案
2. **文档生成**:写一份新 SOP,WorkBuddy 参考知识库里类似 SOP,生成草稿
3. **案例检索**:写方案时找"过去类似项目怎么做" → WorkBuddy 检索知识库,返回 3-5 个最相关的
4. **培训辅助**:新员工入职,WorkBuddy 陪他读知识库,回答他的提问

### 4.5.2 架构描述

```
员工问:"客户申请退款,我们的标准流程是什么?"
   │
   ▼
WorkBuddy 接收问题
   │
   ▼
Step 1:把问题转成搜索查询
   - 关键词:客户退款、标准流程、SOP
   - 向量化:用 Embedding 模型转成向量
   │
   ▼
Step 2:在知识库检索
   - 调用知识库 API:POST /search
   - 返回 Top 10 相关文档片段
   │
   ▼
Step 3:重排序
   - 用 Rerank 模型对 Top 10 重排序
   - 选出 Top 3
   │
   ▼
Step 4:生成答案
   - 把 Top 3 + 问题发给 LLM
   - Prompt:"基于以下 3 个文档,回答用户问题。如果文档没说,明确说'知识库无相关信息'"
   │
   ▼
Step 5:输出
   - 给员工答案
   - 列出"参考了哪 3 个文档"(可点击查看)
```

这是典型的 **RAG(检索增强生成)** 架构。

### 4.5.3 关键技术点

**Embedding 与 Rerank 的选型**:

- Embedding:用哪款模型把文本转向量(常见选型:豆包 Embedding、智谱 Embedding、BGE 等开源)
- Rerank:对初检结果重排序(常见选型:BGE Reranker、Cohere Rerank 等)

**文档切分策略**:

文档怎么切分,决定检索质量。常见策略:

- 按段落切(简单,但可能切碎语义)
- 按章节切(适合长文档)
- 按语义切(用模型判断,质量高但慢)
- 滑动窗口(重叠切分,避免边界信息丢失)

**答案的"幻觉"问题**:

LLM 容易"自信地胡说"。应对:

- Prompt 强约束:"如果文档没说,说'不知道',不要编造"
- 答案必须带"参考文档"链接,人工可验证
- 关键场景(法律、医疗)严禁纯 LLM 回答,必须人工审核

### 4.5.4 失败兜底

知识库对接的常见失败:

- **检索为空**:WorkBuddy 返回"知识库无相关信息,你可以:1) 换个问法 2) 联系知识库管理员"
- **检索质量差**:WorkBuddy 提示"我找到的答案可能不准确,建议你直接看文档 X"
- **知识库宕机**:WorkBuddy 用本地缓存的"知识库快照"回答,但明确标注"快照数据"

## 4.6 场景四:与 BI 系统对接

BI(商业智能)是企业数据决策的核心。报表、Dashboard、数据查询,都靠 BI。

### 4.6.1 对接需求

管理者用 WorkBuddy 跟 BI 对接,典型需求:

1. **自然语言查询**:问"上个月华东区销售情况" → WorkBuddy 生成 SQL → 调 BI → 返回结果
2. **报表自动生成**:每周一早上 WorkBuddy 自动生成"上周运营报表",推到企业微信
3. **数据异常告警**:WorkBuddy 每天扫数据,发现异常(如某指标暴跌)主动告警
4. **跨数据源分析**:把 CRM + 财务 + 供应链 三个数据源拉通分析

### 4.6.2 架构描述:Text-to-SQL

```
管理者问:"上个月华东区销售额超过 50 万的客户有几个?"
   │
   ▼
WorkBuddy 接收问题
   │
   ▼
Step 1:识别意图
   - 类型:数据查询
   - 指标:客户数
   - 过滤:华东区、上月、>50 万
   │
   ▼
Step 2:生成 SQL
   - Prompt 给 LLM:
     "基于以下 schema,生成 SQL:...
     schema: orders, customers, regions..."
   - LLM 输出:SELECT COUNT(*) FROM customers c JOIN orders o ON ... WHERE region='华东' AND order_date BETWEEN ... AND ... AND amount > 500000
   │
   ▼
Step 3:校验 SQL
   - 自动语法校验
   - 重要查询走"dry run"(先 EXPLAIN,不实际跑)
   │
   ▼
Step 4:执行查询
   - 调 BI 系统的 SQL 执行 API
   - 或直连数据仓库(只读)
   │
   ▼
Step 5:生成答案
   - 把数字结果 + 上下文,生成自然语言答案
   - "上月华东区销售额超过 50 万的客户有 23 个,较上月增加 4 个"
   │
   ▼
Step 6:输出 + 写日志
```

### 4.6.3 关键技术点

**Text-to-SQL 的成功率**:

实测当前国产模型(DeepSeek、通义、智谱)在 BI 场景的 Text-to-SQL 准确率,大约 70-85%(以简单查询为基准,具体以你团队实际数据为准)。

成功率提升技巧:

- 提供**业务口径词典**(如第 2 章 2.8 节所讲)
- 提供**典型查询示例**(给 LLM 几个 SQL 样例,让它学)
- **人工 review 关键查询**(涉及金额、删改的查询必须 review)

**写操作风险**:

BI 系统的"修改数据"操作极少,但**生成临时表、修改 ETL 任务**是写操作,必须严格控制权限。

### 4.6.4 失败兜底

- **SQL 生成失败**:WorkBuddy 提示"我无法理解你的问题,你可以:1) 换种说法 2) 看 schema 文档"
- **SQL 执行超时**:WorkBuddy 提示"查询太慢,建议:1) 加过滤条件 2) 找 BI 工程师优化"
- **数据权限不足**:WorkBuddy 提示"你没有访问该数据集的权限,请联系数据 owner"

## 4.7 场景五:与工单系统对接

工单系统(客服工单、内部 IT 工单、运维工单)是企业日常运营的高频系统。

### 4.7.1 对接需求

客服主管/IT 主管用 WorkBuddy 跟工单系统对接,典型需求:

1. **工单自动分类**:客户提交工单 → WorkBuddy 自动判断类型、优先级
2. **自动派单**:WorkBuddy 根据工单内容 + 工程师技能 + 当前负载,自动派给最合适的人
3. **状态跟踪**:WorkBuddy 每天早上列出"超期未处理的工单"
4. **客户回复草稿**:WorkBuddy 读工单历史 + 客户档案,生成回复草稿
5. **批量关闭**:月底批量处理一批"已解决但未关闭"的工单

### 4.7.2 架构描述

```
客户提交工单(通过企业微信):
"我们的接口调用一直返回 500 错误,已经 2 小时了,很急!"
   │
   ▼
WorkBuddy 接收工单(通过 Webhook 或 IM 协议)
   │
   ▼
Step 1:工单分析
   - 提取关键信息:
     - 类型:技术故障 / API 500
     - 优先级:P0(很急,影响业务)
     - 影响:接口调用失败 2 小时
   │
   ▼
Step 2:自动派单
   - 查工程师技能库
   - 查当前负载
   - 匹配最合适工程师(如:张三,API 专家,当前负载低)
   │
   ▼
Step 3:通知工程师
   - 通过企业微信推送工单详情
   - 附上"建议排查方向"(基于历史类似工单)
   │
   ▼
Step 4:同时通知客户
   - 自动回复:"工单已收到,工程师张三将在 30 分钟内联系您"
   │
   ▼
Step 5:跟进
   - 30 分钟后 WorkBuddy 检查工单状态
   - 如未处理,自动升级
```

### 4.7.3 关键技术点

**工单分类的准确率**:

- 用 LLM 做分类,准确率约 90-95%(具体以你团队实际数据为准)
- 错误分类的代价:工程师被打扰,客户体验差
- 应对:**高优先级工单必须有"分类二次确认"**(WorkBuddy 分类后,人工 30 秒确认)

**派单算法的公平性**:

派单不只是"选最合适的人",还要考虑:

- 负载均衡(不能让某工程师天天接单)
- 技能匹配(不是所有人都能处理所有问题)
- 客户偏好(某些客户希望某个工程师对接)
- 轮值规则(7x24 服务的轮班)

WorkBuddy 派单算法支持这些规则,具体配置以官方文档为准。

### 4.7.4 失败兜底

- **工单系统宕机**:WorkBuddy 把工单存本地,系统恢复后同步
- **派单失败**:WorkBuddy 把工单转到"待人工派单"队列
- **客户回复超时**:WorkBuddy 自动升级到主管

## 4.8 权限边界:WorkBuddy 在系统中的位置

这是企业级对接最容易出问题的地方。我单独强调。

### 4.8.1 三个原则

**原则 1:WorkBuddy 是"客人",不是"主人"**

企业系统的主人是 IT 部门和业务部门,WorkBuddy 只是"高级访客"。**一切权限由 IT 授予,WorkBuddy 不得自行获取**。

**原则 2:最小权限**

WorkBuddy 调用某个系统 API,只给它需要的权限。**不要给"管理员 token"**。

**原则 3:可吊销**

任何时候,IT 部门可以吊销 WorkBuddy 的 API 凭证(改个密码、改个 token),WorkBuddy 立即失去访问能力。

### 4.8.2 权限分级建议

| 操作 | 建议权限级别 |
|---|---|
| 读自己的数据 | 员工级(可自助开通) |
| 读部门数据 | 部门负责人审批 |
| 读全公司数据 | IT + 业务 owner 联合审批 |
| 写自己的数据 | 员工级(可自助开通) |
| 写他人数据 | 严格控制,需业务 owner 审批 |
| 删任何数据 | **严禁 WorkBuddy 自动删除**(可标"待删",人工确认) |
| 改核心配置 | **严禁 WorkBuddy 操作** |

### 4.8.3 跨系统操作的风险

更复杂的场景是 WorkBuddy 跨多个系统操作。比如:

"读 CRM 的客户档案 → 查 OA 的合同状态 → 改 BI 的客户分级"

这种**跨系统操作**风险极高,因为任何一个环节出错,都会影响多个系统。

**应对**:
- **跨系统操作必须人工确认**(WorkBuddy 准备,人审核,系统执行)
- 或者把跨系统操作**拆成多个单系统操作**,每步人工确认
- 写操作必须有"撤销"能力(软删除而非硬删除)

## 4.9 审计:留痕、追溯、合规

对接企业系统,审计是底线。

### 4.9.1 审计日志的内容

每条 WorkBuddy 对企业系统的操作,都要记录:

```json
{
  "timestamp": "2026-08-15T10:30:00+08:00",
  "user_id": "zhangsan@company.com",
  "action": "read",
  "system": "crm",
  "endpoint": "/customers/12345",
  "params": {"include": "all"},
  "result": "success",
  "data_size_kb": 12,
  "ai_model_used": "deepseek-v3",
  "purpose": "周报生成-客户档案"
}
```

### 4.9.2 审计日志的保留与访问

- **保留期**:默认 180 天(具体以 WorkBuddy 官方为准),企业版可延长
- **访问权限**:员工可看自己的日志,部门负责人可看本部门日志,审计员可看全公司
- **导出格式**:支持 JSON、CSV,可对接 SIEM 系统

### 4.9.3 异常使用告警

审计日志要配合告警:

- 异常时段(凌晨 3 点大量调用)
- 异常频率(1 小时内调用 1000 次)
- 异常内容(出现敏感关键词)
- 异常结果(大量失败调用,可能账号被盗)

告警通过企业微信 / 飞书 / 邮件 推送给安全管理员。

## 4.10 失败兜底设计

最后讲一个跨所有场景的通用设计:**失败兜底**。

### 4.10.1 失败的三层

| 层级 | 失败类型 | 兜底策略 |
|---|---|---|
| **网络层** | 断网、超时、限流 | 重试 + 降级 + 提示 |
| **协议层** | API 4xx/5xx 错误 | 错误码识别 + 用户友好提示 |
| **业务层** | 数据错误、权限不足、逻辑冲突 | 业务规则校验 + 人工兜底 |

### 4.10.2 重试策略

| 错误类型 | 重试策略 |
|---|---|
| 超时(408/504) | 立即重试 1 次,失败后间隔 3s/9s 重试 2 次,再失败则放弃 |
| 限流(429) | 按"Retry-After"头等待后重试 |
| 服务器错误(5xx) | 间隔 1s/3s/9s 重试 3 次 |
| 客户端错误(4xx) | **不重试**,直接报错 |
| 鉴权失败(401/403) | **不重试**,提示用户检查权限 |

### 4.10.3 降级策略

失败时,WorkBuddy 不直接报错,而是"降级"——

- 能跑的部分继续跑
- 不能跑的部分提示用户
- 把失败的请求写到"重试队列",网络恢复后自动重试

### 4.10.4 用户的"知情权"

所有失败都要明确告诉用户:

- 什么失败了
- 为什么失败
- WorkBuddy 做了什么兜底
- 用户需要做什么

不要让 WorkBuddy 静默失败——这会让用户失去信任。

## 4.11 集成项目管理

企业级对接不是"装个 API 跑通"那么简单,是工程项目。

### 4.11.1 项目阶段

| 阶段 | 周期 | 交付物 |
|---|---|---|
| **需求评估** | 1 周 | 需求文档、对接方案、时间表 |
| **IT 协调** | 2-4 周 | API 凭证、网络打通、权限审批 |
| **原型开发** | 2-3 周 | 1 个场景端到端跑通 |
| **试点** | 2-4 周 | 5-10 个真实用户试用,收集反馈 |
| **推广** | 4-8 周 | 全公司铺开 |
| **运维** | 持续 | 监控、故障处理、版本更新 |

**不要跳过"试点"**——直接全公司铺开,几乎一定踩坑。

### 4.11.2 关键角色

| 角色 | 职责 |
|---|---|
| **业务负责人** | 提出需求、验收结果、推广使用 |
| **IT 负责人** | 开放 API、配置权限、监控安全 |
| **WorkBuddy 管理员** | 配置对接、运维、收集反馈 |
| **一线用户** | 试用、反馈 |

### 4.11.3 常见坑

我列出 5 个最常见的坑,提前预警:

1. **API 限流**:大多数企业系统 API 有 QPS 限制,WorkBuddy 调用频率不能超过
2. **数据量爆炸**:一次拉 100 万条客户数据,WorkBuddy 内存爆掉。要分页/过滤
3. **鉴权过期**:Token 有效期通常 24 小时,WorkBuddy 要自动续签
4. **数据 schema 变更**:IT 部门升级了 CRM 字段,WorkBuddy 立刻读不到。要有"schema 漂移检测"
5. **网络分区**:企业内网与外网不通,WorkBuddy 云端调用失败。要分清楚"内网系统"和"外网系统"

## 4.12 真实案例:一家 200 人制造企业的对接布局

最后给一个完整案例。

**公司背景**:某 200 人制造企业,有 OA(致远)、CRM(销售易)、知识库(Confluence)、BI(Tableau)、工单(Jira Service Desk)5 个核心系统。

**对接策略**:

| 系统 | 对接模式 | WorkBuddy 能力 |
|---|---|---|
| OA | REST API | 请假、报销、审批辅助 |
| CRM | REST API | 客户档案生成、商机跟进提醒 |
| 知识库 | 全文检索 API | 智能问答、文档检索 |
| BI | Text-to-SQL | 自然语言查询、自动报表 |
| 工单 | Webhook + REST API | 自动派单、状态跟踪 |

**实施节奏**:

- Q1:试点 OA + CRM,15 个用户
- Q2:扩展到 80 个用户,加知识库
- Q3:全公司 200 人,加 BI + 工单
- Q4:优化,根据反馈迭代

**效果(以该公司实际数据为准)**:

- 流程性事务(请假、报销)人工时间 -60%
- 客户档案整理时间 -50%
- 工单平均响应时间 -40%
- 知识库检索使用率 +200%

**关键成功因素**:
- IT 部门深度参与(不是"业务单方面推动")
- 试点期足够长(2 个月才推广)
- 每次推广都做培训(不是"装上就能用")

## 4.13 小结

本章讲了五个核心判断:

1. **WorkBuddy 是企业系统的"智能接入层",不是"替代品"**——它的价值是让系统"听懂人话",不是"换掉系统"。
2. **4 种通用集成模式各有边界**——Webhook(实时事件)、REST API(主动查询)、数据库直连(慎用)、浏览器自动化(没 API 时的兜底)。能用 API 就不用数据库,能用 Webhook 就不用浏览器。
3. **5 个常见对接场景的架构是标准化的**——OA、CRM、知识库、BI、工单的接入模式,大多有行业最佳实践可循。
4. **权限边界和审计是底线**——WorkBuddy 是"客人",最小权限,所有操作可追溯,跨系统操作要人工把关。
5. **失败兜底设计是工程问题**——网络层、协议层、业务层三层都要有兜底,用户必须有"知情权"。
