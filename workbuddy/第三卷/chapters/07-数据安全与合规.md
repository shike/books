## 7.1 工具越大,边界越敏感——为什么这一章必须讲

前 6 章,你已经熟悉了 WorkBuddy 的多模型路由、Skill 编写、系统对接、组织 ROI、变革管理。能力越大,边界越敏感。

一个能直接读取你工作目录、调用本地脚本、连接外部 API、跟企业微信/飞书/钉钉对话的桌面 AI,既是效率的倍增器,也是合规的放大器——任何一处疏忽,都可能被组织外部的审计、客户问询或监管检查反复放大。

我举一个真实场景。

某金融科技公司,IT 部门把 WorkBuddy 部署在 50 个分析师的工作电脑上,默认开启了"读工作目录"权限。一名分析师某天让 WorkBuddy 读了他的工作目录(包括 5 份客户合同 PDF),目的是"帮我提取合同里的违约金条款"。WorkBuddy 完成后,根据"知识库索引"的默认设置,**把客户合同的关键字段存进了 WorkBuddy 的语义索引**,用于后续任务检索。

3 个月后,公司因为另一件事接受外部审计。审计师问:"你们公司对客户合同数据的处理,有没有完整的访问日志?谁能在什么场景下访问?"

IT 部门答不上来。原因是:WorkBuddy 的知识库索引是默认开启的,索引的字段不在传统的"访问日志"覆盖范围内,审计师要的"完整访问日志"拿不出来。

**这不是工具的问题,这是"工作流设计"的问题**。

WorkBuddy 默认是"可用"的状态,但要让它"合规模型",需要在工作流设计阶段就把"数据分类、权限边界、审计留痕"做好。这一章讲的就是这件事。

## 7.2 三种部署形态——本机部署 / 云端辅助 / 混合托管

WorkBuddy 的运行形态,大致可以划分为三种:**本机部署(纯本地)、云端辅助(纯云端)、混合托管(本地+云端)**。三者没有绝对优劣,适用场景不同,合规含义也不同。

(图:三种部署形态的架构与责任划分,3.7.1)

### 7.2.1 形态一:本机部署(纯本地)

**定义**:WorkBuddy 客户端完全运行在用户设备上,所有数据(对话、文件、知识库索引、调用日志)都存储在本机。**默认不联网**——除非用户主动选择"联网搜索"或主动调用云端模型。

**数据流向**:

```
┌────────────────────────────┐
│      用户电脑(本机)         │
│  ┌──────────────────────┐  │
│  │   WorkBuddy 客户端    │  │
│  └──────┬───────────────┘  │
│         │                  │
│  ┌──────▼───────────────┐  │
│  │  本机文件 + 本地模型  │  │
│  │  本机知识库索引       │  │
│  │  本机调用日志         │  │
│  └──────────────────────┘  │
│                            │
│  (默认不联网)              │
└────────────────────────────┘
```

**适用场景**:
- 客户信息、合同、源代码等高敏感数据
- 强监管行业(金融、医疗、政务)
- 不能联网或不能上传数据的环境

**责任划分**:
- 用户承担**几乎全部**数据保护责任
- 设备丢失/被盗 = 数据丢失/外泄
- 模型服务方只看到"必要的指令文本",**看不到完整文件**

**优势**:
- 数据自主权最大
- 合规证据最完整(都在自己电脑上)
- 不依赖网络

**劣势**:
- 设备丢失/被盗时风险大
- 不能跨设备同步
- 大模型能力受限于本机算力

### 7.2.2 形态二:云端辅助(纯云端)

**定义**:WorkBuddy 客户端把对话、文件、知识库索引、调用日志等存放在云端,模型推理也在云端完成。

**数据流向**:

```
┌─────────────────┐         ┌──────────────────────┐
│  用户电脑        │  HTTPS  │   云端服务            │
│  WorkBuddy 客户端├────────►│  对话/文件/索引/日志   │
│  (轻量客户端)    │  TLS 1.3│  模型推理服务          │
└─────────────────┘         └──────────────────────┘
```

**适用场景**:
- 团队跨设备协作(在家用电脑写,在公司电脑继续)
- 需要云端模型能力(长上下文、多模态、Agent)
- 数据敏感度较低的场景(草稿、内部交流、公开资料)

**责任划分**:
- **共担责任模型**:用户与服务方共同承担
- 服务方负责"基础设施安全"(KMS 加密、租户隔离、灾备)
- 用户负责"应用层安全"(授权管理、数据分类)

**优势**:
- 跨设备同步
- 大模型能力更强
- 不依赖本机算力

**劣势**:
- 数据物理位置不在用户掌控
- 数据出境风险(云端服务器可能在境外)
- 依赖网络和服务方稳定性

### 7.2.3 形态三:混合托管(本地+云端)

**定义**:核心敏感数据留在本机,非敏感数据(对话摘要、协作笔记、Skill 配置)上传云端,通过细粒度策略控制"哪些内容可以走云端、哪些不行"。

**数据流向**:

```
┌──────────────────────────────┐
│       用户电脑(本机)          │
│  ┌────────────────────────┐  │
│  │   WorkBuddy 客户端      │  │
│  └────┬───────────┬───────┘  │
│       │           │          │
│  本地数据         云端数据    │
│  · 客户合同       · 对话摘要  │
│  · 源代码         · 协作笔记  │
│  · 客户名单       · Skill 配置│
│                    · 模型调用日志│
└──────────────────────────────┘
        ▲              ▲
        │              │ HTTPS
        │              │
   本地存储         云端服务
```

**适用场景**:
- 中大型企业(既想用云端能力,又不想放弃本地数据控制)
- 多元业务场景(部分敏感、部分不敏感)
- 行业监管要求"数据出域"前必须做评估

**责任划分**:
- **三方共担**:用户(本机部分)、服务方(云端部分)、IT 部门(策略配置)
- 必须有"策略引擎":根据数据类型、用户身份、操作类型动态决定数据流向

**优势**:
- 兼顾本地安全与云端能力
- 可根据数据敏感度差异化处理
- 适合真实企业工作流

**劣势**:
- 工程实现复杂
- 策略配置不当会留盲区
- 跨边界的数据流需要完整审计

### 7.2.4 三种形态的责任对照表

| 责任项 | 本机部署 | 云端辅助 | 混合托管 |
|---|---|---|---|
| 数据物理位置 | 用户本机 | 云端 | 两者 |
| 数据保护责任 | 用户承担 | 用户 + 服务方共担 | 三方共担 |
| 设备丢失风险 | 高 | 低 | 中 |
| 数据出境风险 | 无 | 高(取决于云端区域) | 中(策略可控) |
| 合规证据收集 | 容易(都在本机) | 困难(需服务方配合) | 中等(分两块) |
| 跨设备协作 | 不支持 | 支持 | 支持(部分数据) |
| 大模型能力 | 受限于本机算力 | 强 | 强 |
| 实施复杂度 | 低 | 低 | 高 |
| **典型行业** | 金融/医疗/政务 | 互联网/媒体/教育 | 大型制造/跨国企业 |

**核心结论**:**没有"最安全"的形态,只有"最匹配"的形态**。选择哪种形态,要根据你的数据敏感度、监管要求、协作需求综合判断。

## 7.3 数据分类——三类高敏感数据,三种处置策略

把数据笼统地称作"敏感数据"是无意义的。合规审计和事件复盘都要求你**按类型分别设计处置策略**。

下面分三类讨论,这是大多数企业最常碰到的场景。

### 7.3.1 第一类:客户名单与个人信息

客户名单、联系方式、交易记录、用户画像、行为日志都属于这一类,受《个人信息保护法》、《数据安全法》以及行业规范共同约束。

客户信息一旦进入 WorkBuddy,可能以**三种形式**存在:

1. **原始文件**(Excel/CSV/PDF):你授权 WorkBuddy 读取的本地文件
2. **对话上下文**:你向 WorkBuddy 提问时粘贴的片段
3. **知识库索引**:WorkBuddy 主动抓取并向量化的内容(用于后续检索)

其中,**知识库索引是最容易忽略的**——它会持久化、会被自动检索、可能在不同任务间复用,且在删除时往往需要单独的清理动作。

**处置策略**:

| 动作 | 建议 |
|---|---|
| **不向 WorkBuddy 提供未脱敏的客户实名信息** | 若必须使用,先以哈希或假名替换 |
| **关闭"自动加入知识库"选项** | 改为显式加入(每条由人审核) |
| **准备"客户信息脱敏对照表"** | 把真实姓名替换为代号、手机号替换为虚拟号段、地址替换为行政区划代码 |
| **定期清理过期索引** | 每季度清理一次,删除 12 个月前未访问的客户信息 |
| **客户同意书更新** | 在客户协议中加入"允许使用 AI 工具辅助处理"的告知条款 |

**关键提醒**:即使你脱敏了客户信息,**索引本身也可能被还原**。比如"张三""13800138000""北京市朝阳区"三个字段在索引中同时出现,虽然各自脱敏了,但通过交叉比对,有可能还原出原始信息。所以,**索引也要做"假名化"处理**,而不是只对原始文件脱敏。

### 7.3.2 第二类:合同文本与商业秘密

合同、协议、保密条款(NDA)、律师函等,通常包含商业秘密与法律承诺。这类数据的特点是"看起来公开,实则敏感"——客户名称、金额、违约金、竞业条款,任何一项泄露都可能引发商业风险。

**处置策略**:

1. **合同原件保留在专用网盘或合同管理系统(CLM)中**,WorkBuddy 只能读取脱敏版本
2. **若需要 WorkBuddy 协助审阅条款,请提供条款摘录而非整本合同**——比如"请审阅这份合同第 12 条和第 15 条的违约责任"
3. **对于盖章版 PDF,优先用本地 OCR 工具转换为文本**,再人工标注重点后交给 WorkBuddy
4. **合同中的"金额""期限""违约责任"三项**,即使在脱敏版本中也可能因为上下文关联被推断出来。建议同时脱敏这三项,只保留条款逻辑供 WorkBuddy 分析
5. **合同复盘完成后,在 WorkBuddy 中显式删除对话历史**,避免后续任务不慎引用旧条款

(图:客户信息、合同、源代码三类数据的处置要点对比,3.7.2)

**实操建议**:为每份合同建立"WorkBuddy 审阅记录表",记录:
- 哪份合同、什么时间、由谁授权
- WorkBuddy 读了哪些条款(精确到条号)
- 输出结果保存在哪里
- 任务完成后,谁关闭了会话、清理了索引

这张表在合规审计时是"金标准"——它证明了"我们用了 AI 工具,但我们控制住了边界"。

### 7.3.3 第三类:源代码与核心算法

源代码既是企业核心资产,也是合规审计的重点。WorkBuddy 处理源代码时,会经过**三道边界**:

| 边界 | 数据范围 | 风险等级 |
|---|---|---|
| 本地 IDE 插件 | 直接读取你工作目录 | 中(本机泄露风险) |
| 对话上下文 | 你贴入的代码片段 | 中高(可被检索) |
| 云端模型 | 若任务需要远程推理 | **高**(出本机) |

**处置策略**:

1. **核心算法、加密密钥、用户凭证永远不离开本地**——这三类直接列在 WorkBuddy 的"黑名单"里,即使你误操作也不会被读取
2. **在 `.gitignore` 或 WorkBuddy 的排除列表中,显式排除 `secrets/`、`keys/`、`.env`、`*credentials*` 等路径**
3. **为每个项目设置 WorkBuddy 访问白名单**,而不是默认全工作目录开放
4. **上传到云端推理的代码片段,建议只包含函数级、不含模块级上下文**——避免"虽然只贴了 1 个函数,但模型能推断出整个模块的设计思路"
5. **开源代码的贡献者信息、商业 SDK 的 License 限制,需要由法务单独审核**——AI 帮你写代码很快,但 AI 不会替你承担 License 风险

**特别提醒**:**AI 生成的代码同样受 License 约束**。如果 WorkBuddy 帮你写的代码片段,恰好与某个 GPL/LGPL/AGPL 项目的代码高度相似(模型"学"过),那这个代码片段的归属、能不能商用,需要法务介入判断。

我的建议:**所有 AI 生成的代码,在合并到主分支前,先过一次"License 检查工具"(比如 FOSSA、Black Duck、Snyk),不要靠人眼判断**。

### 7.3.4 三类之外的扩展场景

需要说明,以上三类并非穷尽。医疗数据、生物特征、地理位置、未成年人信息等,在不同行业里都有更严格的专项要求。本章聚焦通用场景,特定行业的合规请结合行业规范。

## 7.4 模型调用日志——事后追溯的"黑匣子"

WorkBuddy 在每次模型调用时,会生成一条**调用日志**(也称审计日志)。这条日志是"事后追溯"的关键抓手——出了事,第一件事就是查日志。

### 7.4.1 日志的关键字段

一份完整的调用日志,应该包含以下字段:

| 字段 | 含义 | 为什么重要 |
|---|---|---|
| **谁** | 调用者(用户 ID) | 定位责任 |
| **何时** | 时间戳(精确到毫秒) | 还原时间线 |
| **何处** | 来源(设备 IP、WorkBuddy 实例 ID) | 定位设备 |
| **做了什么** | 任务类型、模型名称、提示词 hash | 还原行为 |
| **读/写了什么** | 文件路径、数据指纹(hash)、授权范围 | 还原数据 |
| **结果如何** | 输出 token 数、调用是否成功、错误码 | 还原结果 |
| **数据指纹** | 输入/输出内容的 hash(不存原文) | 防止原文泄露,又能验证一致性 |

(图:模型调用日志的 7 个关键字段,3.7.3)

**重要原则**:**日志不要存原文,只存 hash**。原因:
- 日志本身就是"敏感资产",存原文会让"日志"变成"数据副本",风险加倍
- 存 hash 足以"验证"——事后可以重新跑同一任务,比对输出
- 存 hash 也是 GDPR/个人信息保护法的要求(最小化原则)

### 7.4.2 日志的保留期限

**WorkBuddy 默认保留 180 天**,企业版可延长。

保留期限的设计逻辑:

| 场景 | 建议保留期 | 理由 |
|---|---|---|
| 个人版 | 90-180 天 | 减轻本机存储压力 |
| 团队版 | 180 天 | 满足一般内部审计 |
| 企业版(强监管) | 1-3 年 | 满足行业法规要求 |
| 上市公司 | 5 年以上 | 满足证券法对内幕信息追溯的要求 |

**注意**:延长保留期不是简单的"多存点东西",还要考虑:
- 存储成本(日志占空间)
- 检索性能(日志多了查询慢)
- 取证效率(出事时能不能快速定位)

我建议**分层保留**:
- 180 天内:全量日志,可秒级检索
- 180 天 - 1 年:压缩日志,可分钟级检索
- 1 年以上:仅保留索引和聚合统计,原始日志归档到冷存储

### 7.4.3 日志的查询与导出

WorkBuddy 提供日志查询界面(具体以你安装版本为准),通常支持:
- 按时间范围查询
- 按用户/设备查询
- 按任务类型查询
- 按模型名称查询
- 按"成功/失败"过滤

**导出格式**通常为 CSV/JSON,便于:
- 法务部门调取
- 内部审计
- 外部监管提交

**重要提醒**:**日志导出操作本身也要留痕**。谁导出了什么日志、什么时间、什么原因,都要记录。这是为了防止"内部人员用导出日志的方式,二次泄露数据"。

## 7.5 数据出境——工程化规避的 6 种手段

"数据出境"是国内合规的高频词。它指的是"数据从境内服务器转移到境外服务器,或境外机构可以访问境内数据"。

数据出境在 AI 工具场景里尤其敏感——**AI 模型推理往往发生在云端,如果云端服务器在境外,就构成了"数据出境"**。

WorkBuddy 的解决方案不是"完全禁止数据出境",而是**给你 6 种工程化规避手段**,让你在不出境的前提下用上 AI 能力。

### 7.5.1 手段一:本机模型推理

用本地部署的开源模型(DeepSeek 开源版、Qwen 开源版、智谱 GLM 开源版等),完全在本机推理。**数据零出境**。

适用:短文本任务(摘要、分类、简单问答)。
限制:模型能力受限于本机算力(7B-13B 参数级别),长文档任务效果一般。

### 7.5.2 手段二:国内云端推理

把模型推理放在国内云服务提供商的境内部署(如主流公有云、私有云、混合云等),数据物理位置在境内。

适用:需要大模型能力、但不能出境。
注意:即使是国内云端,**仍要确认"租户隔离"和"数据存储区域"**——某些云服务商的"可用区"可能涉及境外节点。

### 7.5.3 手段三:数据脱敏后再出境

对必须出境的场景,先在本地做脱敏(去除 PII、去除商业秘密),再把脱敏后的数据传到境外模型。

适用:研究类任务、模型效果对比、多模型路由。
脱敏标准:个人信息去标识化、商业秘密完全去除、关键数字替换为范围(比如"100 万-200 万"代替"1,580,000")。

### 7.5.4 手段四:模型蒸馏与本地化

把云端大模型的能力"蒸馏"到本机小模型。具体做法:
- 用大模型处理一批典型任务,生成"标准答案"
- 用这些"标准答案"训练本机小模型
- 后续类似任务用本机小模型处理

适用:任务类型相对固定(比如"周报生成""客户邮件回复")。
效果:小模型在本任务上可达到大模型 80-90% 的效果,但不能跨任务迁移。

### 7.5.5 手段五:API 网关代理

通过 API 网关代理所有云端调用,网关层做:
- 数据脱敏(自动去除 PII)
- 调用审计(完整记录所有请求/响应)
- 异常检测(识别异常调用模式)

适用:团队级 AI 工具,需要统一管理。
注意:网关层要由公司自建,而不是依赖第三方服务——否则"数据先到第三方网关"本身就可能构成数据共享。

### 7.5.6 手段六:多模型路由

WorkBuddy 的多模型路由功能本身就是规避手段——它可以**按数据敏感度自动选择模型**:
- 敏感数据 → 本机模型
- 中等敏感 → 国内云端
- 不敏感 → 海外云端(成本最低)

适用:多业务场景,有不同敏感度等级的数据。
**这是最"工程化"的方案**,但需要事先做好"数据敏感度分类"和"路由策略配置"。

## 7.6 国内主流合规框架——四组底线与落地含义

合规不是一组条款,而是一种工作方式。下面列出**国内主流的合规框架**(不指定具体认证编号,因各行业、各地区适用的具体规范会有差异),并讨论它们在 WorkBuddy 场景下的落地含义。

### 7.6.1 第一组:《个人信息保护法》与"告知-同意"

**核心原则**:
- 处理个人信息要有合法基础(同意、合同、法律义务等)
- 敏感个人信息(生物识别、宗教信仰、未成年人信息)需**单独同意**
- 个人信息处理涉及"委托处理"时,需签署数据处理协议(DPA)

**WorkBuddy 场景下的落地**:
1. **客户协议更新**:在客户协议中加入"允许使用 AI 工具辅助处理您的信息"条款
2. **员工告知**:在企业内部公告 WorkBuddy 使用范围、数据流向、存储位置
3. **第三方共享清单**:WorkBuddy 涉及哪些第三方服务(模型厂商、云服务商),需要明确告知
4. **DPA 签订**:与模型厂商、云服务商签订数据处理协议,明确各方责任

**易踩的坑**:**很多企业认为"我们用的 AI 工具是国产的,所以没问题"**。但即使是国产模型,如果涉及**跨厂商协作**(比如用 DeepSeek + Kimi + 智谱的多模型路由),每个厂商都是"委托处理方",每个都要签 DPA。

### 7.6.2 第二组:《数据安全法》与"数据分类分级"

**核心原则**:
- 数据按"重要程度"分级(一般、重要、核心)
- 不同级别对应不同保护措施
- 数据出境前要评估"国家数据安全"

**WorkBuddy 场景下的落地**:
1. **数据分类标签**:为 WorkBuddy 处理的每类数据打"敏感度标签"(L1/L2/L3 或 低/中/高)
2. **分级保护**:L1 数据可出境,L2 数据需评估,L3 数据**严禁出境**
3. **出境评估**:对必须出境的数据,做"个人信息保护影响评估"(PIPIA),保留评估报告

**易踩的坑**:**"重要数据"和"核心数据"的认定,各行业标准不同**。金融行业的"重要数据"和医疗行业的"重要数据"可能不一样。建议咨询你所在行业的法务或合规部门,不要凭通用认知判断。

### 7.6.3 第三组:行业专项规范(金融、医疗、政务等)

**核心原则**:
- 各行业有自己的数据安全规范
- 金融行业:客户信息保护、反洗钱、客户身份识别
- 医疗行业:病历保护、隐私保护、生物信息安全
- 政务行业:政务数据开放、政务数据安全

**WorkBuddy 场景下的落地**:
- 金融行业:严禁将客户交易数据、身份信息用于模型训练;工作目录授权要按"最小授权"原则
- 医疗行业:病历数据严禁出境;AI 输出可作为"辅助参考",但**不能替代医生诊断**
- 政务行业:严格遵守"涉密不上网、上网不涉密";涉密文档绝对不进入 WorkBuddy

**易踩的坑**:**行业规范的更新频率比法律更高**。今年合规的方案,明年可能就过时。建议每季度关注你所在行业的监管动态。

### 7.6.4 第四组:网络安全与数据保护"通用要求"

**核心原则**:
- 网络安全等级保护(国内通行的网络安全建设要求)
- 密码法(商用密码使用规范)
- 数据出境安全评估办法(出境前评估)

**WorkBuddy 场景下的落地**:
- 网络架构:WorkBuddy 部署的网络要符合企业内部网络安全规范(防火墙、入侵检测)
- 密码合规:本机加密、传输加密,要使用合规的商用密码算法
- 出境评估:对需要出境的数据,做完整的数据出境安全评估,保留评估报告

**重要提醒**:不同时期、不同行业、不同业务场景,适用"哪些通用要求"会有差异。本节给出的是**通用框架**,不是"全行业统一清单"。具体到你所在的行业、企业规模、数据出境场景,**请结合具备资质的法律顾问共同确认**。

## 7.7 监管视角下的 72 小时取证准备

"72 小时取证"不是法律规定的固定数字,而是监管实践中对"信息安全事件响应"的常见时间窗。监管视角下,当发生数据泄露、滥用、未授权访问等事件时,企业需要在短时间内(通常 24-72 小时)提供可信的证据链。

### 7.7.1 事前要做的 4 件事

**事前的准备,比事后的应对更关键**。我列 4 件"出事前必须做完"的事:

1. **完整的日志体系**:WorkBuddy 的调用日志、企业系统的访问日志、网络流量日志,都要完整保留
2. **数据指纹库**:对重要数据(客户合同、源代码、客户名单)生成"数据指纹"(hash),存放在独立的安全位置
3. **应急响应流程**:写一份"信息安全事件应急响应 SOP",明确谁负责、做什么、什么时间完成
4. **定期演练**:每季度做 1 次"模拟事件"演练,让团队熟悉流程

(图:72 小时取证的"事前-事中-事后"三阶段,3.7.5)

### 7.7.2 事中要做的 5 件事

事件发生时,按以下顺序应对:

**小时 0-2:发现与初步评估**
- 谁发现的、什么时间、什么场景
- 初步判断:数据范围(哪些数据可能被影响)、影响用户数(多少人受影响)、影响等级(L1/L2/L3)

**小时 2-8:控制与遏制**
- 切断相关访问通道(封账号、撤权限、停服务)
- 冻结相关数据(防止二次泄露)
- 通知相关方(管理层、法务、PR)

**小时 8-24:取证与分析**
- 调取 WorkBuddy 调用日志
- 调取企业系统访问日志
- 比对数据指纹,确认"是否真的泄露""泄露范围多大"
- 写"事件初步报告"

**小时 24-48:决策与沟通**
- 决策:是否通知用户、是否通知监管、是否公开声明
- 沟通:按合规要求通知相关方(用户、监管、客户)
- 内部同步:统一对外口径,防止信息混乱

**小时 48-72:补救与复盘**
- 补救:撤回泄露的数据(如可能)、通知受影响用户、提供补救方案(如改密码、监控账户)
- 复盘:写"事件完整报告",明确根因、改进措施、责任人
- 改进:更新安全策略、流程、技术控制

### 7.7.3 事后要做的 3 件事

事件处理完,**不是结束**。还要做 3 件事:

1. **更新应急响应 SOP**:根据本次事件暴露的不足,修改 SOP
2. **培训与演练**:把本次事件作为培训材料,让全员了解
3. **持续监控**:对相关数据、相关用户、相关系统做"加强监控",持续 30-90 天

### 7.7.4 取证清单模板

给监管或法务部门取证时,通常需要以下材料:

| 类别 | 必备材料 |
|---|---|
| **数据范围** | 受影响的数据类型、数据量、用户数 |
| **时间线** | 事件发现时间、控制时间、通知时间、复盘时间 |
| **根因分析** | 直接原因、间接原因、系统性原因 |
| **日志证据** | WorkBuddy 调用日志、系统访问日志、网络日志 |
| **数据指纹** | 泄露数据 vs. 原始数据的指纹对比 |
| **通知记录** | 用户通知、监管通知、客户通知的记录 |
| **补救方案** | 已经采取的补救措施、长期改进计划 |
| **责任认定** | 责任人员、处理决定 |

## 7.8 合规与效率的平衡——不要"为了合规而合规"

讲了这么多合规要求,我必须强调一句:**合规是为了业务,不是为了合规本身**。

如果你的合规设计让业务无法开展,那这个设计是有问题的。

我见过一些企业,把合规推到极致,结果:
- 所有数据都要"四重审批"才能用 AI
- 工程师为了合规要填 20 份表格
- 业务部门为了赶时间,偷偷绕开合规

**这种"过度合规"反而催生了"违规"**。

正确的姿势是**"分级合规"**:

| 数据敏感度 | 合规要求 | 业务影响 |
|---|---|---|
| 低(公开资料) | 无需额外合规 | 直接用 |
| 中(内部资料) | 授权 + 脱敏 + 日志 | 简单审核即可 |
| 高(客户数据/合同/源代码) | DPA + 强脱敏 + 完整审计 | 需要 IT/法务审核 |

**核心原则**:**数据敏感度越高,合规越严;但合规流程越繁琐,业务越想绕开**。所以**敏感度分类一定要准**——不要把"低敏感数据"也按"高敏感"管,否则业务会崩溃;也不要"高敏感数据"按"低敏感"管,否则会出事。

## 7.9 真实案例:某金融科技公司的合规改造

最后,给你一个完整的 6 周合规改造案例。

**背景**:某金融科技公司,3 年前开始用 AI 工具(那时还没有 WorkBuddy),数据出境管控松散,模型调用日志不全,客户信息处理不规范。2026 年,接受外部审计,被指出 12 项合规问题。CTO 决定 6 周内完成整改。

### 第 1-2 周:数据清点与分类

- 全公司梳理"AI 工具处理的 17 类数据"
- 按敏感度分级:L1(低,5 类)、L2(中,8 类)、L3(高,4 类)
- 列出每类数据的"现在流向"(本机/国内云端/海外云端)

### 第 3-4 周:部署形态重构

- L3 数据(客户身份、交易记录):**全部迁回本机部署**
- L2 数据(内部文档、协作笔记):**保留混合托管,本机+国内云端**
- L1 数据(公开资料、模型路由的优化数据):**可用海外云端,做脱敏**

- 改造 WorkBuddy 配置:关闭 L3 数据的"知识库索引"功能,改为"按需读取"

### 第 5 周:日志体系完善

- 接入 WorkBuddy 审计日志到企业 SIEM(安全信息与事件管理平台)
- 为每条日志加上"数据指纹 hash"
- 关键操作(读 L3 数据、跨边界传输)加实时告警

### 第 6 周:应急响应演练

- 模拟"客户数据泄露"事件
- 完整跑 24 小时取证流程
- 根据演练结果修改应急响应 SOP

### 6 周后

- 12 项合规问题全部关闭
- 数据出境 100% 符合"分级管控"原则
- 日志覆盖 100%,关键操作告警 100%
- 业务部门感知:对日常工作流影响 < 5%(主要是 L3 数据的"读"操作需要 1 步授权)
- 监管二次审计:无新增问题

**关键成功因素**:
1. 数据清点做得彻底(没有"漏网之鱼")
2. 部署形态"分级",不是"一刀切"
3. 日志体系完整,关键操作实时告警
4. 应急响应演练发现 3 个流程漏洞,提前修补

## 7.10 小结

本章讲了五个核心判断:

1. **三种部署形态(本机/云端/混合)责任划分不同**——本机部署责任全在用户,云端辅助是共担模型,混合托管是三方共担。没有"最安全"的形态,只有"最匹配"的形态。
2. **三类高敏感数据(客户/合同/源代码)各有不同处置策略**——核心是"分级管控",不是"一刀切"。脱敏、授权、审计三件套缺一不可。
3. **模型调用日志是事后追溯的"黑匣子"**——7 个关键字段缺一不可,存 hash 不存原文是基本要求。保留期按业务需要分级(180 天 - 5 年)。
4. **数据出境的工程化规避有 6 种手段**——本机推理、国内云端、脱敏后出境、模型蒸馏、API 网关、多模型路由。不同场景选不同手段,组合使用。
5. **72 小时取证需要事前准备**——完整的日志体系、数据指纹库、应急 SOP、定期演练,缺一不可。事中按"0-2-8-24-48-72 小时"节奏推进,事后复盘改进。
