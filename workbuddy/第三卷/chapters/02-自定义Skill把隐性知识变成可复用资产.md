## 2.1 为什么需要自定义 Skill

在第一卷第 6 章,我讲过 Skill 的概念——**Skill 是"提示词 + 文件读取规则 + 工具调用 + 输出格式"的标准化打包**。一个 Skill 就像一份"SOP + 模板 + 自动化",团队任何人调用它,都能产出符合标准的成品。

到了第三卷,我们要从"会用 Skill"进入"**自己造 Skill**"。

原因是:**一个组织真正有价值的工作,是隐性的、经验性的、不在文档里的**。

我先举一个例子。

一家消费品公司的市场部,有一个"包装文案改写"的常规工作:同一款产品,要让文案适配"小红书风""抖音风""电商详情页风""线下海报风"四种风格,以前由资深文案小王负责,他每次接到任务,凭经验改写,质量稳定。问题是:**小王一个人扛不住**——他同时管 3 个品牌、十几个 SKU,经常加班到深夜。

公司后来用 WorkBuddy 自动化,效果不好——WorkBuddy 改出来的文案,要么"小红书风"过于平淡,要么"抖音风"过于直白。**为什么?因为"小红书风"是隐性知识**——它在小王脑子里,在小红书 KOL 投过的稿件里,在过去三年累计的几百篇爆款笔记里,但它**没有写在任何文档里**。

公司后来怎么解决的?**让小王把他的隐性知识显性化,做成一个 Skill**。

具体做法:小王坐下来,花两周时间,把"小红书风"的特征拆成 30 条规则——"标题要在 18 字以内、带 emoji 密度、开头要有钩子、正文要分点、结尾要有互动引导……"。然后把这 30 条规则写成 Skill 的 prompt,加上"读输入 → 按规则改写 → 输出三版候选"的流程,放到 WorkBuddy 技能市场。

从此,任何团队成员输入"产品名 + 卖点 + 风格(小红书)",一键产出符合小红书风的三版文案,质量稳定在"小王初稿水平"。

**这个 Skill,值多少?**如果按小王的工时成本,这个 Skill 一年能省 800-1200 小时,折合人民币 30-50 万元(以一线城市文案市场价计算,具体以你团队数据为准)。

这就是 Skill 的核心价值——**把一个人的隐性知识,变成组织所有成员都能调用的可复用资产**。

本章,我把这个"显性化"过程完整拆给你看。

## 2.2 Skill 的本质——四要素打包

我先给 Skill 一个工程化的定义。

**Skill = 提示词模板(Prompt) + 文件读取规则(Input Schema) + 工具调用配置(Tool Config) + 输出格式规范(Output Schema)**

这四个要素缺一不可。

| 要素 | 作用 | 没有会怎样 |
|---|---|---|
| 提示词模板 | 定义 Skill 的"思考方式"——它该按什么逻辑处理任务 | 每次调用效果不一致,质量靠运气 |
| 文件读取规则 | 定义 Skill 该读哪些文件、按什么格式读 | 读不到该读的数据,输出基于错误输入 |
| 工具调用配置 | 定义 Skill 该调用哪些本机工具(邮件、PPT、Excel 等) | 只能输出文字,不能直接产出成品 |
| 输出格式规范 | 定义 Skill 的输出该是什么格式(Markdown / Word / Excel / 邮件草稿) | 产出格式混乱,人工后期整理成本高 |

我用第一卷第 4 章的"周报生成"场景做对照。

**没有 Skill 的工作流**:
1. 员工每天打开 WorkBuddy
2. 手动复制粘贴本周邮件、聊天记录
3. 写一段 prompt:"基于以上内容,生成周报"
4. AI 输出 800 字周报草稿
5. 员工人工改格式、调语气

**有 Skill 的工作流**:
1. 员工打开 WorkBuddy,在技能市场点击"周报生成 V3.2"
2. Skill 自动读取授权文件夹("工作目录/本周")
3. Skill 按预设 prompt 跑 4 步推理(本周事件 → 分类归纳 → 风险识别 → 措辞润色)
4. Skill 输出符合团队模板的 1500 字周报
5. 员工花 5 分钟补充本周临时事项,提交

**差异**:有 Skill 后,每次产出的质量稳定,且省了"复制粘贴"+"改格式"+"调语气"三步,每次省 30-60 分钟。

这就是 Skill 的本质:**把"优秀员工的最佳实践"固化成可复用的工作流**。

## 2.3 Skill 的标准结构

WorkBuddy 的 Skill 有标准结构,基于一个 YAML/JSON 格式的元数据文件 + 一个 Markdown 格式的指令文件。两者放在一个目录里,就是完整的 Skill 包。

### 2.3.1 目录结构

一个完整的 Skill 包,标准目录结构如下:

```
my_skill/
├── skill.yaml          # 元数据:名称、版本、作者、依赖
├── instructions.md     # 指令文件:核心 prompt + 工作流定义
├── inputs.schema.json  # 输入定义:接受哪些参数
├── outputs.schema.json # 输出定义:产出什么格式
├── examples/           # 案例目录:3-5 个调用样例
│   ├── example_1.md
│   ├── example_2.md
│   └── example_3.md
├── tests/              # 测试用例
│   ├── test_001.md
│   └── test_002.md
├── tools.json          # 工具调用配置
└── README.md           # 给团队成员看的说明
```

每个文件的用途,我下面用一个真实 Skill 案例演示。

### 2.3.2 元数据(skill.yaml)

```yaml
name: weekly_report_generator
display_name: "周报生成器"
version: 1.2.0
author: market_dept_skill_team
description: |
  基于本周邮件、聊天记录、文档,自动生成符合
  公司周报模板的草稿。
tags:
  - 周报
  - 文书
  - 高频
license: internal_use
min_workbuddy_version: "1.0.0"
required_permissions:
  - folder: ~/WorkBuddy_workspace/本周
    access: read
  - folder: ~/WorkBuddy_workspace/周报模板
    access: read
  - file: ~/WorkBuddy_workspace/周报输出/{date}_周报.md
    access: write
```

这个文件定义了 Skill 的"身份证"——它叫什么、谁写的、依赖什么权限。WorkBuddy 在加载 Skill 前会先读这个文件,确认权限、版本兼容性。

### 2.3.3 输入定义(inputs.schema.json)

```json
{
  "type": "object",
  "properties": {
    "date_range": {
      "type": "string",
      "description": "本周日期范围,格式 YYYY-MM-DD 至 YYYY-MM-DD",
      "required": true
    },
    "focus_areas": {
      "type": "array",
      "items": { "type": "string" },
      "description": "本周重点关注的项目/客户/产品",
      "required": false
    },
    "extra_notes": {
      "type": "string",
      "description": "本周临时事项,人工补充",
      "required": false
    }
  }
}
```

这个文件让 WorkBuddy 在调用 Skill 前,知道要问用户哪些参数(类似函数参数),减少"AI 凭假设乱猜"的情况。

### 2.3.4 输出定义(outputs.schema.json)

```json
{
  "type": "object",
  "properties": {
    "report_content": {
      "type": "string",
      "description": "周报正文,Markdown 格式"
    },
    "summary_metrics": {
      "type": "object",
      "properties": {
        "tasks_completed": { "type": "integer" },
        "tasks_in_progress": { "type": "integer" },
        "risks_identified": { "type": "integer" }
      }
    },
    "suggested_followups": {
      "type": "array",
      "items": { "type": "string" },
      "description": "建议的下周跟进事项"
    }
  }
}
```

这个文件让 WorkBuddy 在生成结果后,知道要把内容输出到哪个字段(类似返回值类型),便于下游程序或人工处理。

### 2.3.5 指令文件(instructions.md)

这是 Skill 的核心,定义了"AI 该按什么逻辑思考"。

```markdown
# 周报生成器 · 指令

## 角色定义
你是一名资深行政助理,负责为某中层管理者撰写周报。
你的工作风格:结构清晰、措辞专业、突出重点、不夸张。

## 输入材料
- `date_range`:本周日期范围
- `focus_areas`:本周重点关注的事项
- `extra_notes`:用户人工补充的临时事项
- 自动读取:`~/WorkBuddy_workspace/本周/` 下的所有文件
  (邮件存档、聊天记录、提交的文档)
- 自动读取:`~/WorkBuddy_workspace/周报模板/template.md`

## 工作流

### Step 1:本周事件归纳
- 读取所有输入材料
- 按时间线整理出"本周发生的关键事件"
- 输出:50-80 条事件卡片

### Step 2:事件分类
- 把事件分成三类:已完成、进行中、风险
- 风险类要明确"风险描述 + 应对建议"
- 输出:三段式分类结果

### Step 3:措辞润色
- 按"周报模板"的格式(标题层级、用词、长度)
- 调整为"对上汇报"的语气(专业、克制、突出成绩)
- 字数控制在 1200-1800 字

### Step 4:补充与输出
- 整合 `extra_notes`
- 列出"建议的下周跟进事项"(3-5 条)
- 输出 Markdown 格式,符合公司模板

## 输出要求
- 严格遵守 outputs.schema.json 的字段定义
- 不编造数据,不夸大成绩
- 风险事项必须明确"风险等级"(高/中/低)
```

这就是 Skill 的"大脑"——它告诉 WorkBuddy 该按什么流程思考。

### 2.3.6 工具调用配置(tools.json)

```json
{
  "tools": [
    {
      "name": "read_files",
      "params": {
        "folder": "~/WorkBuddy_workspace/本周",
        "recursive": true,
        "file_types": ["eml", "txt", "md", "docx", "pdf"]
      }
    },
    {
      "name": "read_template",
      "params": {
        "path": "~/WorkBuddy_workspace/周报模板/template.md"
      }
    },
    {
      "name": "write_file",
      "params": {
        "path": "~/WorkBuddy_workspace/周报输出/{date}_周报.md",
        "encoding": "utf-8"
      }
    }
  ]
}
```

这个文件定义 Skill 可以调用哪些本机工具。WorkBuddy 在跑 Skill 时,会按这个配置调用相应工具。

### 2.3.7 测试用例(tests/test_001.md)

```markdown
# Test 001:标准周报生成

## 输入
- date_range: "2026-08-10 至 2026-08-16"
- focus_areas: ["产品 v2.0 发布", "Q3 预算复盘"]
- extra_notes: "本周参与了 2 次客户拜访"

## 预期输出
- 包含 3 段:已完成 / 进行中 / 风险
- 字数 1200-1800
- 风险事项至少 1 条
- 跟进事项 3-5 条
- 不出现具体客户名(脱敏)

## 通过条件
- 人工 review:合格
- 字段完整性:100%
- 字数在区间内
```

测试用例是 Skill 质量的"守门员"——每次 Skill 版本更新,跑一遍测试,确认没退化。

## 2.4 第一个 Skill 案例:周报生成(完整开发流程)

我用"周报生成"Skill 做完整演示。这是大多数组织最高频的 Skill,也是"显性化"最简单的起点。

### Step 1:确定需求

跟资深员工小王访谈,问三个问题:

1. **你每周做这件事花多少时间?**
2. **哪几步最花时间?**
3. **哪几步你"凭经验"做,新员工做不了?**

小王回答:每周花 4-5 小时。最花时间的是"读本周所有材料"(2 小时)、"归纳分类"(1 小时)、"措辞润色"(1 小时)。最依赖经验的是"措辞润色"——他知道"对上汇报"该用什么语气,新员工写的周报总被领导批"不专业"。

**Skill 化的目标**:把 4-5 小时压到 30 分钟(小王的人工 review + 临时事项补充)。

### Step 2:显性化隐性知识

让小王把"对上汇报"的措辞规则写出来。他写 30 分钟,大概写出 15 条:

1. 标题用"已完成/进行中/风险"三段式,不用"亮点/不足/反思"等花哨词
2. 数字必须具体(不说"显著提升",说"提升 27.3%")
3. 风险事项必须明确"风险等级 + 应对建议 + 责任人"
4. 不出现"应该""可能""大概"等模糊词
5. 领导关心的"重点客户、重点项目"放第一段
6. ……(略,共 15 条)

这就是 Skill 的"知识原料"。

### Step 3:写 instructions.md

按 2.3.5 的模板,把 15 条规则嵌入工作流的"Step 3:措辞润色"步骤。

```markdown
### Step 3:措辞润色

执行以下 15 条措辞规则:

1. 三段式结构:已完成 / 进行中 / 风险
2. 数字必须具体(给百分比、给金额、给人数)
3. 风险事项 = 风险等级 + 应对建议 + 责任人
4. 禁用"应该/可能/大概/差不多"
5. 重点客户、重点项目放首段
6. 不出现"领导""老板"等口语化称谓,用"管理层"
7. 动词主动语态,不用被动语态
8. 每段首句是"该段结论",后面是论据
9. 风险事项不超过 3 条(避免显得全盘被动)
10. 已完成事项突出"对业务的影响",不只罗列"做了什么"
11. 时间表述用具体日期,不用"最近""之前"
12. 不引用具体客户名(脱敏)
13. 不引用具体工资、奖金数字
14. 长度 1200-1800 字(超出截断,不足补充)
15. 末尾加 1 段"下周计划"(3-5 条)
```

### Step 4:写测试用例

至少 3 个测试用例:

1. **正常周报生成**(标准输入)
2. **风险事项较多的情况**(3 个以上风险)
3. **本周无事可写的情况**(材料少,如何避免拼凑)

每个测试用例写预期输出 + 通过条件。

### Step 5:本地调试

在 WorkBuddy 中加载 Skill,跑测试用例,人工 review 输出。

调试常见问题:
- 输出太短 → 调整 prompt 中的字数约束
- 输出格式不对 → 调整 instructions.md 的 Step 顺序
- 读不到文件 → 检查 tools.json 的路径
- 数字不具体 → 在 instructions.md 加"强制数字"规则

### Step 6:发布到内部 Skill 库

测试通过后,把 Skill 目录打包,发布到团队"内部 Skill 库"(团队自建的共享目录,WorkBuddy 可识别为本地 skill 源)。

### Step 7:收集反馈,迭代

发布 2 周后,收集 5 个使用者的反馈:
- 输出质量
- 操作流畅度
- 期望改进点

根据反馈,更新到 V1.1、V1.2…… 这就是 Skill 的版本管理。

## 2.5 第二个 Skill 案例:会议纪要

这个 Skill 比"周报生成"更结构化,适合"会议多、节奏快"的团队。

### 2.5.1 需求来源

某产品部门每周 5-8 场会议(需求评审、技术评审、跨部门对齐、上线复盘)。会议纪要以前由产品经理轮流写,每次 30-60 分钟,经常写不完或漏掉关键决策。

### 2.5.2 关键设计

这个 Skill 的核心创新是**"角色感知"**——它知道每个参会者的角色(产品、技术、运营、市场),对每条发言按角色加权。

```yaml
inputs:
  meeting_audio: required
  participant_roles:
    - name: 张三
      role: 产品
      weight: 1.0
    - name: 李四
      role: 技术负责人
      weight: 1.5  # 技术决策权重更高
    - name: 王五
      role: 运营
      weight: 0.8
```

### 2.5.3 工作流

Step 1:转写会议录音(用 Whisper 类工具,WorkBuddy 内置)
Step 2:按发言人分块,识别每条发言的角色
Step 3:提取"明确决策"(有"决定""拍板""就这么定"等强信号的发言)
Step 4:提取"行动项"(有"我来""我负责""下周三前"等信号的发言)
Step 5:按"决策 / 行动项 / 待讨论"三段式输出

### 2.5.4 输出示例

```markdown
# 2026-08-15 需求评审会 · 纪要

## 关键决策
1. v2.1 版本推迟到 9 月 5 日上线(原定 8 月 30 日)
   - 决策人:李四
   - 理由:支付模块的容错测试未完成
2. 新增"会员积分"功能,优先级 P1
   - 决策人:张三
   - 范围:仅支持消费积分,暂不支持积分兑换

## 行动项
| 行动 | 负责人 | 截止时间 |
|---|---|---|
| 完成支付容错测试 | 李四 | 8 月 25 日 |
| 提交会员积分 PRD | 张三 | 8 月 20 日 |
| 协调运营资源 | 王五 | 8 月 18 日 |

## 待讨论
1. v2.1 推迟对 Q3 OKR 的影响(下次周会讨论)
2. 会员积分的兑换比例(需财务确认)
```

### 2.5.5 质量验证

跑 10 场历史会议(用过去的人工纪要做 ground truth),计算 Skill 输出与人工纪要的一致率。

实测 10 场:决策完整率 95%、行动项完整率 88%、待讨论准确率 75%。**对"决策 + 行动项"足够准,人工只需 review 待讨论部分**,单场会议从 45 分钟压到 10 分钟。

## 2.6 第三个 Skill 案例:客户档案整理

这个 Skill 解决销售/客服团队的"客户信息分散"问题。

### 2.6.1 痛点

销售经理管 50+ 客户,每个客户的信息分散在:企业微信聊天记录、邮件、CRM 系统、合同 PDF、内部周报、会议纪要。**新销售接手一个老客户,要看 2-3 天历史材料才能进入状态**。

### 2.6.2 Skill 设计

输入:客户名(或客户 ID)
输出:一份"客户档案.md",含以下结构化字段:

- 基本信息(行业、规模、决策人、关系建立时间)
- 历史合作(过往订单、关键节点)
- 关键联系人(姓名、职位、关系强弱)
- 沟通偏好(喜欢的沟通方式、忌讳话题)
- 当前进展(最近 30 天的互动)
- 风险信号(超过 30 天未跟进 / 投诉记录 / 预算缩减迹象)
- 下一步建议

### 2.6.3 工作流

Step 1:输入客户名
Step 2:WorkBuddy 在授权目录搜所有含此客户名的文件
Step 3:按文件类型分类处理
  - 邮件 → 提取关键时间点
  - 聊天记录 → 提取关系信号
  - 合同 PDF → 提取订单与履约信息
  - 会议纪要 → 提取关键决策
Step 4:聚合到"客户档案.md"模板
Step 5:标注"信息置信度"(高/中/低,基于源文件数量)
Step 6:人工 review 后归档到客户管理目录

### 2.6.4 效果

实测:以前新销售接手客户,平均 2.5 天进入状态;用 Skill 后,2 小时拿到完整档案,**5-6 倍效率提升**。

**额外价值**:Skill 输出带有"信息置信度"标注,新销售能快速识别"哪些信息可靠、哪些需要再确认",避免凭过期信息做判断。

## 2.7 第四个 Skill 案例:招聘 JD 撰写

这个 Skill 服务于 HR 团队,解决"JD 质量参差"问题。

### 2.7.1 痛点

某公司 HR 团队,JD 撰写由不同 HR 负责,质量参差。新 HR 写的 JD 经常被业务部门批"看不懂""不吸引人"。

### 2.7.2 Skill 设计

输入:
- 岗位名(如"高级 Java 工程师")
- 业务部门填写的"岗位需求"表(原始素材)
- 公司 JD 模板

输出:
- 完整 JD(岗位描述、任职要求、薪酬范围、福利)
- 候选人画像(理想候选人的特征)
- 面试问题建议(5-10 个,按维度分类)

### 2.7.3 关键技巧

这个 Skill 的核心技巧是**"JD 风格学习"**——它会读公司过去 2 年发布的 30-50 份 JD,学习公司的 JD 风格(措辞偏好、长度、版式),保证输出与公司既有 JD 一致。

具体做法:
- 在 inputs.schema.json 加一个 `style_reference_folder` 参数
- 指向公司历史 JD 目录
- Skill 在工作流 Step 1 先读历史 JD 提取风格特征
- Step 2 撰写新 JD 时,严格模仿风格

### 2.7.4 效果

实测:HR 写一份 JD 从 1.5 小时压到 20 分钟,且新 HR 写出的 JD 与资深 HR 写的一致度达到 90%+(以"业务部门满意度"做 ground truth)。

## 2.8 第五个 Skill 案例:数据透视

这个 Skill 服务于运营/财务团队,解决"每次分析都要重新解释数据"问题。

### 2.8.1 痛点

某零售公司,运营经理每月做销售分析。每次分析,要重新解释"字段含义"——"GMV 是含税还是不含税""订单数算不算取消单""客单价是按订单还是按用户"。

AI 每次都"假设"一个口径,跟实际口径对不上,反复修正。

### 2.8.2 Skill 设计

这个 Skill 的核心是**"业务口径词典"**——一个 `data_dictionary.md` 文件,定义了每个字段的口径。

```markdown
# 销售数据字段口径

## GMV
- 定义:含税销售额
- 计算:订单金额(含税)+ 退款金额(负)
- 包含:已支付未发货订单
- 不包含:未支付订单、已全额退款订单

## 订单数
- 定义:已支付订单数
- 不包含:未支付、已取消

## 客单价
- 定义:GMV / 独立用户数
- 不按订单算(避免批发大单拉偏)
```

Skill 在工作流 Step 1 **先读这个词典**,所有后续计算严格按词典口径。

### 2.8.3 工作流

Step 1:读 `data_dictionary.md`,加载口径定义
Step 2:读用户给的 Excel/CSV
Step 3:让 AI 输出"字段映射表"——把数据列对应到口径词典
Step 4:按口径计算,生成透视结果
Step 5:输出图表 + 文字洞察

### 2.8.4 效果

实测:运营经理每月分析时间从 6 小时压到 1.5 小时,且**口径错误率从 30% 降到 5%**。

**额外价值**:口径词典本身就是组织资产——以后换人、换模型,只要词典不变,分析结果就一致。

## 2.9 Skill 的测试与发布

### 2.9.1 测试方法

每个 Skill 必须经过三层测试:

| 测试层级 | 测试者 | 测试内容 | 通过标准 |
|---|---|---|---|
| 单元测试 | Skill 作者 | 跑测试用例集,验证输出符合 schema | 100% 字段正确 |
| 集成测试 | 团队同事 3-5 人 | 在真实业务场景跑 5-10 次,人工 review | 80% 输出可直接用 |
| 回归测试 | 发布前 | 对比新旧版本输出,确认没退化 | 关键场景无退化 |

**特别强调"集成测试"**——单元测试通过不等于真实场景可用。我见过一些 Skill,作者自己测通过了,团队一用就出问题,因为作者对自己的"输入材料"太熟悉,默认了很多隐性假设。

### 2.9.2 发布渠道

WorkBuddy 的 Skill 有三个发布渠道:

| 渠道 | 范围 | 适合 |
|---|---|---|
| **WorkBuddy 技能市场(官方)** | 公开,所有用户 | 通用型 Skill(周报、邮件、纪要等) |
| **团队内部 Skill 库** | 仅团队成员 | 内部业务 Skill(本团队专用) |
| **个人 Skill 目录** | 仅本人 | 个人高频任务(私人模板) |

(关于"WorkBuddy 技能市场"的具体上架流程、审核机制,以 WorkBuddy 官方文档为准。)

**建议**:大多数组织级 Skill 用"团队内部 Skill 库"——它不上公网、仅团队成员可见、可以内部治理(下架、修订、版本管理)。

### 2.9.3 文档要求

发布前,Skill 必须有完整 README.md,包含:

1. Skill 名称、功能简介
2. 适用场景 / 不适用场景
3. 输入参数说明
4. 输出格式说明
5. 使用示例(2-3 个)
6. 已知问题与限制
7. 作者、联系方式、更新日期

**没有 README 的 Skill,不允许发布**——这是治理底线。

## 2.10 Skill 的版本管理

### 2.10.1 版本号规范

采用语义化版本(SemVer):

- **MAJOR.MINOR.PATCH**(主版本.次版本.补丁)
- MAJOR:不兼容变更(比如改了输出 schema)
- MINOR:向后兼容的新功能(比如加了新输入参数)
- PATCH:向后兼容的 bug 修复

例:V1.2.3 → V1.2.4 是修 bug;V1.2.4 → V1.3.0 是加新功能;V1.3.0 → V2.0.0 是 schema 变更。

### 2.10.2 更新流程

1. 开发者改 Skill,在本地测试通过
2. 提交 PR(写明变更内容、影响范围、测试结果)
3. 团队 1-2 人做同行 review
4. 团队负责人批准
5. 发布到内部 Skill 库,版本号 +1
6. 通知团队成员:"XXX Skill 已更新,建议试用"

### 2.10.3 废弃机制

当一个 Skill 有更好的替代品,或不再适用,要走"废弃"流程:

1. 在 README 加"⚠️ 已废弃,推荐用 XXX 替代"
2. 在内部 Skill 库标灰(仍可调,但显眼提示)
3. 保留 3 个月,让用户过渡
4. 3 个月后下架

**不允许"静默废弃"**——突然下架会让依赖它的同事工作断档。

### 2.10.4 变更日志

每个 Skill 必须维护 CHANGELOG.md:

```markdown
# Changelog

## V1.2.4 (2026-08-15)
- 修复:风险事项识别漏掉了"延期"关键词
- 改进:输出长度上限从 1500 调到 1800

## V1.2.3 (2026-07-20)
- 修复:特定 Excel 格式读不到
- 新增:支持 PDF 输入

## V1.2.0 (2026-06-10)
- 新增:支持"重点客户"加权重
- schema 变更:inputs.focus_areas 改为可选
```

变更日志是"组织记忆"——新人接手时,看日志能快速理解 Skill 的演进历史。

## 2.11 团队 Skill 库的治理

### 2.11.1 三类角色的分工

| 角色 | 职责 | 谁来当 |
|---|---|---|
| **Skill 开发者** | 写 Skill、维护、迭代 | 业务骨干(小王这种) |
| **Skill 评审者** | 评审新 Skill,把关质量 | 部门负责人 + 1-2 名资深员工 |
| **Skill 治理者** | 维护 Skill 库、版本管理、废弃决策 | 通常由 IT 或 PMO 兼任 |

### 2.11.2 评审标准

新 Skill 进入团队库,要过五个评审标准:

1. **必要性**:这个 Skill 真的解决高频问题吗?还是"为了 Skill 而 Skill"?
2. **质量**:输出是否稳定?测试通过率是否 ≥ 80%?
3. **可维护**:作者是否愿意长期维护?是否有备选维护人?
4. **文档**:README、CHANGELOG、测试用例是否齐全?
5. **安全**:是否涉及敏感数据?权限配置是否合理?

任何一项不通过,打回修改。

### 2.11.3 数量控制

**不要追求 Skill 数量**。一个团队超过 30-50 个 Skill,就会出现"找不到、记不住、用不上"的问题。

推荐:- 团队 5-10 人:核心 Skill 控制在 10-15 个
- 团队 20-30 人:核心 Skill 控制在 20-30 个
- 团队 50+ 人:核心 Skill 控制在 40-50 个,**且按部门/职能分目录**

**定期清理**:每季度 review 一次,识别"三个月无人调用"的 Skill,要么下架,要么找问题。

### 2.11.4 共享与归属

Skill 鼓励共享,但要明确归属:

- 作者署名(skill.yaml 的 author 字段)
- 部门归属(归属哪个部门)
- 维护责任人(谁是主备维护人)

避免出现"大家都在用,但没人维护"的孤儿 Skill。

## 2.12 把"老师傅经验"显性化——组织级 AI 落地的真正起点

讲完技术细节,我要回到一个更深的命题。

**Skill 化不是"技术工作",是"组织工作"**。

它的本质,是**把一个人的隐性知识,变成组织的显性资产**。这件事,日本管理学叫"知识管理"(Knowledge Management),中国管理学叫"经验沉淀"。

这件事,大多数中国组织做得很差。

我见过大量组织,资深员工离职,他的经验、诀窍、人脉、判断力跟着走。公司花 1-2 年重新培养新人,新人又花 1-2 年积累经验,又离职,周而复始。

**Skill 化打破这个循环**。

一个 5 年资深的销售,他的客户沟通话术、谈判节奏、风险预判经验,被显性化成 5-10 个 Skill,新人入职第一天就能调用,虽然新人用得不如老师傅精准,但**起步就比"零"强太多**。

这就是 Skill 化的**组织意义**——**它让组织不再依赖个人英雄主义,让知识变成可传承的资产**。

我建议每个团队,从最高频、最依赖老师傅的 3-5 个任务开始,做 Skill 化。不贪多,但要扎实。

## 2.13 小结

本章讲了五个核心判断:

1. **Skill 的本质是"提示词+文件+工具+输出"四要素打包**,它把"优秀员工的最佳实践"固化成可复用工作流。
2. **Skill 的开发是"显性化"过程**——把隐性知识从人脑里抠出来,写成结构化指令。这件事技术不难,难的是"愿意坐下来写"。
3. **Skill 的质量靠测试和迭代**——单元测试、集成测试、回归测试三层,加版本管理、变更日志、废弃机制。
4. **团队 Skill 库要治理**——三类角色(开发者、评审者、治理者),五个评审标准,数量控制,定期清理。
5. **Skill 化是组织级 AI 落地的真正起点**——它的价值不仅是"省时间",更是"让组织不再依赖个人"。

下一章,我们从"自定义 Skill"进入"多模型策略"——讲怎么用 API Key、自购模型、私有化部署,让组织不被单一厂商绑定。

## 2.14 实践练习

**练习 1:显性化你自己的一个高频任务**
- 选你每周做 ≥ 3 次的一件事
- 写下"做这件事的 10 步流程"
- 标出哪 3 步最依赖"经验"(新员工做不了)
- 把那 3 步展开写成"判断规则"(每条 1-2 句)
- 这就是你的 Skill 草稿

**练习 2:开发一个完整的"周报生成"Skill**
- 按 2.4 节的流程,完整走一遍
- 准备 3 个测试用例
- 让 2-3 个同事试用,收集反馈
- 迭代一版,发布到团队内部 Skill 库

**练习 3:治理你的团队 Skill 库**
- 列出团队现有所有 Skill(或个人常用模板)
- 标出"三个月无人调用"的
- 标出"作者已离职/转岗"的
- 输出治理方案:哪些下架、哪些维护、哪些保留
